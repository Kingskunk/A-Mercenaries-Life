# Gameplay Mechanics Rules

Shared implementation, combat, equipment, state-safety, and verification rules for *A Mercenary's Path*. Prose and voice live in `.agents/rules/narrative_guidelines.md`; quest shape, rewards, failure and time costs live in `quest/QUEST_DESIGN_RULES.md`. Cross-references below name the file and section.

## 1. ChoiceScript Code Discipline & State Hygiene
* **Strict Line-Separated Flow Control:** `*if`/`*elseif`/`*else`/`*set`/`*goto`/`*gosub` must start on their own indented lines — never inline within prose, or ChoiceScript prints the raw code to the player instead of parsing it.
* **No Nested Multireplaces:** `@{var1 @{var2 ...|...}|...}` fails to parse. Compute multi-condition stat hints into a `*temp` string (`${hint_text}`) before the `*choice` block instead.
* **Expressions Need Explicit Parentheses Around Every Operator Pair.** ChoiceScript does not chain operators: `a + b + c`, `x * 100 + y`, and `(a) and (b) or (c)` all throw "expected CLOSE_PARENTHESIS". Nest pairwise: `(((gold * 100) + (silver * 10)) + copper)`, and write `or`/`and` chains as `(((a) or (b)) or (c))`. Hit twice on the same "can the player afford 2 silver" check while writing the Iron Wharves and Pier quests; `quicktest` catches it immediately, but only on lines it reaches.
* **A Prose Line Must Not Start With `*`, and `*word*` Is Not Italics.** A leading `*` is read as a command, so a line like `*Clink.* The mallet strikes…` fails as an unknown command. Mid-line, ChoiceScript doesn't render `*word*` as emphasis at all and prints the asterisks literally. Use `[i]…[/i]` for emphasis anywhere in prose.
* **`*comment` Is the Only Comment Syntax.** A trailing `; note` or `// note` after a `*create` or `*set` becomes part of the line or a parse error. Annotate on a `*comment` line above instead.
* **Engine State Hygiene:** Every temporary roll modifier (`advantage`, `disadvantage`, `guidance_active`) must reset to `false` inside `roll_d20_check` on return, so bonuses never leak into unrelated choices.
* **Refresh/Replay Safety (No Bare `*set var +N`/`-N`):** A refresh or Stats/Menu round trip can replay the current page with no new player action, silently re-running every command on it. A bare increment/decrement is unsafe anywhere a page can pause (`*choice`, `*page_break`, before a `*gosub`/`*gosub_scene`) unless guarded:
  1. **Prefer a fully derived stat** — recomputed from persistent flags every time (`recalculate_armor_class`) instead of nudged with `+N` per change; a full recompute needs no lock at all.
  2. **Otherwise, lock the mutation:** `*if (not(X_locked)) or (not(locked_X_page_id = page_id)) ... *set stat +/-N ... *set X_locked true ... *set locked_X_page_id page_id` (`page_id` only advances on a genuine new choice/Next, never a replay). Reuse `currency_txn_locked` for silver/copper, `stat_bump_locked`/`locked_stat_bump_page_id` for everything else non-currency — don't invent a lock per stat or site (a full sweep found this exact bug at 40+ sites, all fixed with this one shared pair). If two independent mutations can land on the same page with no `*choice` between them (a hub spending an actions-left slot *and* granting a companion bump), give the second its own lock — the pre-declared `stat_bump2_locked`/`locked_stat_bump2_page_id` slot exists for exactly this, so reach for it before declaring a new one-off pair.
  3. **Splitting a `*if (check_success) *set stat +N ...prose... *else...` block to add a guard:** compute the bump once inside the guard, then follow with a second unguarded `*if (check_success)...*else...` purely for prose. Re-reading `check_success` is safe, but if the *prose* re-checks the stat you just bumped against the same threshold that decided the bump, a replay sees the already-bumped value and flips to the wrong prose. Capture the pre-bump boolean into its own persistent flag inside the guard instead (see `lyra_pay_generous`) and branch prose on that flag.
  4. **One page legitimately triggering the same kind of mutation twice** (some pages fall from one activity into another with no intervening choice, e.g. `calendar.txt`'s `advance_time`) needs a per-call-site identifier on top of `page_id`: `*set time_advance_call_id "<unique_id>"` before the gosub, lock compares both. Use a plain `*create`d variable, not `*params` — `*params` throws if reached without a real gosub (which quicktest's coverage pass does), where a `*create` default just reads as "unlocked."
* **A Dossier Action That Advances Time Must Put `advance_time`'s Lock Pair Back.** The dossier (`choicescript_stats.txt`) runs beside the game: what it writes with `*set` is carried back, and the page underneath is **replayed** when the dossier closes. `advance_time` remembers only its last call (`time_advance_locked`, `locked_time_advance_page_id`, `locked_time_advance_id`), so a rest taken in the dossier leaves the lock holding *its* id, and the page underneath then finds a lock that is not its own and applies its own time advance a second time (the clock ran an hour too far in a sabotage test). Save those three and `time_advance_call_id` in `*temp`s before the call and set them back after it (see `codex_rest_short`). Test it in a real browser with a page that has just advanced time: open the dossier, act, close, and check the clock moved by the action's time only. The dossier prints progressively, so wait for its last option to appear before reading or clicking it.
* **Class Resources Live in One Place, and No Scene Types a Pool Number.** The maximum of every class pool (Second Wind, Rage, Pact Magic, Wizard and Bard slots) is written down once, in `refresh_class_resource_maxs` (`startup.txt`), as a ladder over `character_class` and `character_level`; `update_dnd_stats` calls it, so the `_max` variables follow the level. A long rest is one routine, `restore_class_resources`: every pool refills to its max, temp HP clears, the Hexblood's Hex is ready again. Every sleeping place already calls `calendar.txt` `resolve_sleep`, and `resolve_sleep` calls that routine, so a sleeping place lists nothing (a new inn or camp that calls `resolve_sleep` gets a full long rest for free); the prologue rests call it directly. A short rest is `short_rest_preview` and `do_short_rest`, and the one-line banner a resting place prints is `short_rest_banner`. Panels show `x / ${..._max}`: a literal "/ 2" in a display is a bug. **Adding a pool** (second-level slots, Action Surge, Arcane Recovery) means its `*create` and `_max` create, one line in the ladder, one in `restore_class_resources`, (for a short-rest give-back) `short_rest_preview`, `do_short_rest` and `short_rest_banner`, and the displays (`choicescript_stats.txt`, `index.html`, `inventory.js`). It never means editing a scene that sleeps or rests. Second Wind follows the 2024 rules: 2 uses, 3 from level 4, 4 from level 10; a short rest returns one use, a long rest all of them.
* **A Genuine +1 Called From a Page Needs a Guard a Replay Cannot Repeat, and a `page_id` Lock Is the Wrong Guard in the Dossier.** `do_short_rest` gives a Fighter one Second Wind use, which is a real `+1`. A short rest always takes an hour, so the clock at its end is unique to it: `last_short_rest_stamp` remembers it, and a replayed page (same clock) gives nothing a second time. A `locked_..._page_id` set inside the dossier would be carried back with the *dossier's* page number, which the game's own `page_id` does not follow, so a later page could collide with it and silently skip a real rest. The dossier page itself is never replayed (it has a `saveSlot`, so `refreshSavedProgress` gives it no resume point); the page underneath is, and that is what the guard is for. Test it in a real browser with a pool that can still take a second give-back (Second Wind at 1 of 2: a pool at 1 of 1 cannot show a double give, because the replay finds nothing to give), and sabotage the guard once to see the test fail.
* **Max HP and Proficiency Are Derived From Level, and Only in `update_dnd_stats`.** `hp_max` is `character_level * (hit_die_max + con_mod)` (house rule: the maximum of the die at every level, solo campaign) and `prof_bonus` is `2 + (((character_level - 1) - ((character_level - 1) modulo 4)) / 4)`. Never set either anywhere else, and never change `character_level` without calling `update_dnd_stats` right after, so HP, proficiency and the pool maxima follow. Current HP moves by the change in max HP, so a level-up (like a CON buff) raises it by the same amount. The engine has no floor: `/` gives 2.25 at level 2 and `round()` gives 3 at levels 3, 4 and 8, so take the remainder off with `modulo` first.
* **The Level-Up Pool Is Derived From Success Flags; a New Quest Is One Line.** `refresh_quests_finished` (`startup.txt`) counts finished quests from flags that are set once, in the quest's success label, and never cleared; `refresh_level_up_progress` holds the thresholds and sets `level_up_ready`. Only a successful completion counts: a failed ending does not, and a radiant job (the crane shifts, the scrap round) never does. A quest whose failed ending still sets its stage to `resolved` (Silt-Gate, the Rotten Rib) must also test its resolution. Give every new quest its own completion flag: an item flag (a reward the player can hold, sell or lose) and a flag another route also sets (`turned_in_customs_vellum`, `met_morzan`) are not markers. Training sessions go through `training_preview` (on the page before) and `do_training_session` (after `advance_time`), guarded by the clock at the end of the session like `do_short_rest`; a training place never counts anything itself. "A day" is the day the session started.
* **A Level Is Taken by an Exact Target, and Everything Else Follows From State.** `do_level_up` (`startup.txt`) sets `character_level` to `level_up_from + 1`, where `level_up_from` was set on the confirm page (`codex_levelup`) before the choice, so a replay of the apply page sets the same level again instead of adding another. Current HP moves by the change in max HP (`update_dnd_stats`), and each class pool rises by the change in its maximum (the old maxima are captured in `*temp`s at entry, so a replay finds the maxima already changed and adds nothing). Class features for a new level plug into `do_level_up` after `update_dnd_stats`, one hook each; no place that levels the player up lists them, and the result page prints its pool line through `level_up_banner`. A sabotage run (`+ 1` instead of the exact target) doubled the level, HP and slots on replay.
* **The Top-Bar Level Up Button Is a Shortcut, Never the Decision.** It shows while `level_up_ready` is true and hides in a fight or while the dossier is open; it opens the dossier's own `codex_levelup` page, exactly as the Inventory's Rest card opens `codex_rest`, and the dossier menu offers the same choice, so a missing button loses nothing. `level_up_ready` is derived and kept current by `update_hub_condition` (called by `advance_time` and the district hubs); a sub-hub such as the room hub does not call it, so do not promise "every hub".
* **Detect the Open Dossier With `window.stats.scene.secondaryMode === "stats"`, Never With the Show Stats Button's `data-return`.** Closing the dossier from its own menu (`Close Dossier & Return`, which is `*finish`) leaves `data-return` set (`returnFromStats` never calls `setButtonTitles`), so a check on it stays true after any dossier visit: it hid the Level Up button and disabled the Inventory's Rest and Use buttons. The same quirk means the first Show Stats click after closing the dossier only reloads the page (engine behavior in `ui.js`, left as it is). Look the top-bar button up on every poll instead of caching it: the page rebuilds the bar, and a cached element goes stale.
* **A Training Place Follows One Shape, So Later Teachers Cost Prose Only.** The compound's drill square (`pv_poi_carrion`, `port_valen.txt`) is the pattern for every level's teacher: (1) a hub button that shows while `level_up_sessions_needed > 0`; (2) a place page with a layered intro and three options, where the training button is always listed and reworded when it cannot run, with the reason chosen hour first, then weather (a stormy night is "shut until morning", not "called off"), and the closure page reads the clock and `training_preview` directly and costs nothing; (3) a session page that sets `hours_to_pass training_hours` and `exposure_base_mins`, calls `calc_exposure`, `advance_time` (its own unique `time_advance_call_id`), `recalc_hp_from_neglect`, the death check, and only then `do_training_session`; (4) prose picked from `training_sessions` (`modulo` a pool of six, so no two sessions in a row match, and a replay prints the same words), never from the clock or `*rand`, with the hour a session began derived from the clock at its end, and a first-session and a last-session beat keyed on the count; (5) a talk page whose words follow the bands (sessions, quests) and whose numbers stay in a bracket line. The count, the once-a-day rule and the thresholds are never written in the place. A new squad or teacher adds vignettes and talk lines, and nothing that trains changes.
* **A Blank Line After an `*if` That Printed Nothing Does Not Start a New Paragraph.** The engine drops the blank line that follows a skipped block, so sky text followed by a false ground-memory `*if` and then the next layer ran together in one paragraph. Put the blank line BEFORE each optional check (after the text that always prints), as the compound hub does, and after the last always-printed line of a chain. Check it by rendering (`tools/render_hub.js`), which shows each paragraph on its own line.
* **Reset a Consumed Input Outside the Lock, Not Inside It:** A subroutine that clears caller-supplied working variables when done (`advance_time` zeroing `minutes_to_pass` etc.) must do that reset *unconditionally after* the guarded math, never inside the same guard — otherwise a replay's skip also leaves the variable stuck at its last input instead of clean, since resetting to a fixed literal is always safe to repeat and needs no lock.
* **A Column-Wise Currency Subtract Can Drive a Higher Denomination Negative Even With Plenty of Total Funds.** Decomposing a spend into gold/silver/copper and subtracting each column independently only borrows when silver/copper goes negative — nothing borrows into gold, the top denomination, so a cost large in a denomination the player holds none of can drive that column negative even with ample total wealth. Always recompute from total value (`(gold*100)+(silver*10)+copper) + currency_add_amount`, then re-split fresh) instead of adding/subtracting per column — there's no individual column left to run short on.
* **A Shared Subroutine Called Multiple Times On the Same Page Needs a Per-Call-Site Lock — a Single Shared "Last Call" Id Is Not Enough Past Two Calls.** A `_call_id` comparison against one remembered value only tracks the most recent caller: fine for a subroutine invoked once, but if a loop calls the same guarded subroutine 3+ times on one page (e.g. `fight_enemy_turn` calling `resolve_enemy_attack` once per living enemy slot), each new call overwrites the remembered id, so a replay reconstructing from post-round stats finds an earlier slot's id no longer matching and re-rolls it fresh. Fix: independent per-call-site memory (e.g. one boolean per slot, `combat_enemy_atk_locked_1/_2/_3`), not one shared id.
* **A Persistent Stat Read For Display, Then Zeroed Later On the Same (Guarded) Page, Needs the Read Inside the Guard Too — Not Just Before It.** Reading a value for display before the guarded block that zeroes it isn't safe just because it runs first in program order — a refresh reconstructs from *current* stats, which by replay time may already hold the post-reset value, so the unguarded read reproduces as blank/zero. Move the display computation inside the same guard as the reset, so it's captured atomically with the mutation that would otherwise erase its input. (A read of a value that's only ever incremented, never reset, is safe either side of the guard — the risk is specific to a read sitting right before something in the same block zeroes that value.)
* **A Guarded Incremental Mutation Can Be Silently Erased By an *Unrelated*, Unconditional Line That Touches the Same Stat on the Same Page.** If a guarded mutation and an unrelated unconditional line both write the same stat on the same page, the unconditional write reruns on every replay while the guarded one only applies once — it silently outruns and erases the guarded value. Once you spot two writers to one stat on one page with only one of them guarded, stop mutating that stat from either side and recompute it as a pure function of persistent, correctly-guarded inputs instead (`recalc_hp_from_neglect` is the pattern: `hp_current` is persistent health and the two neglect debts are applied to it by delta against `hp_debt_applied`, so a second call with unchanged debts changes nothing and a wound survives every recalc) — same "prefer a fully derived stat" principle as the refresh-safety rule above.
* **`*goto_scene` Must Never Fire From Inside an Active `*gosub_scene` Call.** `scene.js`'s own `goto_scene` detects this case (a non-gosub `*goto_scene` while `choice_subscene_stack` is non-empty), logs a warning, and discards the entire subscene stack — corrupting any outer `*return` still pending. A shared subroutine that needs to end the game or jump scenes on some internal condition (`calendar.txt`'s neglect clock hitting 0 HP, for instance) can't do that jump itself; it has to surface the condition as a plain stat (`hp_current <= 0` is already visible to the caller) and let the *top-level* caller — after its own `*gosub_scene` call has already returned — do the `*goto`/`*goto_scene`. This is why Port Valen's neglect-death check is a 3-line idiom repeated at every call site (`port_valen_rest`, `port_valen_eat_mess`) rather than one shared subroutine that jumps internally.
* **Full Slot Coverage:** When gating by learned spells/cantrips, check every slot (primary, secondary) so no build is orphaned.
* **Three-Point Metadata Synchronization:** New lore/location/faction/companion needs all three: (1) `*create var false`, (2) progressive disclosure in the dossier (`*if (var)`), and (3) dev jump menus setting all prerequisite flags/clock state.
* **One-Time Story Grants Guard Themselves:** Wrap a discrete once-only grant (reward, relationship bump, item handoff) entirely in `*if (not(has_X)) ... *set has_X true ...`, checked before any side effect. Naturally replay-safe on its own — no `page_id` lock needed, that's only for mutations with no natural "already happened" flag (e.g. currency, where the amount varies by branch).
* **Guard One-Time Init on a Dedicated Flag, Never a Variable With a Matching Default:** Gate a run-once block with its own `*create ..._initialized false`, not another variable's value, without confirming its `*create` default first — if that default already reads as "done" (e.g. a non-empty-string default against a guard checking `= ""`), the guard is permanently stuck one way and never fires.
* **`*set var -1` Is Decrement Shorthand, Not "Set to -1":** A leading `+`/`-` on `*set`'s right-hand side always means "adjust the current value," even when a literal assignment was intended. To assign a literal negative, use an expression whose first token isn't an operator: `*set var 0 - 1`.
* **A Bare `*create X 85` Stores a String; Only `*set X +N` Produces a Real Number.** `typeof` stays `"string"` until real arithmetic runs on it (ChoiceScript's own comparisons coerce loosely, so this is usually invisible). A Node harness inspecting `stats` directly must coerce with `Number(v)`/`isNaN`, not trust `typeof`.
* **`/` Never Floors — Halving an Odd Number Produces a Fractional Stat ChoiceScript Will Happily Print.** A plain `/ 2` for a resistance/half-damage effect looks right and passes any test that only checks "did the number go down," but an odd input yields a fraction (`HP: 10.5 / 14`) that prints verbatim with nothing catching it. Any `/ N` meant to floor needs `(X - (X modulo N)) / N` instead (already used for `currency_add`'s carry math and `resolve_dissonant_whispers`'s half-damage) — plain `/` is only safe when the numerator is provably always a multiple of the divisor.
* **When auditing a system for missing mechanics, the dossier (`choicescript_stats.txt`'s `print_ability_card`/class-features section) is the fastest source of truth for what's *promised* — grep it for "advantage"/"disadvantage"/"until"/"can't"/"reaction" and cross-check each hit against the actual combat code.** A feature can be selectable at character creation and fully described in the dossier while doing nothing in an actual fight (found this for two Fighter Fighting Styles and Barbarian Unarmored Defense this way). Not every promise is worth chasing, though: a rider that needs infrastructure the engine doesn't have yet (an ally combatant, a short-rest event distinct from long rest) is a real feature to flag, not a cheap fix — implementing one such ability while its siblings silently stay unwired would leave the game *more* inconsistent than leaving all of them alone. Fix what maps onto mechanics that already exist; flag what would require inventing a new one, don't half-build it.

## 2. Equipment & Magic Item Systems
* **Tradeable Items Live in `tools/gear_catalog.json`; the Repeated Code Is Generated, Never Hand-Written.** One catalog entry per item (id, kind, names, retail price, hint, blurb, optional per-shop `quotes` for unique dialogue, optional `warn`, tier, sell percentages, loadout fields, dossier text). `node tools/gen_gear.js` (also run automatically by `compile.js`) rewrites every block between `GEN:BEGIN <name>` / `GEN:END <name>` marker lines: the `*create has_<id>` / `spare_<id>` / cart variables (`startup.txt`), the loadout branches including the sidearm variants and the `gear_info` trade table (`equipment.txt`), the dossier list lines and equip options (`choicescript_stats.txt`), the inventory panel entries (`inventory-data.js`), each shop's buy and sell stanzas and its trade-panel cart pass (`port_valen_middle_ward.txt`, `port_valen_dredge_end.txt`), and `web/mygame/trade-data.generated.js`. Never edit inside a generated block; `node tools/gen_gear.js --check` exits 1 if one is stale. To add an item: add its catalog entry, list its id in each shop that stocks or buys it (`shops` in the catalog), run the generator. The shared routines do the rest (`gear_buy_label` / `gear_sell_label` build option text, `grant_gear` and `sell_gear` change ownership through `{gear_flag_var}`, `gear_sale_value` prices a sale, and each shop's single `*_buy_do` / `*_sell_do` holds the currency lock and `advance_time` once). A sell shop's `buyer` is `smith`, `pawn` or `general` (the flat 50% counter Hollis & Daughters and Vael & Son both use); each buyer reads its own `sell` percentage, and a price that floors to 0 means the buyer declines, so keep a cheap item's retail high enough that 50 percent is at least 1 copper. To add a whole new shop, add the two marker pairs to its scene, a `*_buy_do` / `*_sell_do` label copied from Halda's, and a `shops` entry (plus a `trades` entry and the `*_open_panel` / `*_cart_pass` / `*_settle` labels if it should offer the trade panel). Armor picks an existing `armor_type` (the type decides the AC formula and tier), and quest rewards or story items stay out of the catalog. Set `flags: {create: false, hand: true}` for an item whose flag or dossier text is hand-written. **Worn clothing** is catalog kinds `cloak`, `hands`, `waist`, `feet` and `neck` (loadout `desc` and `prose`, stackable), with optional `traits` `{cold, wet, heat, stat, bonus}` (see the paper-doll rule below and the readme in the catalog). A shop with `"menu": false` feeds only the trade panel, so several plain category menus can share one panel list (the Gilt Needle does this). The sell `buyer` `tailor` is Fenwick. The equipment slot an item fills (Cloak, Hands, Body armor and so on) is derived from its `kind` (`slotLabel` in `gen_gear.js`, `gear_slot` at runtime) and shown in the shop menus, the trade panel and the inventory; tools and consumables show none.

* **Item Titles Are Short and Plain.** Three words or fewer, no treatment words (boiled, oiled, waxed, tarred, riveted, lined, quilted) and no lore prefixes in the title; that detail belongs in the `blurb` and the dossier `line`. A longer title wraps to a second line in the trade panel, the inventory and the slot cards. A rename changes display text only (ids never change) and has to be swept across `tools/gear_catalog.json`, the hand-written loadout tables in `equipment.txt`, `company_intake.txt` and `startup.txt` (chargen and dev-preset `*_desc`), `choicescript_stats.txt`, `inventory-data.js` and `inventory.js`, acquisition banners and purchase buttons in the scenes, and `EQUIPMENT_AND_ITEMS_REFERENCE.md`; grep the old title afterward. Only the title shown in the panels and lists is shortened: an NPC's dialogue, narration and acquisition banners may keep an item's full in-fiction name (Talia's "Pitch-Sealed Deck Boots" is still that in the reward banner), and quest documents whose full names are spoken in dialogue (the Grey Waterway Toll Register, the Gilded Scales Letter of Credit) keep them. Two items must never share a title (the outlaw's "Scout Boots" and the armor "Scout Wraps" once collided).
* **What a Worn Piece Does Is Shown Everywhere From One Table.** The text for a worn piece (weather cuts, score bonus) is the `*set garment_hint` line in `equipment.txt` `garment_traits`. `tools/gen_equipment_data.js` publishes it as `window.GARMENT_HINTS`, and the inventory panel's slot cards, the inventory item list, the trade panel's "Wearing:" comparison under each equipment row, and the dossier's worn-gear lists all read it (the dossier through `garment_traits` directly). A worn piece with no bonus says "No bonuses" on its card. The attuned Hearthstone is the one worn piece outside the table and is special-cased in the JS and the dossier. Never hand-write a piece's numbers in a panel.
* **Equipment Score Bonuses Are Derived From What Is Worn, Never Written.** `recalculate_equipment_bonuses` (`startup.txt`) reads `garment_traits` for the seven worn slots (armor, head, cloak, hands, waist, feet, neck), takes the single highest `garment_bonus` per stat (they do not stack, and the attuned Hearthstone's +1 CON is one candidate), stores `equip_<stat>_bonus`, and rebuilds the scores as base + timed boon + equipment before calling `update_dnd_stats` (which shifts max HP by the CON change and recomputes AC). Every `equip_*` routine and `attune_item` call it, and it does nothing until `loadout_initialized`. Any code that puts on or removes clothing goes through `equip_<slot>` / `equip_by_slot` and `sell_gear`, never a bare `*set equipped_<slot>_id`. **The inventory panel cannot recompute scores**, so a swap where the piece going on or coming off carries a `statBonus` is handed to ChoiceScript: `inventory.js` sets `equip_slot` and `equip_item_id` and opens `choicescript_stats` `codex_equip_do`, the same way Use opens `codex_use_do`.
* **Gear Is Stackable, and the Trade Panel Is Only a Layer Over the Menus.** `has_<id>` means "at least one" and `spare_<id>` counts the copies beyond the first (stackable kinds: armor, shield, weapon, head, tool), so any code that grants or takes catalog gear goes through `grant_gear <id> <copies>` / `sell_gear`, never a bare `*set has_<id>`, unless it is a one-off quest reward outside the catalog. `sell_gear` is also how a scene spends one copy of a used-up tool (a rope let down a shaft, a torch burned): it gives up a spare first and clears `has_<id>` on the last copy, so a later scene can gate an option on `has_hemp_rope` and take the rope with it. The general goods (rope, torch, lamp oil, tinderbox, chalk) are catalog tools with no effect of their own yet; they exist so those options can be added to quests later. The trade panel (`web/mygame/trade.js`) only builds a cart and clicks the hidden `⚖ Settle up the trade panel.` option; prices, counts, coin and stock are decided in ChoiceScript (`equipment.txt` `shop_*`), inside the shop's currency lock. Every shop that offers the panel keeps its plain "look over the racks" / "put something on the bench" menus as a fallback, and the panel never becomes the only way to trade.
* **Consumables Are Catalog Items Used Through One Routine.** A potion, salve or draught is a `kind: "consumable"` catalog entry with an `effect` (`heal` dice, `boon` stat/bonus/minutes, `wash`, or `dressing`), stackable through `has_<id>` / `spare_<id>`. A `wash` (the lye soap) resets the hygiene clock to Clean, needs open water within reach (`equipment.txt` `water_at_hand`, always false for now so it does nothing in the city; add a camp or overland water test there when those exist) and is refused inside six hours of the last wash; a `dressing` (Ambrose's linen bandage) sets `dressing_on` and is refused while unhurt or while one is already on, and `calendar.txt` `resolve_sleep` adds `dressing_bonus` HP to the next sleep that heals and clears it. Both are refused without being consumed. A new effect type needs `gen_gear.js` (`effectSummary`, `genGearInfo`) and a branch in `use_consumable`. Its effect is written only in `equipment.txt` `use_consumable`; the combat option, the dossier's satchel menu (`codex_use`) and the inventory panel's Use button all call it, so never write a one-off `*set has_x false` heal. Healing consumables are free in combat but out of combat share the once-a-day instant-heal limit (`last_mundane_treatment_day`), so a stack of them cannot bypass slow healing; boons have no limit and take a unique-buff slot. Using one mid-fight costs the turn, and the dossier refuses while `combat_engaged` is true, so any new fight exit must go through `fight_cleanup`.
* **Armor Has a Derived Tier and a Class Proficiency Rule.** `armor_tier` (none/light/medium/heavy) is derived from `armor_type` at the end of `apply_armor_loadout`; a new armor id needs its `armor_type` mapped there, an AC branch in `recalculate_armor_class`, and the same branch in `EquipmentEngine.recalcArmorClass` (`equipment-panel.js`, which also mirrors the tier and proficiency; run `tools/check_ac_formula_sync.js`). `armor_prof_check` holds the class table, and `armor_nonprof` becomes disadvantage on STR and DEX rolls in `roll_d20_check`. Spellcasting is intentionally not restricted. The starting kit is grandfathered. Shops show a proficiency warning through `armor_prof_check` and never gate on it. Shields follow the same rule through `shield_prof_check` and `shield_nonprof`, with a grandfathered starting shield; never sell or drop gear by class, because loot has to work for every build.
* **New Weapons/Armor Route Through the Loadout System, Never a Bare `*set weapon`:** Direct `*set weapon`/`weapon_desc` etc. belongs only in chargen archetypes and inside `apply_weapon_loadout` itself. Anything picked up mid-game must instead: grant a `has_X` flag, add a branch in `apply_weapon_loadout` keyed by a new `equipped_weapon_id`, and let the player switch via `*gosub_scene startup equip_weapon "X"` from the Equipment codex. Every weapon needs a `weapon_hands` tag; equipping two-handed auto-drops `shield_equipped` via `apply_weapon_loadout`.
* **Magic Items Are Attuned, Never Given Outright:** A bonus must never be a permanent `*set <stat> +N` at pickup — attunement has to be *revocable*. Instead: grant `has_X`, add the bonus as a candidate in `startup.txt` `recalculate_equipment_bonuses` keyed on `X_attuned` (the Hearthstone's +1 CON is the model; `recalculate_attuned_bonuses` is now only a thin wrapper around it), bind/unbind via `attune_item "X"`/`unattune_item "X"`, capped by `max_attunement_slots` (5). Equipment bonuses to the same score do not stack, so an attuned bonus and a worn piece's bonus compete and only the highest counts. An ability-score bonus needs a `base_<stat>` snapshot (from `update_dnd_stats`) so it can be added/removed cleanly. Auto-attune on pickup if a slot is free, mirroring the shield's auto-equip.
* **The Full Paper-Doll (Head/Cloak/Hands/Waist/Feet/Sidearm/Neck/Ring1/Ring2) Follows the Same Id-Driven Shape, Scaled to What Each Slot Actually Needs.** Every slot has an `equipped_<slot>_id` (or, for rings, one shared `apply_ring_loadout`/`equip_ring` taking `*params ring_slot item_id` — a ring means the same thing on either hand, so one subroutine beats two copy-pasted `*if` chains) and a pure `apply_<slot>_loadout` re-derive called unconditionally from `update_dnd_stats`, exactly like weapon/armor. Head is the only cosmetic-shaped slot with real AC math (`head_ac`/`head_is_armor`, gated into `recalculate_armor_class`) — Cloak/Hands/Waist/Feet/Neck never call `recalculate_armor_class`. Every worn slot has traits in `equipment.txt` `garment_traits` (percent cuts to the cold, rain and heat parts of outdoor exposure, and an optional ability-score bonus), read at use time from the equipped ids so a swap never leaves a stale value: `calendar.txt` `calc_exposure` sums the cuts over every slot and `startup.txt` `recalculate_equipment_bonuses` derives the score bonuses. The clothing slots are catalog kinds (`cloak`, `hands`, `waist`, `feet`, `neck`, plus `head` and `armor`) with `traits` on the item; older hand-written worn items keep hand rows at the top of `garment_traits`. The dossier's Apparel and Accessories pages and the inventory panel's Cloak, Hands, Waist and Feet dropdowns are the swap routes. Don't invent per-slot variants of this shape; a new slot is a new `equipped_<slot>_id` + `apply_<slot>_loadout`/`equip_<slot>` pair, nothing more.
* **A Mundane Find (No Stat Bonus) Skips the Attunement/Dossier Indirection Entirely.** Not every pickup needs the `has_X`-gated dossier-choice flow above — that machinery exists to manage a *revocable bonus*. An item with no mechanical effect (a found signet ring, a keepsake) just does `*set has_X true` + `*gosub_scene startup equip_<slot> "<item_id>"` directly at the pickup site, with a branch in the matching `apply_<slot>_loadout` for its desc. Reaching for attunement plumbing on a flavor item is over-engineering; reach for it only once an item actually grants something `recalculate_attuned_bonuses` (or an AC/damage equivalent) needs to track.
* **Equipment Ability-Score Bonuses Are Ordinary and Do Not Stack; a Bonus on the d20 Roll Itself Is the Rare, Gated Kind (rewritten 2026-09-26 at the user's direction).** A +1 to an ability score is modest: modifiers step every two points (10/12/14/16, capped at +3), so a +1 raises the modifier only when it lifts an odd score onto the next even number (about +0.5 on average), and a +2 always raises it by exactly 1. Ordinary purchasable gear (a tailor's coat, gloves, a belt) may carry a +1 or +2 to a score. **Equipment bonuses to the same score do not stack: only the single highest equipment bonus to that stat applies** (food, drink, sleep and other timed boons are a separate channel and still add; different stats each get their own). What is rare is a flat bonus applied to the roll itself: +1/+2/+3 to d20 checks, attack rolls or spell save DCs, or advantage. That is worth a full point on every roll, so it belongs only to powerful items and rare sources: a named NPC's personal gift, a rare quest reward, late-game content. Early, ungated finds (battlefield salvage, a strongbox, a found-not-sold item) stay mundane (`QUEST_DESIGN_RULES.md` §10's "tangible and modest"). Penalties on the roll (fatigue, routine, grime) are a separate mechanic and stay as they are. Attunement (§2 above) still governs magic items, and any bonus must be derived and revocable, never a permanent `*set`.
* **The Inventory Panel (`web/mygame/inventory.js`) Is a Deliberate, Scoped JS Mirror of Equipment Logic — Not a Second Source of Truth.** `equipment.txt` stays the only place item data and rules are authored. `tools/gen_equipment_data.js` parses every `apply_<slot>_loadout` id-lookup table straight out of `equipment.txt` into `web/mygame/equipment-data.generated.js` (auto-run from `compile.js`'s Node CLI branch) — adding a new item id there is picked up automatically, no JS-side duplication needed. The only hand-ported logic is `equipment-panel.js`'s `EquipmentEngine.recalcArmorClass`, a ~15-line copy of `recalculate_armor_class` kept in lockstep by `tools/check_ac_formula_sync.js` (drives real headless playthroughs via `randomtest.js`'s harness, diffs the real AC against the JS mirror's) — **run it after any edit to `recalculate_armor_class` and fix the mirror if it fails.**
* **`equip_weapon` Must Swap, Not Overwrite, When the Incoming Id Already Sits in the Sidearm Slot.** Sidearm items carry no `has_X` ownership flag — a swapped-in sidearm's *only* record of existing is `equipped_sidearm_id` itself. `equip_weapon` (and its JS mirror, `EquipmentEngine.equipItem`) both check `new_weapon_id = equipped_sidearm_id` first and swap the two ids instead of blindly overwriting, or the previously-swapped-in sidearm item is permanently erased (both slots end up pointing at the same id) the moment the player picks "switch back to starting" after using "swap to sidearm" — a real bug found live via the Inventory panel, fixed at the source in `equipment.txt`, not worked around in the JS layer alone. Any future slot pair that shares an id space the same way (weapon/sidearm today) needs the identical guard.
* **The Inventory Panel's Interactive Slots Must Match What `choicescript_stats.txt`'s Real `codex_equipment_*` Menus Actually Offer — Never What `EquipmentEngine` Could Technically Do.** `inventory-data.js`'s `equippedSlots` gates each slot's control on `swappable: true`, set today for Weapon, Armor, Shield, Head, Cloak, Hands, Waist and Feet because that's the real menu's actual scope (always offers "switch back to starting/origin-default" regardless of ownership, has_x alternates, and for Weapon a separate sidearm-swap action). Neck (the Hearthstone's attunement lives in the dossier), Rings and Sidearm have no picker in the panel. A swap where the piece going on or coming off carries an ability-score bonus (`statBonus`) is handed to the dossier (`codex_equip_do`) so ChoiceScript re-derives the scores. Building a swap control for a slot the real menu never exposed produced a real, player-visible bug (every dropdown showing "None" with nothing to switch back to, since a slot with only one real candidate collapses to no control the moment you leave it) — re-adding `swappable` to a slot needs the real menu checked for a matching choice first, not just "the engine supports it."
* **A Renamed Item Id's Display Fields (`*_desc`/`*_prose`) Touch More Files Than `equipment.txt` Alone.** Beyond the obvious loadout tables, a rename has to be swept across: `company_intake.txt`/`startup.txt` (chargen `*create` defaults and dev-menu presets), `choicescript_stats.txt` (both the live stat display AND the real `codex_equipment_*` menu's `*choice` option text, which hardcodes item names in player-facing labels), any scene banner/shop text that names the item directly (`alderford.txt`, `port_valen.txt` — found via grep, not assumption), `web/mygame/inventory-data.js` (the Inventory panel's own catalog), and `EQUIPMENT_AND_ITEMS_REFERENCE.md`. Grep the old name and the full banned-jargon list across the whole `web/mygame` tree after every rename pass — the "obvious" file list reliably undercounts real references.

## 3. Reusable Town-Content Primitives (Gambling, Taverns, Currency)
* **Never Hand-Roll a New Ante/Payout/Lock Trio Per Town — Call the Shared Subroutine.** `startup.txt` provides three so future towns don't reinvent this plumbing:
  * `currency_add` — pure arithmetic, no locking of its own. Input `currency_add_amount` (signed, copper-equivalent); adds/spends against `gold`/`silver`/`copper` with correct carry/borrow. Always call from inside the caller's own replay guard.
  * `resolve_wager` — one subroutine for any gambling table. Set `wager_bankroll_var` (that table's own bankroll stat name), `wager_ante_copper`, `wager_win_copper`, plus the usual `check_*`, then gosub. Debits the ante, credits the house, pays out on success capped to the bankroll. Returns `check_success` and `wager_bankroll_busted` — use the latter to hide the option once the house is tapped out (`taphouse_dice_table`). A new den just needs its own bankroll stat and a few `*set`s.
  * `buy_tavern_item` — one subroutine for a purchasable consumable that spends coin and optionally heals HP and/or grants the single-slot nourishment buff. Set `tavern_item_cost_copper`, `tavern_item_hp_heal`, and (if buffing) `tavern_item_buff_*`, then gosub. Hide an item's option while its own buff is already active, so players can't re-buy an effect they have.
  * **Food, drink, unique and sleep buffs are timed ability-score boons, not roll bonuses.** A buff's `_stat` and `_bonus` add to the ability SCORE (`buff_<stat>_bonus`, summed by `recalculate_buff_stats` in `startup.txt`). The six score variables (`strength` ... `charisma`) HOLD the boosted number, so the sidebar, dossier, every modifier and every raw-score check agree; `base_<stat>` keeps the unboosted score. After chargen never write a score directly: change `base_<stat>` and call `recalculate_buff_stats`. The scores are base + timed boon + equipment (`equip_<stat>_bonus`, from `recalculate_equipment_bonuses`, which also folds in the attuned Hearthstone); the two channels are separate, so a boon still adds when a worn piece already gives the same stat. Modifiers derive from the boosted score in `update_dnd_stats` / `recalculate_con_mod`, and `buff_<stat>_helps` records whether a boon actually moved the modifier. Modifiers step at even numbers (10-11 is +0, 12-13 is +1, 14-15 is +2, 16+ is +3), so a +1 only matters when it lifts an odd score, which is what makes food choices and where the player buys them a real decision. It flows into everything derived: attacks and checks, AC (DEX), and max HP (CON, applied as a delta so wounds persist). Never add a buff to a d20 roll or write "+1 X checks" in player text; write "+1 X". `recalculate_buff_stats` is fully derived and only re-derives when a total changed, so call it after any code path that starts a buff (the shared primitives already do) and after buffs decay (`calendar.txt` does). Raw-score gates such as `wisdom >= 13` see the boosted score.
  * All three handle their own internal replay locks already (`resolve_wager`'s ante and payout each get a dedicated pair) — a caller doesn't need `currency_txn_locked` around calls into them, only around hand-written currency mutations elsewhere.

## 4. Testing Tools & Verification
* **Several complementary tools/techniques — use the right one, and don't treat any one as sufficient alone:**
  * `quicktest.js` (`node quicktest.js web/mygame`) — parses every scene and walks every reachable line once. Catches parse errors and `*goto`/`*label`/variable typos. Doesn't catch logic bugs.
  * `randomtest.js` (`node randomtest.js num=N seed=S`) — plays start-to-finish with random options, `N` times. Catches crashes/reachability across real playthroughs; does **not** check refresh-safety (never revisits a pause point it already passed).
    * `showUnreachedLabels=true` cross-references every `*label` against the run's hit-count map and reports the ones that stayed at 0 — cheap way to catch dead content (an `*if` guard that can never be false, a `*label` nothing `*goto`s anymore). Not automatically dead, though — may just be content this seed range didn't reach (especially squad/origin-gated); rerun with a different `num`/`seed` before concluding it's truly unreachable.
    * `gotoLoopCap=N` (default 200000) guards against a *goto cycle with no intervening `*choice`/`*page_break`/`*finish`/`*ending` — that shape runs entirely inside one synchronous JS call, so Node never gets a chance to time out or interrupt it, and an unguarded run would hang forever with zero output. Counts every `*goto` across a whole playthrough (monkey-patched onto `Scene.prototype.goto`, not a change to `web/scene.js` itself) and throws past the cap instead. Hitting it isn't necessarily a code bug: an open-world seed that keeps choosing to eat/rest can genuinely wander forever with nothing forcing a `*finish` (this is exactly what first surfaced Port Valen's now-fixed free-mess exploit, see the Neglect Clock entry in `QUEST_DESIGN_RULES.md` §12) — `randomtest.js` reports this case as `OPEN-WORLD WANDER (seed N)` and moves on to the next seed rather than aborting the whole batch, since it isn't a crash.
  * `refresh_fuzz_test.js` (`node refresh_fuzz_test.js num=N seed=S`) — catches the refresh/replay-duplication class the rest of this doc guards against. At every pause, snapshots stats, independently replays the page against a clone, diffs the result; any stat that comes out different re-ran on replay and shouldn't have. Run after any change touching a bare `*set stat +N`/`-N`, not just once at the end.
    * `mode=smart archetype=str|dex|con|int|wis|cha|balanced` makes the walk build-aware: scans each option for its `check_stat`, always takes an available `[Cantrip: Guidance]` first, otherwise prefers the archetype's matching stat (or the build's actual highest for `balanced`). Gives repeatable coverage of each archetype's real success paths instead of depending on chargen RNG. `showChoices=true` logs every pick and why.
    * `[refresh-duplication]` findings are always worth investigating. `[shadow-diverged]` and `[shadow-no-pause]` are diagnostic-only categories (see below) — don't chase them as bugs. `quietDiagnostics=true` collapses both into one summary count each instead of printing every instance, so real findings aren't buried under routine diagnostic noise on a large run — flip it off (the default) when actually investigating why a specific page diverges.
    * `gotoLoopCap=N` (default 200000), same mechanism and same reasoning as `randomtest.js` above — counts every `*goto` across a whole iteration (main walk plus every shadow probe it runs) and reports `OPEN-WORLD WANDER (seed N)` instead of a `[crash]` finding when it fires, since a wandering seed isn't a code bug either.
  * `tools/lint_thin_prose.js` (`node tools/lint_thin_prose.js [minWords=10]`) — static scan flagging `*choice` options that resolve with little or no actual narration before the next `*goto`/`*gosub_scene`/choice (something happened — damage dealt, an item bought — with no prose wrapped around it). Catches what none of the above can: a thin resolution is perfectly valid ChoiceScript and won't crash or diverge on replay, it just reads as an empty beat. Report-only (`THIN` findings are the punch list; `SILENT` — zero printed output — is mostly this codebase's normal "selection-menu with header-only flavor, shared narration after the `*choice` block" pattern and isn't printed at all by default, pass `showSilent=true` for the list; `DELEGATED` options whose prose comes from a `${variable}` — this project's shared-flavor-string pattern, see `combat.txt` — can't be scored statically and aren't flagged).
  * `tools/lint_mechanics_leak.js` (`node tools/lint_mechanics_leak.js`) — greps narration (outside `[brackets]`/`${...}`/`[b]...[/b]` banner spans) for mechanic vocabulary leaking into prose per `QUEST_DESIGN_RULES.md` §11: `DC <N>`, `<N> damage`, `<N> HP`, `NdN` dice notation, "armor class" or an ability check named directly ("a STR check"). Caught a real instance this way (a Relentless Endurance beat narrating "clinging to 1 HP" — fixed by grounding it in sensation instead, the HP number was already shown in the banner line right after). Report-only; expect the occasional false positive in the dossier's own stat-card lines if a new one doesn't use the `[b]...[/b]` banner convention.
  * `tools/lint_prose_tics.js` (`node tools/lint_prose_tics.js [includeNegativeFraming=false]`) — greps for the specific filler phrases `narrative_guidelines.md` §6 names by pattern ("says nothing"/"without a word", "Not X. Just Y.", a standalone one-word dialogue reply, "the way he always"/"the kind of quiet that", "files it away"/"let that settle"). The "doesn't/didn't `<verb>`" negative-framing check is off by default — on this codebase it produced ~53 hits, nearly all legitimate (weather/fact descriptions, or already-compliant "didn't X. Did Y instead" framing) — opt in only when specifically hunting that pattern. Report-only.
  * `tools/lint_weapon_assumption.js` (`node tools/lint_weapon_assumption.js`) — flags `narrative_guidelines.md` §9's forbidden phrases (pommel, hilt, scabbard, bare steel, iron grip, half-drawn, clutching your weapon) and walks each match's enclosing `*if`/`*elseif` chain (stopping at a `*label`) to check whether anything actually gates on `weapon`/`weapon_type`. `VIOLATION` = no such gate anywhere in scope (confident). `REVIEW` = some weapon-related gate exists but the tool can't confirm it's scoped to bladed weapons specifically (that section's own trap: `character_class = "fighter"` alone doesn't prove a blade). Caught and fixed several real instances in `alderford.txt`'s bailiff-confrontation scene this way. Expect real false positives from ambiguous English ("iron grip" as a political-control metaphor, "hilt" as a mature-content idiom, or a correctly-typed NPC weapon mention like Lyra's bow/knife) — read every hit in context, this is a candidate list, not a verdict. Report-only.
  * `tools/lint_anachronisms.js` (`node tools/lint_anachronisms.js`) — greps narration and dialogue for chemical and industrial engineering anachronisms forbidden by `QUEST_DESIGN_RULES.md` §10 (carbon, turbine, drive-cam, drive-shaft, cast-iron assembly, pneumatic, flywheel, anthracite steel, etc.). Report-only.
  * `tools/lint_blank_landing.js` (`node tools/lint_blank_landing.js [maxScan=50]`) — catches a bug class none of the above can: a `*page_break` whose destination prints nothing at all before its `*choice`, so the player sees a genuinely empty screen (just buttons) right after a hard page transition. Distinct from `lint_thin_prose.js`'s `SILENT` category, which only looks *inside* a `*choice` option's own body — a silent option is fine as long as it's on the same scrolling page as text that already printed above it, but `*page_break` forces a fresh page, so if the destination's own header is empty there's nothing left on screen at all. Found live: one of four "ask Maura a question" options in `alderford.txt` had a stray `*page_break` its three siblings didn't, landing on a header-less revisit hub (`taphouse_bar_loop`) — invisible to every other check because nothing crashes and no option is individually thin. A full sweep afterward found the same shape at 22 sites across 5 header-less hubs (`lyra_dialogue_hub`, `counting_house_menu`, `taphouse_bar_loop`, `taphouse_dice_menu`, `taphouse_smiths_menu`) — a systemic authoring habit (page-break after every dialogue/transaction beat), not a one-off. Two different fixes depending on the hub's shape, both applied: **remove the `*page_break`** for a one-off beat so its closing prose stays visible with the reappearing menu right below it (21 of the 22 sites — matches its siblings that never had the page break in the first place); **add a short, stable header to the hub itself** only where the pause is doing real work — `taphouse_dice_menu` is a repeatable mini-game loop where a fresh page per round is the *better* UX (an unbroken wall of accumulated roll text only gets worse the more someone plays), so its 3 sites kept the page break and got one generic table-grounding line instead. Method (a text-line heuristic, not a real parse — doesn't evaluate `*if`/`*else` branch logic, just whether *any* line in the reachable span looks like prose) also distinguishes a genuinely **BLANK** landing from a **BANNER-ONLY** one (a `[bracket]` stat/status dashboard with no narrative sentence, e.g. combat's per-round HP banner in `fight_round_hub`) — the latter is usually intentional design, not a bug, and is reported separately, low-priority, spot-check-don't-fix-by-default. Report-only; read every hit, this is a candidate list.
  * `tools/lint_vocab_overuse.js` (`node tools/lint_vocab_overuse.js [path] [top=40] [minCount=5] [clusterWindow=8]`) — the vocabulary-repetition half of `narrative_guidelines.md` §4 ("Vary Vocabulary Across Adjacent Text") that no other tool checks; `lint_prose_tics.js` greps fixed phrases, this measures word *frequency*. Three reports from one pass: **GLOBAL OVERUSE** (every word ranked by raw count across the whole corpus — the "AI has a favorite word and used it 300 times across 9 files" signal, invisible from inside any single scene); **TIGHT CLUSTERS** (the same word 2+ times within `clusterWindow` lines, same file — that rule's literal complaint, and the more directly actionable of the two); **RESTRICTED WORDS** (an empty-by-default, hand-maintained list at the top of the file — add `{ word, maxUses }` entries for anything you want kept deliberately rare, e.g. a word meant to mark one specific place or moment, and every use gets listed once total uses cross the limit). A proper-noun word (a character/faction/place name) is excluded from all three via a self-maintaining heuristic instead of a hardcoded name list: only counted if at least half its raw occurrences actually start lowercase, since a name essentially never does. Frequency analysis, not comprehension — read the top of each list, not the whole thing; a high rate for a genuinely common setting concept (iron, timber, stone in a low-fantasy port city) is often just genre, not a bug. Report-only.
  * `tools/render_hub.js` (`node tools/render_hub.js [weather] [time] [day] [scene] [label]`; `STATS='{"current_district":"harbor"}'` sets extra variables, `SAVVY=1` renders as a wisdom-14 character) — renders a hub or POI label's actual player-facing text and menu options for every weather x time x day combination (336 renders, or narrow with arguments), after running the real `calendar.txt` flag derivation. It reads what the player would see, so it catches what `quicktest` cannot: crowds in a blizzard, daylight at midnight, a Marketday line contradicting a fog line, an outdoor option offered in a storm. Run it whenever a hub or POI's weather, time or day prose changes, and scan the `street_life=empty` renders for people-words (see `QUEST_DESIGN_RULES.md` §12). `PICKS=4` renders every combination once per variant of a random pool (`*rand` becomes a fixed sequence), so a pool of variants is checked exhaustively instead of at random. It stubs `*choice`, `*page_break` and `*finish`, so it shows the intro and the menu, not what a choice does. The calendar recomputes `day_of_week` from `campaign_day` on every `advance_time`, so the tool sets `campaign_day` to match the weekday it is rendering.
  * `tools/scripted_play.js` (`node tools/scripted_play.js <script.json> [key=value ...] [--json] [--raw] [--no-menus]`; `--presets` lists the character presets, `--labels=<scene>` lists a scene's labels) — plays one path through the real engine from a script and prints what the player reads: the prose of each page, the choices offered, the option picked, page breaks and dice checks, then the coin and HP change and any watched variables. Where `render_hub.js` shows one page of one label in every weather, time and day, this follows choices, so it shows a route. The character comes from a dev-menu preset, the world from `weather`, `time`, `day` and `stats`, and the dice are forced per step with `rand` (`"low"`, `"mid"`, `"high"`), so the same script always prints the same text. `refresh: true` replays every page on a copy (what opening the Stats screen and returning does) and reports any variable that changes, which catches an unguarded reward or time advance, and `sabotage` proves that check can fail. Starting at a label skips the `*temp` lines above it, so give any it reads in `stats` (the tool says which one is missing). Example scripts are in `tools/play_scripts/`. It also loads as a module (`require("./scripted_play.js").play(script)`) for scenario tests. It shows prose but does not judge it. Advisory.
  * `tools/sim_weather.js` (`node tools/sim_weather.js [days=400]`) — advances the real `calendar.txt` one day at a time and prints weather counts, persistence, forecast accuracy, `ground_state` and temperature distributions, season-invalid days (expect 0), the exposure table per cloak, full worn kits and regional extremes (`temp_extreme` steps past freezing or hot), and a clock check that exposure speeds only the hunger and fatigue clocks (never the wash clock) and is cleared afterward. Run it after changing the weather tables, the 55 and 80 percentages, the temperature bands or `calc_exposure`.
  * `tools/lint_thin_places.js` (`node tools/lint_thin_places.js [only=<name>] [strict=true] [show=3]`) — the environment counterpart of `lint_thin_prose.js`, which only checks what a `*choice` option resolves to. It renders each hub and point of interest through `tools/render_hub.js` across every weather x time x day combination (and every variant of a random pool, via `PICKS`), counts the words the player actually sees, and reports the combinations under that entry's minimum: 100 words for a hub or district intro, 35 for a re-entry line printed on every return to a sub-hub. New hubs and re-entry lines should be added to its `ENTRIES` list. Advisory (exit 0) unless `strict=true`; a full run takes several minutes, so use `only=`.
  * `tools/lint_all.js` (`node tools/lint_all.js [path] [skip=a,b] [only=a,b]`) — runs every per-file linter below on one scene file or a folder, in one report. It is the single list an editor "Lint File" button should call, so adding a linter means adding one line to its `LINTERS` array. Whole-game tools (`lint_thin_places`, `sim_weather`, `check_*`, quicktest, randomtest) are deliberately not in it; `.vscode/tasks.json` has a task for each.
  * `tools/lint_dash_frequency.js` (`node tools/lint_dash_frequency.js [path] [rate=3] [line=3] [window=4] [span=10]`) — reports em dashes per 1000 words of prose per file (limit 3), lines holding 3 or more, and dense runs (4 or more in 10 prose lines). A dash is fine now and then; this finds the passages that lean on it. Advisory.
  * `tools/lint_weather_names.js` (`node tools/lint_weather_names.js [path]`) — enforces `QUEST_DESIGN_RULES.md` §12: flags a Storm-and-Blizzard pair (use `weather_severity >= 3`), a condition naming three or more weather types, a weather-name test mixed with another variable, `${weather}` printed inside a sentence, and a file that builds a sky chain without ever reading `ground_state` (the weather-memory block `narrative_guidelines.md` §10 requires at the foot of the sky layer). Plain sky chains are allowed. Advisory.
  * `tools/lint_slow_healing.js` (`node tools/lint_slow_healing.js [path] [all=true]`) — guards the Port Valen slow-healing rule (§12): flags `*set hp_current hp_max`, an absolute `*set hp_current N`, a heal with no `hp_max` cap, and prose claiming the body is fully restored. Checks only `port_valen*` files unless `all=true`, since the prologue may heal instantly. Advisory.
  * `tools/gen_equipment_data.js` (`node tools/gen_equipment_data.js`, or just `node compile.js` — it's auto-invoked from the Node CLI build) — regenerates `web/mygame/equipment-data.generated.js` from `equipment.txt`'s own `apply_<slot>_loadout` tables, so the Inventory panel's item data can't drift from the real source. Re-run any time an `apply_<slot>_loadout` table's shape changes in a way its narrow purpose-built parser might not expect (a new field name, a differently-indented block) and confirm the generated JSON still looks right.
  * `tools/gen_gear.js` (`node tools/gen_gear.js`, or `--check` to exit 1 on a stale block; also run by `compile.js` before `gen_equipment_data.js`) — regenerates every catalog-driven block and `web/mygame/trade-data.generated.js` (see §2). Run `--check` after editing `gear_catalog.json`.
  * **Testing a JS panel (`trade.js`, `inventory.js`) needs a real browser; `quicktest`/`randomtest` never see it.** `node compile.js <output.html>` writes a self-contained build to any path (leaving `play_game.html` untouched); load it in headless Chrome over the DevTools protocol (no dependencies: Node's global `WebSocket` is enough), give the game the state under test through `window.stats`, and jump into a scene with `clearScreen(function(){ safeCall(null, function(){ var sc = new Scene("scene", window.stats, nav, {debugMode:false}); sc.targetLabel = {label:"label", origin:"url", originLine:0}; sc.execute(); }); })`. Drive the panel by clicking its buttons and read `window.stats` back. A panel must also be tested after ChoiceScript redraws the page, because the old page can linger while it fades out (the trade panel's reopen logic compares node identity for that reason).
  * `tools/check_ac_formula_sync.js` (`node tools/check_ac_formula_sync.js num=400`; its goto-loop counter accumulates across iterations, so with `num` above about 6 the later playthroughs are counted as "errored before reaching equipped gear" although nothing is wrong: run several batches of `num=6` with different `seed=` values instead) — drift-check for `equipment-panel.js`'s hand-ported `EquipmentEngine.recalcArmorClass` against the real `recalculate_armor_class`: runs real headless playthroughs (`randomtest.js`'s harness), feeds each completed one's final stats into the JS mirror, diffs the AC. Run after any edit to `recalculate_armor_class` (§2) — a mismatch means the mirror needs the same edit, not the other way around.
  * **A one-off directed trace** for a specific mechanic the other three are unlikely to reach on their own (a particular class+spell combo, a specific fight outcome). Bootstrap identically to `randomtest.js`, but override `Scene.prototype.choice` to pick options by substring match against a scripted `PICKS="Cadre Dread Warlock|Jump to Chapter 2|...|[Spell: Armor of Agathys]"` list (`|`-split, falls back to the first available option once exhausted). Can force a dev-menu preset straight into any fight/branch; a `stats[k] = v` injection pass (once `stats.intake_completed`) can set a spell/cantrip no preset combines, without hand-writing a new one. Delete the scratch script when done — it's a throwaway, not something to commit.
* **Harness setup requirements** for any of the above written fresh: override `saveCookie` to fire its callback immediately (not deferred through the same `timeout` var `clearScreen` uses — `printLoop()` calls it on every pause purely to persist stats for a refresh that'll never happen in a harness; a deferred no-op silently clobbers the real `*choice` continuation and stops the walk after one choice while still reporting a pass); and set `global.safeTimeout = function(fn) { safeCall(null, fn); };` before loading `mygame.js` (without it, a fresh `Scene`'s first `execute()` defers through a real async `setTimeout` a synchronous harness never gets to run, reading as "no content" instead of the parse error it actually is).
* **`refresh_fuzz_test.js`'s replay simulation has a blind spot at a pause point reached through `*gosub_scene`** (any fight run through `combat.txt`): reconstructing a bare `Scene` at the recorded line/scene without rebuilding `stats.choice_subscene_stack` means the simulated `*return` has nothing to return to, so it runs off the end to `*finish` instead of re-pausing — reported as `[shadow-no-pause]`, not a confirmed bug. `probeCurrentChoice` checks `choice_page_start_scene !== scene.name` up front and reports this case before ever attempting a reconstruction, because blindly building the shadow `Scene` from the *current* scene (not the one the page actually began in) can do worse than just fail to re-pause — a real instance had a page that began in `alderford.txt` reach a pause inside `combat.txt`; the tool built a shadow `combat` Scene at the recorded line/indent (both only meaningful in `alderford.txt`), and `combat.txt`'s own unrelated line at that number happened to sit at a different indent, throwing "increasing indent not allowed" — a `[shadow-crash]` that looked like a real engine bug but was purely a coincidental cross-file line-number collision. To actually verify refresh-safety at one of these pause points, simulate a **real** cold refresh instead: capture `choice_page_start_scene`/`_line`/`_indent` at the pause (exactly what a real reload reads), construct a fresh `Scene(choice_page_start_scene, stats, nav, false)` at those coordinates with fresh `temps`, execute, and confirm it re-pauses identically — no subscene-stack reconstruction needed, since that already lives on `stats` and survives the new Scene object for free.

## 5. Reusable Small-Combat Engine (`startup.txt` primitives + `resolve_*`)
* **For a short, contained skirmish, reuse the combat primitives in `startup.txt` rather than hand-rolling a new one per fight.** Built and proven on the Alderford culvert encounter.
  * **The player's own attack roll needs zero new code** — just `roll_d20_check` with `check_dc` = the enemy's AC (`combat_enemy_ac`). Advantage, guidance, nat 20/1, expertise, meal buffs all work for free.
  * **`resolve_player_hit`/`resolve_player_weapon_hit`** — call after `check_success` with `combat_player_dmg_dice_sides`/`_bonus` set. Applies to `combat_enemy_hp` (floored at 0), self-locked, reports `combat_player_dmg_dealt`. The weapon variant additionally resolves Sneak Attack.
  * **`resolve_enemy_attack`** — rolls the enemy's attack against `armor_class`, applies damage to `hp_current` on a hit (halved raging, floored at 1 — let the caller narrate a rescue instead of a kill). Self-locked. Reads `combat_enemy_atk_bonus`/`_dmg_dice_sides`/`_dmg_bonus` (set once at fight start) and `combat_enemy_disadvantage`/`_advantage` (per-round caller flags; `_advantage` self-clears after one use, `_disadvantage` the caller resets each round). Both true cancels per normal rules.
  * **A per-round mutation (round counter, action-menu choice) still needs the standard replay lock** — not exempt for being "in a loop." Reset the counter to a fixed literal at the fight's true start; put the (locked) increment only where a genuinely new page cycle begins (end of enemy turn, before `*page_break`) — never both on the fight-start page.
  * **A reaction spell (Shield, etc.) doesn't need a new pause point.** An "arm it" option sets a persistent flag and `*goto`s back to the same round hub at no action cost (mirroring the Guidance-cantrip trick); the relevant `resolve_*` primitive checks the flag and auto-fires/disarms itself the moment it matters, inside its own existing pass. Less "realistic" than a true interrupt-and-ask, but needs no new engine surface — only build a real interrupt if that tradeoff specifically matters for an ability.
  * **A flag set before a `*gosub_scene` can get cleared by the very call it's feeding.** `roll_d20_check` resets `advantage`/`disadvantage` before returning, so "was advantage true going into this roll" (Sneak Attack's trigger) needs capturing before the call — or better, read it as the primitive's own output: `roll_had_advantage`, set inside `roll_d20_check`'s own locked fresh-roll branch, is naturally replay-safe the same way `check_success` is, with no caller-managed flag needed at all.
  * **A spell with a genuinely unusual damage shape** (Magic Missile: 3d4+3, always-hits, no attack roll) is often clearer as its own small inline block (a few `*rand` calls into `combat_enemy_hp`, own lock) than forced through `resolve_player_hit`, which only models "one roll, gated on `check_success`." Don't generalize the primitive for a one-off.
  * **Audit a "built for later" dormant subroutine for a replay lock before giving it its first real caller** — `second_wind`/`activate_rage` sat unlocked for a session because nothing had called them yet; the bug had simply never been exercised.
  * **A resource-spending spell that reports one computed number (temp HP, HP healed) doesn't need its own output variable** — `combat_cast_result` is shared across False Life and Healing Word. Likewise, buff casts that can never be chosen in the same round as each other can share one lock (`combat_cast_locked` covers Hex, Agathys, False Life, Healing Word) instead of a dedicated pair each.
  * **An ongoing damage-rider (Hex's +1d6 "on every hit") belongs inside every damage-dealing primitive itself**, not bolted onto each choice branch — a future attack option then gets correct interaction for free.
  * **Temporary hit points need their own pool (`temp_hp`), separate from `hp_current`, absorbed first on a hit before any overflow.** Keeps ordinary HP clamping ignorant of temp HP, and lets a shattering effect (Armor of Agathys) detect "temp_hp hit exactly 0" cleanly.
  * **Bonus-action spells loop back to the round hub free; full-action spells consume the round.** Don't retrofit this onto abilities that already shipped consuming the round despite being bonus actions in 5e (Second Wind, Rage) — that's a deliberate, tested tradeoff, not an oversight.
  * **Attack cantrips need their own bespoke `*choice` option each, in the shared engine file — never a single generic "cast a cantrip" option reading back a detected name/stat/dice-sides.** A generic cascade was tried first (`detect_attack_cantrip` populating `has_attack_cantrip`/`attack_cantrip_name`/`_stat`/`_dice_sides`, one "Channel ${attack_cantrip_name}" option reading them back) and broke two things at once: every cantrip printed the same "the working..." text regardless of which one it was (a direct `narrative_guidelines.md` §2 violation — see `combat.txt`'s `fight_round_hub` for the fix, six separate options, one per cantrip), and because the detection had to be an `*else` chain (only one winner), a build with two attack cantrips could only ever reach whichever was checked first — the second was silently unreachable in combat. Six bespoke options costs the same one-time write as the shared buff-spell options already do (Hex, Agathys, etc.) and both bugs disappear; a fight never needs its own copy, so this doesn't reopen the "5 fights, 10 spells, do we duplicate everything" scalability concern the generic cascade was built to dodge in the first place.
  * **Where a cantrip/spell's RAW secondary effect maps cleanly onto an existing engine flag, wire it in — check the dossier's `print_ability_card` (`choicescript_stats.txt`) for what's already being promised to the player first.** Ray of Frost's "target's speed reduced by 10 ft" and Vicious Mockery's "throw off their next strike" both became `*set combat_enemy_disadvantage true` on a hit — the same flag `resolve_enemy_attack` already reads for a Brace action, so no new mechanic was needed, just reusing the one that exists. Don't force a translation that doesn't fit (Chill Touch's "can't regain HP" — this engine never grants enemies healing at all, so there's nothing to prevent) — a vivid, distinct description on its own already satisfies `narrative_guidelines.md` §2; a mechanical rider is a bonus where one actually maps, not an obligation to invent one everywhere.
  * **Every hit/miss line needs real variety (3 randomized phrasings, not one fixed sentence), and a killing blow needs its own distinct text — a fight that reuses one line every round, with no acknowledgment when a hit is the one that actually ends it, reads as flat and mechanical no matter how good the individual sentence is.** Built two layers: (1) `combat_flavor_weapon_hit/miss_1/2/3` (melee), `_ranged_1/2/3`, and `combat_flavor_enemy_hit/miss_1/2/3` (plus optional per-slot `enemy2/3` override triplets) are picked by a fresh `*rand 1 3` every time, via `pick_weapon_flavor` (player) and `fight_narrate_enemy_turn`'s own selection logic (enemy) — each fight writes all three variants per line, and all three must vary the actual *physical action* (a thrust vs. timing an overextension vs. a parry-and-counter), not just reshuffle adjectives around the same motion, or the repetition just moves up a level. (2) A death blow — `combat_enemy_hp <= 0` checked immediately after the damage primitive returns, at *every* damage source (the weapon attack including Sneak Attack, all six cantrips, Magic Missile, Dissonant Whispers, and Armor of Agathys' retaliation) — swaps in `pick_weapon_death_flavor`/`pick_spell_death_flavor` instead of the ordinary hit line, plus a `💀 ... Defeated` banner in place of the usual `🩸 Hit` one. Unlike the per-round hit/miss triplets, the death-blow lines are deliberately generic and enemy-agnostic (parametrized with `${combat_enemy_epithet}`/`${weapon}` only, no per-fight override) — mirroring how buff-spell flavor already stays enemy-agnostic on purpose, since a full per-fight *and* per-attack-type finisher set (3 fights × up to 9 damage sources × 3 variants) would be a much larger writing cost than one good shared set for comparatively little payoff. `*create` rejects a `${}`-interpolated default value ("value must be a simple string") — the death-blow text lives inline inside the two `pick_*_death_flavor` subroutines in `combat.txt`, not as named `startup.txt` constants, for exactly that reason.
  * **A rider that depends on a per-enemy trait (not just a hit/miss), like Shocking Grasp's advantage against a metal-armored target, needs its own tag on the enemy — cheap to add given the existing per-slot fields.** `combat_enemy_metal_armor` (`startup.txt`) follows the exact same pattern as `combat_enemy_epithet`: a `combat_enemy1_metal_armor`/`_2`/`_3` per slot (defaulting `false`), snapshotted by `fight_setup` and mirrored by `fight_sync_target_in` alongside every other per-slot field, so `combat.txt`'s Shocking Grasp option just reads the plain `combat_enemy_metal_armor` name like any other primitive would. No existing fight sets it true yet (a Silt-Lurker and casual cudgel-wielding dock-guards are both honest "no" answers) — it's there for the next fight that's actually against armored soldiers/knights/constructs, verified by injecting it true in a directed trace rather than waiting for real content to exist.

## 6. Combat as a Standalone Scene File (`combat.txt`) — Fight Library Pattern
* **The round-by-round combat loop lives once in `combat.txt`**, entered via `*gosub_scene combat fight_<name>`. It returns with `combat_outcome` (`"victory"`/`"rescued"`/`"fled"`) and prints no start/end-of-fight prose itself — the caller branches on the outcome and owns 100% of the narrative reaction, so the kill/retreat beat and the quest-giver's response read as one continuous scene.
* **A new fight costs one short `fight_<name>` entry label** — enemy `combat_enemy_*` stats and a handful of `combat_flavor_*` strings, then `*gosub fight_setup` / `*goto fight_round_hub`. Everything else (every spell option, enemy-turn resolution, retreat/rescue) is already shared.
* **Most ability-casting flavor is enemy-agnostic and belongs directly in the shared `fight_round_hub`, not parametrized per fight** — Hex, Agathys, False Life, Healing Word, Magic Missile, Shield, Second Wind, and Rage all describe the player's own casting motion, not the creature (strip any stray environmental wording so they read fine anywhere). What varies by foe (the player's weapon hits, misses and finishing blows, the attack spells' hits, misses and finishers, the enemy's own attack, and how every line refers to the target through `combat_enemy_epithet`, "the wolf" or "Captain Vane") comes from the enemy type library and the damage-type-keyed labels described below (`flavor_player_*`, `flavor_creature_*`, `flavor_kill_*`, `flavor_yield_*`, `flavor_spell_*`), so a fight normally sets no `combat_flavor_*` at all. Only a foe no library type fits is written out by hand.
* **Reusing the same enemy across two quests just means two scenes calling the same `fight_<name>` label** — `*gosub_scene`'s return address is dynamic (pushed onto `stats.choice_subscene_stack` at call time, popped by `*return`), so it always hands control back to whichever quest actually called it. For an encounter that should *feel* distinct despite reusing a type, set a few per-slot `combat_flavor_enemy*_hit/miss_N` lines as local color (see the type library bullet) instead of copying the label.
* **Up to `combat_enemy_slot_cap` simultaneous enemies are supported (6, widened from 3 on 2026-09-27; `combat_enemy_count`), and a single-enemy fight needs zero changes to work with it.** Slot 1 IS the original `combat_enemy_*` names a single-enemy fight already sets; `fight_setup` snapshots whatever's there into `combat_enemy1_*` (its real permanent home) automatically. A multi-enemy fight additionally sets `combat_enemy_count` plus `combat_enemy2_*` through `combat_enemy6_*` for the extra slots (and optionally `combat_flavor_enemy2_hit/miss` through `_enemy6_hit/miss` — falls back to the shared `combat_flavor_enemy_hit/miss` when a slot doesn't define its own, so identical mooks only need flavor written once) before `*gosub fight_setup`. Every existing damage/attack primitive in `startup.txt` stays single-target and untouched — `combat.txt`'s `fight_sync_target_in`/`fight_sync_target_out`/`fight_pick_target` mirror whichever slot is "active" into the canonical `combat_enemy_*` names right before/after a primitive touches them, so the primitives never had to learn multiple enemies exist. The player always auto-targets the first living slot (ascending order, never picks a dead one back up); each living slot gets its own attack roll every round in `fight_enemy_turn` (a defeated slot's turn is skipped entirely — no roll, no prose); the round-hub banner lists every slot's HP with a `(Down)` tag once defeated. `fight_cleanup` resets `combat_enemy_count`/`combat_active_target` back to 1 so multi-enemy state never leaks into the next fight. First built and proven on `fight_rennick_guards` (`alderford.txt`'s curing-shed standoff) — **tune per-enemy damage down from what a solo fight would use**, since N attackers roughly multiplies a round's expected incoming damage by N; the first pass at this fight (guard stats sized like a solo encounter) nearly dropped a 10-HP caster to the rescue floor in round one against two guards, and needed a real reduction in `atk_bonus`/`dmg_bonus` to land as a fair multi-round fight instead of a coin-flip near-knockout.
* **The 3→6 slot widening (2026-09-27) replaced every per-slot hand-copied block with ONE generic block, using `{}` name indirection and bounded `*goto` loops — read this before touching any per-slot combat code again.** ChoiceScript has no arrays, so the storage itself is still a fixed pool of numbered `*create`d variables (`combat_enemy1_*`..`combat_enemy6_*`); what changed is that every OPERATION over that pool (`fight_sync_target_in/out`, `fight_pick_target`, `fight_check_all_dead`, `fight_enemy_turn`, `fight_cleanup`, `apply_slot_stat_override`, `apply_enemy_type`'s rename-override tail, each `apply_type_X`'s slot-2-and-beyond branch, `fight_library`'s slot loop, `fight_narrate_enemy_turn`'s override lookup, `resolve_enemy_attack`'s per-slot lock) is now ONE label written once instead of duplicated per slot, with the slot number as data. **The technique:** build the variable's name as a string (`*temp p (("combat_enemy" & slot) & "_")`, ChoiceScript needs the nested parens — no chained `&` without them) and read or write through `{}` (`*set combat_enemy_hp {(p & "hp")}`; `{}` also works directly as a `*set` WRITE target, and an expression can go straight inside it, not just a bare pre-built `*temp`). A bounded loop is `*temp i 1` / `*label ..._loop` / `*if (i <= N) ... *set i + 1 *goto ..._loop`, entirely safe inside a `*gosub`'d subroutine (a real proof-tested pattern, not a guess). **The one sharp edge, found the hard way:** quicktest's line-coverage walk visits an `*if` body's lines even when the guard is false for the CURRENT data (confirmed for a plain `*if`, not only a compound `and`/`or`, and nesting does NOT protect against it) — so an indirected read/write inside ANY `*if` body must resolve to a variable that exists for every slot value the walk might leave in place when it enters, never a variable that exists only for "the slots this branch is logically restricted to." Slot 1 in particular has several fields under the ORIGINAL bare (unnumbered) name with no numbered `combat_enemy1_*` equivalent (`name_override`, `epithet_override`, `hp/ac/atk_override`, and every `combat_flavor_enemy1_*` hit/miss/move2 variant) — the fix each time was to `*create` an inert, always-`""`/`999` numbered placeholder for slot 1 too (never read by real logic, which still uses the bare name) rather than trying to guard the read, and then drop any `*if (slot >= 2)`-style guard around it, since the guard doesn't help. **Verified before/after identical** (a scratch copy with every real fight run through fixed dice, byte-for-byte matched against the pre-refactor output, 53 cases, 0 diffs) plus new coverage for 4–6 simultaneous enemies and the latent hand-authored/no-type and per-slot-override-text paths (0 real content uses either, but the code path is real and must not silently break). A fight reached via `*gosub`/`*goto` directly inside `combat.txt` (rather than the real `*gosub_scene combat fight_<name>` every quest scene actually uses) can hit an unrelated ChoiceScript resume/replay bookkeeping quirk under `whileAvail` when it concludes — a test-harness trap, not a bug in the game; drive a test fight through a real caller scene.
* **The Ally Pool (`combat_ally1_*`–`combat_ally4_*`, `startup.txt`, added 2026-09-27) Is Storage Only — Step 2 of the Turn-Order/Initiative Rebuild, Nothing Acts On It Yet.** `combat_ally_slot_cap` (4) mirrors `combat_enemy_slot_cap`'s ceiling pattern, and each slot carries the enemy pool's basic fields only (`name`/`epithet`/`hp`/`max_hp`/`ac`/`atk_bonus`/`dmg_dice_sides`/`dmg_bonus`/`dmg_type`/`weapon_type`), not its condition/stun/movepool/resistance machinery — no ally AI exists to use any of that yet, so it wasn't built speculatively. `combat_ally_count` defaults 0, and no fight sets it; `fight_cleanup`'s per-slot reset loop deliberately does not touch `combat_ally*` (nothing populates it per-fight, so nothing needs resetting between fights yet — revisit once a fight actually fills a slot). `combat.txt`'s `fight_narrate_ally_attack` is placeholder narration for one AI-controlled ally's attack on one enemy slot (melee/ranged wording split, generic and un-voiced on purpose, since no actual ally exists in the game yet) — nothing calls it (no ally AI, no turn queue), so it's exercised only by a synthetic test reaching it via a real `*gosub_scene combat fight_narrate_ally_attack <ally_slot> <target_slot> <hit>` call, same convention as every other combat test in this file. **A real gotcha hit while building this, worth remembering everywhere in this engine:** a `${}` token inside a string resolves *immediately*, at the `*set`/`*create` that assigns it, never later when that stored string is finally printed — so a flavor pool "baked" once with `${combat_ally_atk_epithet}` inside it at game-start (when that variable was still empty) freezes in the empty value forever; every later read of that pool variable prints the epithet as blank, no matter what the variable holds by then. (This is the same fact 5(above) already documents for `*create` rejecting a `${}` default outright — the same rule applies to `*set`, which does accept one syntactically but still resolves it immediately rather than deferring it, which is easy to miss since it doesn't error.) Caught by a synthetic rename test that checked the actual printed text for a custom epithet, not just that the label ran without error — the fix was to build the five variants' text inline, fresh, inside `fight_narrate_ally_attack` itself (an `*if (fnaa_v = N) *set fnaa_line "...${...}..."` chain, exactly `flavor_type_swordsman`'s own pattern), after the epithets are already synced, instead of pre-storing them as named `startup.txt` constants. **Generalized the same day to narrate EITHER direction** (an ally attacking an enemy, or an enemy attacking an ally), not just ally-as-attacker -- the params changed from (ally_slot, target_slot, hit) to (attacker_kind, attacker_slot, defender_kind, defender_slot, hit), where kind is the literal string "ally" or "enemy" on either side (both slot pools follow the identical combat_<kind><slot>_<field> naming shape, so one prefix-builder handles both). This wasn't a mirrored second label -- the existing text already named both sides purely by epithet, third person throughout, so it works unchanged in either direction; only which side is "attacker" and which is "defender" changes. (Contrast with the existing enemy-attacks-PLAYER prose, flavor_type_swordsman etc., which is hardcoded second-person -- "your shoulder" -- and genuinely can't be reused for an ally target without rewriting every type's lines; that's out of scope here.) The scratch variables were renamed from combat_ally_atk_*/combat_ally_atk_target_* to direction-neutral combat_attacker_*/combat_defender_*, since either can now hold an ally's or an enemy's data. This surfaced one real gap: enemies never had a stored melee/ranged flag (their ranged-ness lived only in flavor prose) -- added combat_enemy1_weapon_type-_6_ (default "melee", mirroring combat_allyN_weapon_type), set to "ranged" only where a type needs it (archer, slinger -- the other ten rely on the default plus fight_cleanup's reset-to-default backstop, the same way most types already skip re-setting dmg_type and rely on its own default/reset). Verified in both directions: a 23-check suite (default sync, melee/ranged wording each way, per-slot rename each way, no cross-contamination) plus a direct check that every real type resolves the correct weapon_type (archer/slinger -> "ranged", everything else -> "melee"). A test-authoring gotcha, not a game bug: passing a bare word like ally/enemy as a *gosub_scene argument is parsed as a VARIABLE LOOKUP ("Non-existent variable 'ally'"), not a string literal -- needs "ally"/"enemy" quoted, same as any other string argument.
* **Enemy Ability Scores (`combat_enemy1_strength`–`_charisma`, `startup.txt`, added 2026-09-27) Are Groundwork for Initiative Rolls and Later Saving Throws/Stat-Modifying Spells — Step 3 of the Turn-Order Rebuild.** Six scores per slot (STR/DEX/CON/INT/WIS/CHA), default 10 (average, +0). Draft per-type ranges (all 12 types) live inline in each `apply_type_X`, proposed and confirmed with the designer before writing any code, not invented unilaterally.

* **Target Selection Is a JS Panel Reusing `combat_player_chosen_target`, Not a New ChoiceScript Menu -- and It Lives IN the Existing `#statSidebar`, Not a Separate Panel (2026-09-27).** The first design (a standalone floating bar) was wrong twice over, both caught by the designer looking at the actual rendered page, not by anything a test could have caught: a bottom-of-viewport bar collided with the title and button row, and a left-corner mirror of the sidebar was still "the same ugly buttons just moved to the side."   * **A real, more serious bug than the visual ones, and a lesson in test rigor, both worth keeping.** The first fix (re-sync once at the top of `fight_round_hub`, so the very next full page build picks up a new click) only helps if the click happens BETWEEN hub visits. It does nothing for the far more common case: the player is already looking at an already-built menu, clicks a new target in the sidebar, then picks an option that was already sitting on screen -- that option's own code (e.g. `*set check_dc combat_enemy_ac`) reads the bare `combat_enemy_*` fields exactly as they were synced when THAT page was built, and a click after the fact does not retroactively change them. The actual fix needed `*gosub fight_pick_target` as the first line of every option that targets the enemy -- the weapon attack, Brace, and every targeted cantrip/spell (Fire Bolt, Ray of Frost, Shocking Grasp, Eldritch Blast, Chill Touch, Vicious Mockery, Magic Missile, Hex, Dissonant Whispers -- 11 sites total; Armor of Agathys/False Life/Healing Word/Shield don't target the enemy at all and don't need it), so the sync happens at the moment the option is actually chosen, not merely when the page was built. **The bug was caught by a real-browser test that looked wrong at first glance and turned out to be right** -- clicking a target mid-turn (after a non-damaging Brace, before a second Attack) landed the damage on the OLD target. **A first draft of that same test had already "passed" against the unfixed code**, because its assertion was `/Ithel/.test(pageText)` -- too loose: Ithel's own later turn in the same round also prints its name in a miss/hit line, so the text search found a true match for the wrong reason regardless of who the player's attack actually hit. Rewritten to check HP deltas instead (durable and unambiguous: enemies never damage each other, so a candidate's HP can only move from the player's own attack) -- confirmed across four repeated runs against real, unforced dice, not scripted_play's forced rolls, specifically because this class of bug (state read once at the wrong moment) can only be caught by driving the real click through the real compiled page, never by ChoiceScript-only testing in isolation.

* **`announce_turn_order` (2026-09-27, step 6) Is the Only Player-Visible Confirmation the Turn Queue Exists At All.** The designer asked, directly: "how do I know it's working, nothing shows me the initiative order." Fair -- the roll and the dispatch (steps 4-5) were both real, but neither one surfaced anything to the player, so there was no way to tell them apart from the old system without deliberately engineering a DEX mismatch and watching for an enemy to act out of turn. * **`score_to_mod` Was an Unintentional House Rule, Not a Deliberate Balance Choice — Uncapped to the Real 2014-Rules Formula (2026-09-27), for the Player Too, Not Just Enemies.** Discovered while drafting the enemy ability-score ranges above: the ladder flatlined at -1 for any score ≤9 and capped at +3 for anything ≥16, when it should be `floor((score-10)/2)` uncapped in both directions. This wasn't enemy-only — `score_to_mod` is also what `update_dnd_stats` and `recalculate_con_mod` used (via their own **hand-copied duplicate** of the same ladder, not by calling `score_to_mod` itself) for the player's own `str_mod`/`dex_mod`/`con_mod`/`int_mod`/`wis_mod`/`cha_mod`, and the player can already exceed 16 today (a 16-point base array plus a +2 racial bonus, Company Intake, makes an 18 a normal build) — so this was already silently clipping the player's own attack/save/DC bonus at +3 instead of the +4 real math gives an 18, with no new content needed to trigger it. Fixed both ways at once, confirmed with the designer first since it's a retroactive buff to any existing high-stat build, not just a future-facing enemy fix: `score_to_mod` now covers the full legal score range 1-30 as an `*if` threshold ladder (not division/modulo — this engine's negative-division rounding was never verified, and a plain `*if` chain says the same thing with zero doubt), and also outputs `sm_mod_str` (`"+4"`/`"-2"`/... same display format the old hand-copied strings used) so callers don't need their own stringification. `update_dnd_stats`'s five duplicated ladders and `recalculate_con_mod`'s own copy were rewritten to `*gosub score_to_mod` instead of each maintaining independent (and, before this fix, already-inconsistent-with-the-standalone-subroutine) copies of the same math — one place this formula can go wrong from now on, not six. **A real bug caught mid-fix, not by a player:** the first pass rewrote `update_dnd_stats`'s five blocks but missed `recalculate_con_mod`'s own separate label entirely, so CON kept using the old capped ladder while the other five scores used the new one — caught by a synthetic test that set CON 20 and expected `+5`, got the old `+3` back, because the test actually checked the *value*, not just that the call succeeded. Verified against the real engine for every score 1-30 against a JS-computed reference, plus the specific newly-reachable values (18→+4, 20→+5, 30→+10, 7→-2, 3→-4, 1→-5) and the player-facing path end to end (`update_dnd_stats` with overridden scores, not just `score_to_mod` in isolation). **A harness reminder that bit this test too:** `*gosub` only reaches a label in the *same* scene file — calling `score_to_mod`/`update_dnd_stats` (both in `startup.txt`) from a separate test caller scene needs `*gosub_scene startup <label>`, not a bare `*gosub`, which fails "bad label" instead of erroring usefully about the cross-file call.
* **A `*gosub_scene`-only library scene like `combat.txt` must NOT be added to `*scene_list`** — but it does still have to be told to `compile.js` by name, in a *second*, separate place. List order also builds the implicit "`*finish` continues into the next declared scene" chain (`nav.nextSceneName` is a flat `scene_list[i] → [i+1]` map). Inserting `combat` after `startup` once silently hijacked character creation's `ready_camp` `*finish` into `combat.txt` instead of `camp_night.txt`, crashing on an unrelated bare `*return` deep in the file. `*gosub_scene` doesn't require list membership to target a scene at runtime — but fixing that bug by removing `combat` from `*scene_list` broke something else: `compile.js` has **no directory-scan fallback** (its own comment: "as we can't read the dir") and only bundles files it's told about — `*scene_list` entries, plus a short hardcoded list (`verifyFileName("calendar.txt")` and friends) for exactly this "subroutine scene, not in the list" case. `combat.txt` silently stopped being bundled into `play_game.html` the moment it left `*scene_list`, with zero error at compile time — `quicktest`/`randomtest`/`refresh_fuzz_test` all load scenes a different way (straight off disk) and never touched this path, so nothing caught it until a real compiled build hit `*gosub_scene combat ...` and failed with "scene doesn't exist." **Any scene excluded from `*scene_list` for the `*finish`-chain reason above must be added to `compile.js`'s hardcoded `verifyFileName(...)` list instead** (mirror the `calendar.txt` line right next to it) — and re-check the actual compiled `play_game.html` for the scene's data (`grep '"combat":'` or similar), not just `quicktest`/`randomtest`, since those two tools can't catch this class of bug at all. **`equipment.txt` is the third such library scene** (called only via `*gosub_scene equipment <label>`, from `update_dnd_stats` at character creation, every dev-menu preset, and quest reward sites), and it hit exactly this bug: it was missing from `compile.js`, so a compiled build would have failed with "scene doesn't exist" at character creation. Any new subroutine scene needs its `verifyFileName(...)` line the day it is created.
* **`death.txt` Is a Second `*goto_scene`-Only Library Scene, Same Treatment as `combat.txt`.** Not in `*scene_list`, told to `compile.js` via its own `verifyFileName("death.txt")` line, for the identical reasons above. It holds one shared `*label death_screen`: any caller sets `death_cause` ("starvation" | "exhaustion" | "combat"), and for a location other than Port Valen, `death_location_name` first (defaults "Port Valen") — then `*goto_scene death death_screen`. Unlike `combat.txt`, callers never `*gosub_scene` into it — there's nothing to return to, the game is ending — so it's reached with a plain `*goto_scene`, which is exactly why it *can* safely end the game or vary its prose internally without tripping the `*gosub_scene`-stack restriction two entries above: it's never entered as a subroutine in the first place.
* **A Weapon's Damage Die Comes From `weapon_type`, and Two-Handedness Comes From `weapon_hands`, Never From `weapon_type`.** The player's attack in `fight_round_hub` rolls d4 for finesse, d6 for ranged, d12 for a melee weapon with `weapon_hands = "two_handed"`, and d8 otherwise; ranged and finesse are tested first, so a two-handed bow stays a d6. Dueling's +2 and Great Weapon Fighting read `weapon_hands` too. A new two-handed melee weapon therefore needs only `hands: "two_handed"` in its loadout entry (`weapon_type` stays `melee`); the old `weapon_type = "two_handed"` branch never fired for that reason.
* **`combat_engaged` Is True From `fight_setup` Until `fight_cleanup`.** The dossier's satchel and the inventory panel's Use button refuse while it is true (a fight has its own item option, which costs the turn). Any new exit from a fight must go through `fight_cleanup`, or the flag sticks.
* **A Night-Danger Encounter Is an Arrival Hook With Non-Combat Exits (the Dredge-End Ambush Pattern).** `port_valen_dredge_end_arrive` rolls `dredge_ambush_chance` once per night (`dredge_ambush_night`) when the hour is Night or Pre-Dawn and the district is not empty, and offers pay the toll, fight, slip away (DEX check) or turn back, so a weak build is never forced into a lethal fight. Fights report `combat_outcome` like any other (`rescued` means robbed to 1 HP, not dead). Loot is 5-25 copper (trimmed from 15-45 so a win pays about half a Quayside laborer's day, 20-40 copper, instead of out-earning honest work) plus 1-3 Scrap Steel plus a chance at a catalog weapon through `grant_gear`. * **Combat Lethality Is Opt-In Per Fight, Default Off.** `combat_player_can_die` (a `combat_enemy_*`-style per-fight stat, default `false`) gates whether `resolve_enemy_attack` floors the player's `hp_current` at 1 (existing behavior, unchanged for every fight that doesn't set it) or lets it reach 0. A fight that sets it `true` in its own `fight_<name>` entry label can end in `fight_enemy_turn` reporting `combat_outcome "player_died"` instead of the usual `"victory"`/`"rescued"`/`"fled"` — `fight_player_died` can't `*goto_scene death` itself (same subscene-stack restriction), so it just reports the outcome and `*return`s like any other exit. **Every** `*gosub_scene combat fight_<name>` call site must check `*if (combat_outcome = "player_died") *set death_cause "combat" *goto_scene death death_screen` alongside its existing victory/rescued checks — including fights that are non-lethal today, since an un-guarded call site silently falls through to whatever the caller's last `*if`/fallback branch is (usually "flee") instead of ending the game, the moment someone later flips that one fight's flag. Set `death_enemy_epithet` before the jump if the fight has a `combat_enemy_epithet` worth reusing in the death screen's closing line.
* **Condition-on-Hit (Frightened/Poisoned/Stunned) Is Opt-In Per Fight, Single-Round Only, By Design — Never a Multi-Turn Lock.** A `fight_<name>` label sets `combat_enemy_inflicts_condition`/`_condition_name`/`_condition_icon` (Frightened/Poisoned) to make that enemy's hit set the player's ordinary global `disadvantage` flag for their next roll — no new mechanic, it just reuses what `roll_d20_check` already reads. `combat_enemy_inflicts_stun`/`_stun_name`/`_stun_icon` works the same way but costs the player their entire next turn (`player_stunned`, consumed the instant `fight_round_hub` sees it) instead of just a disadvantage roll. Deliberately single-round: a solo-fight stun-lock isn't fun and this engine has no way to cleanse a condition early to compensate for one — don't chain stun sources or extend either condition past one round. Every enemy is unaffected by default (all three default `false`); an enemy type or fight that doesn't opt in behaves exactly as it did before this system existed.
* **Condition/Stun/Movepool Resets Belong in `fight_cleanup`, Never `fight_setup` — Every `fight_<name>` Label Sets Its Own Fields, Then Calls `fight_setup`.** Resetting these fields inside `fight_setup` would wipe out the very values the calling label just set one line earlier. They reset instead at the *end* of the previous fight (`fight_cleanup`), so an enemy that doesn't opt in never inherits a leftover flag/name/icon/moveset from whichever earlier encounter last used it. This bit a real early draft of the system — caught and fixed before shipping, not by a player.
* **Enemy Movepool (`combat_enemy_move2_chance` 0–100) Gives One Enemy a Second, Different Attack Without a New Engine Concept.** `fight_pick_enemy_move` (combat.txt) rolls it once per living enemy's turn; 0 (the default) means "never," so every existing single-move enemy is unaffected. When move 2 fires it overrides the scratch atk/damage/condition fields for that one attack only — `fight_sync_target_in` resyncs the base values from each slot's permanent `combat_enemy1/2/3_*` storage at the top of the next round regardless, so nothing needs to explicitly restore them afterward. **A movepool enemy can't also carry an always-on `combat_enemy_inflicts_condition` from `fight_setup`** — `fight_pick_enemy_move` owns that scratch flag once `move2_chance > 0` is active, so give the condition to move 2 instead (`combat_enemy_move2_inflicts_condition`), not the base move.
* **The Enemy Type Library (`combat.txt`'s `apply_enemy_type`) Lets a Mixed Fight Drop a Reusable Stat Block/Movepool/Flavor Set Into Any Slot (1–3), Including the Same Type Twice or Different Types Together, With No Per-Fight Duplication.** **A scene plugs a fight in without touching `combat.txt`:** it sets `combat_lib_1` (and `combat_lib_2`, `combat_lib_3`) to library type ids, `combat_is_nonlethal` if the brawl should end in surrender, and optionally name overrides, then `*gosub_scene combat fight_library` (the named fights `fight_dredge_ambush`, `fight_wreckers`, `fight_shroud_thieves`, `fight_rennick_guards`, `fight_silt_lurker` and `fight_granary_rats` are thin callers of it). **Any slot can be made tougher or weaker than its type** with three numbers set before the call: `combat_enemy_hp_override` (current and max HP), `combat_enemy_ac_override` (the number the player must beat to hit it) and `combat_enemy_atk_override` (its to-hit bonus; the type's special move moves by the same amount, so a +2 captain is +2 on every swing), with `combat_enemy2_` and `combat_enemy3_` versions for the other slots. Leave one alone and that number stays the type's own; 0 is a legal value. Captain Vane, a swordsman with 24 HP, AC 14 and +5 to hit, is a `swordsman` with `combat_enemy_hp_override 24`, `combat_enemy_ac_override 14` and `combat_enemy_atk_override 5`. Damage dice and damage bonus are still the type's own. Under the hood `999` means "not set" (quicktest runs both sides of every `*if`, so the arithmetic in `fight_setup` must never see a string), `fight_setup` applies and clears them and `fight_cleanup` resets them. A type is a **weapon**, not a person: `swordsman`, `axeman`, `knifeman`, `maceman`, `spearman`, `hookman` (hooked pole), `archer`, `slinger` and `guard` (plain mace, no special move) for anything humanoid, and `lacedon`, `mire_rat` and `beast` for creatures (`beast` is a generic natural-attack monster with no special move, 9 HP, AC 11, +3, d6+1, whose prose says only lunge, spring, rush, snap, bite, rake and slam, so a scene makes it a wolf, a boar, a bear, a giant spider or a ghoul by naming it: `combat_lib_1 "beast"`, `combat_enemy_name_override "Dire Wolf"`, `combat_enemy_epithet_override "the dire wolf"`, and the hp, ac and atk overrides for a tougher one). Underneath, `fight_library` sets `combat_apply_type` and `combat_apply_slot` (1/2/3) and calls `*gosub apply_enemy_type` once per slot; each call is independent, so a hand-written fight can still mix a library type into one slot with a hand-authored enemy in another. Add a new type by writing an `apply_type_<name>` label (stats and movepool only; either existing one as a template), one dispatch line in `apply_enemy_type`, one line in `flavor_from_type`, and a `flavor_type_<name>` label holding its prose. **A type's hit, miss and move-2 prose is written once, not once per slot:** `apply_enemy_type` records the slot's type in `combat_enemy1/2/3_flavor_type`, and `fight_narrate_enemy_turn` fetches the line from `flavor_from_type` (globals `fft_type`, `fft_v`, `fft_m2` in, `fft_hit`, `fft_miss`, `fft_m2hit`, `fft_m2miss` out), which rolls **eight** hit/miss variants and **three** move-2 pairs per type. Two copies of the same type in one fight draw from the same pool but roll independently on every attack, so they do not repeat in lockstep. A hand-authored fight (no type) is unchanged: its own `combat_flavor_enemy*_hit/miss_1-5`, five variants.
  * **The library names each fighter through `combat_enemy_epithet`, so calling a swordsman "the black knight" or "Captain Vane" is only a rename.** Every enemy line uses `$!{combat_enemy_epithet}` at the start of a sentence (the engine capitalizes the first letter) and `${combat_enemy_epithet}` inside one; the epithet defaults to the type ("the swordsman") and a scene overrides it with `combat_enemy_epithet_override` (slot 1) or `combat_enemy2_epithet_override` / `combat_enemy3_epithet_override`, and the banner name with the matching `_name_override`. This works only because the library's lines are built at the moment of the attack (`flavor_from_type`, called from `fight_narrate_enemy_turn`), when the attacker is already the active slot. Verified against `web/scene.js` `replaceVariables`: a `${var}` inside a `*set "..."` string resolves *immediately*, the instant that line runs, so a line stored at fight setup (the player's strike pools, a hand-authored fight's per-slot lines) cannot use the epithet and must name its target "they" or "the creature". Types are humanoid or creature bodies, so a line may say elbow, jaw or claws, but never a pronoun, a place or worn gear. An epithet with no article works as a proper name (`Captain Vane`).
  * **Optional per-instance rename** (`combat_enemy1/2/3_name_override`/`_epithet_override`, set before that slot's `apply_enemy_type` call) correctly renames the status banner, spell-targeting text, and victory/defeat lines — those interpolate live off `${combat_enemy_name}`/`${combat_enemy_epithet}` in directly-printed text, not through a stored variable — and, because the library's prose names the fighter through the epithet (see above), every library line too.
  * **Shared type and player strike lines are place-free, gear-free and pronoun-free, so any fight against human combatants can reuse them unchanged.** The hit, miss and move-2 lines of every type in `apply_enemy_type`, and the player's `flavor_player_*` lines (below), name no ground, wall, prop, water or street, no weather, lighting or time of day, and nothing the player may not be wearing (cloak, coat, cloth, leather, boots, armor, harness); the enemy is never "he", "she" or "it": it is the epithet or, to refer back within a line, singular "they" with a plural verb ("they slow", "they fold"), and never "the body" or "the frame" standing in for the foe. Each line is one physical action: how the attack moves, where it lands or how the player turns it aside, and what it costs. The old per-slot variables (`combat_flavor_enemy_miss_5`, `combat_flavor_enemy2_hit_4` and so on) still work as an override for a variant 1-5, a non-empty one replacing exactly that one library line and a per-slot `_move2_hit`/`_move2_miss` replacing the move-2 line, but **no shipped fight uses them**: a place belongs in the scene's own prose around the fight, not in combat text. Variants 6-8 are always the library's. `fight_cleanup` clears every slot's type, hit/miss variables and the creature pool's variants 6-8, so nothing carries into the next fight. The shared text never has to name a place, and a new fight normally needs no override at all. Write new types to the same rule. **The player's own strikes follow the weapon's damage type and name the fighter struck.** Against a human fighter, `pick_weapon_flavor` builds the hit and miss line at the moment of the attack, before the roll, from one of four labels: `flavor_player_slashing` (longsword, axes), `flavor_player_piercing` (daggers, stiletto, spear), `flavor_player_bludgeoning` (quarterstaff, bare fists) and `flavor_player_ranged` (bow, crossbow), each with eight hit/miss pairs chosen by `weapon_damage_type` and `weapon_type`. They name the target through `combat_enemy_epithet`, like the enemy lines, so with two guards the player reads "the left guard's hip", never "they". Two extra rules apply because the weapon's name is the player's own: the weapon is only ever an *object* of the sentence ("your ${weapon}"), never the subject of a singular verb ("your twin daggers finds" is wrong, "the point of your twin daggers finds" is right), and the bludgeoning lines read "bare fists" when the weapon noun is "unarmed". A new weapon needs no prose if its damage type is one of the three; a new damage type needs its own label and a line in `pick_weapon_flavor`. **A creature has its own lines, built the same way and named through the epithet.** `apply_creature_weapon_flavor` raises `combat_player_creature` (as well as `combat_player_keyed`; `fight_cleanup` clears both), and `pick_weapon_flavor` then calls `flavor_creature_slashing`, `_piercing`, `_bludgeoning` or `_ranged` (eight hit/miss pairs each). They assume only a body with a head, neck, shoulder, flank, side, ribs, legs and a reaching limb, so the same lines read on a wolf, a ghoul, a giant spider or a skeleton, and they call the foe the epithet or singular "they" (never he, she or it, and never "the body" as a stand-in), no hide, blood, claws, teeth, tail, fur or scales, and no sound the foe may not make. `apply_generic_weapon_flavor` raises only `combat_player_keyed`, and nothing is stored: the Dissonant Whispers lines and the sneak-attack lines are written in `fight_round_hub` and name the foe too. **The finishing blow is keyed the same way.** `pick_weapon_death_flavor` builds the blow at the moment of the kill from `flavor_kill_<type>` (a death), `flavor_yield_<type>` (beaten into surrender or a stupor, when `combat_is_nonlethal`) or `flavor_creature_kill_<type>` (a creature, eight lines each, no yield set), for `slashing`, `piercing`, `bludgeoning` and `ranged`, eight lines each, naming the fighter through the epithet. They assume no weapon anatomy the whole family does not share: no crossguard, pommel, hilt, haft, ferrule or blade, because an axe, a spear, a dagger and a staff are all just slashing, piercing or bludgeoning here. A slashing weapon has an edge and a flat, a piercing one a point, a blunt one is swung, and the rest is the fighter's body (elbow, knee, shoulder). Do not use "guard" in the sense of a fighter's defense in any player-side line, because it is also the epithet of Rennick's guards ("under the left guard's guard"): write "defenses", "reach", "parry" or "weapon". The old stored lethal set (five lines per damage type, written for "it", with "steel", "ferrule" and "crossguard") is gone. **Spell prose is built the same way.** Each attack spell option sets `combat_current_spell_id`, declares `*temp fsh` and `*temp fsm`, and calls `pick_spell_flavor`, which runs `flavor_spell_<spell>`: eight hit/miss pairs for Fire Bolt, Ray of Frost, Shocking Grasp, Eldritch Blast, Chill Touch, Vicious Mockery (a miss is a resisted insult) and Dissonant Whispers (a hit is a failed save, a miss a save for half damage), and eight hits for Magic Missile, which never misses. The killing or surrendering blow is `flavor_spell_end_<spell>` (five lethal and five non-lethal lines each, three for the generic fallback, Armor of Agathys included), called by `pick_spell_death_flavor`. They follow the weapon rules: named through the epithet (singular "they" to refer back, never he, she or it), and no scenery ("the damp air", "whatever's standing behind it"), so a spell line never places the fight anywhere. A hit, miss or kill assumes only a head, shoulder, chest, flank, legs and a reaching limb, so it serves a person or a monster; only the non-lethal set may use hands, weapons and knees. Keep a spell's mechanical text (the effect, the banner) in the hub and its prose here, and name the foe in banners and option labels too (`disadvantage on ${combat_enemy_epithet}'s next attack`). Still saying "it": the Shield working ("keeping it there"), which refers to the working, not a foe.
  * **The gang types are live in one shipped fight: the Dredge-End night ambush.** `fight_dredge_ambush` (combat.txt) picks one of four bruiser types at random (`maceman`, `knifeman`, `hookman`, `axeman`, each with a matching weapon and condition: mace Dazed, knife Poisoned, hooked pole Off-Balance, axe Bleeding) plus a `slinger` in slot 2, and records the bruiser's type id in `dredge_ambush_bruiser` (the loot check in `port_valen_dredge_end.txt` reads `"knifeman"` and `"axeman"`) (slots shift as foes fall, so the caller cannot read it back from `combat_enemy_name`). **No fight in the game is hand-authored.** `fight_rennick_guards` is two `guard` slots named "the left guard" and "the right guard" (non-lethal, with the default place-free finishers), `fight_silt_lurker` is a `lacedon` and `fight_granary_rats` is three `mire_rat` slots (lead, flanking, third), both using the creature lines; alderford.txt sets the shed, cellar and granary around them. `fight_wreckers` is an `axeman` and a `slinger`, and `fight_shroud_thieves` a `knifeman` and a `slinger` (non-lethal), with nothing retuned for the breakwater or the cellar. The old `fight_gang_thug` prototype and the cellar-only finishing-blow set (`combat_nonlethal_style`) were removed. A condition should match its weapon: a poison rider belongs on a knife, not a club.
* **Damage-Type Resistance/Vulnerability Is Real Data Now, Not Just Print Text — `combat_player_dmg_type`/`combat_enemy_dmg_type`.** Every damage source now sets an actual type token (vocabulary: `bludgeoning`/`piercing`/`slashing`/`fire`/`cold`/`lightning`/`necrotic`/`psychic`/`force`/`poison`, matching `weapon_damage_type`'s existing vocabulary) instead of just printing a word in a banner. A weapon attack sets `combat_player_dmg_type` to `weapon_damage_type` right after `roll_d20_check` succeeds; each attack cantrip's own `*choice` option sets its own fixed type (Fire Bolt → `"fire"`, Ray of Frost → `"cold"`, Shocking Grasp → `"lightning"`, Eldritch Blast → `"force"`, Chill Touch → `"necrotic"`, Vicious Mockery → `"psychic"`); Magic Missile and Dissonant Whispers set theirs *inside* their own `resolve_*` primitive in `startup.txt` instead, since RAW gives them exactly one type with no per-caster variation. An enemy's own attack type is `combat_enemy_dmg_type` (per-slot: `combat_enemy1/2/3_dmg_type`, default `"bludgeoning"` — every existing enemy is unaffected until a fight/type deliberately sets it to something else), with an independent `combat_enemy_move2_dmg_type` for a movepool's second move (`apply_type_gang_thug`'s knife-stab move 2 sets `"piercing"`, since its cudgel move 1 correctly stays the `"bludgeoning"` default).
* **Resistance/Vulnerability Storage Is Two String Slots Each, Not a Boolean Per Type — a Deliberate Tradeoff for ChoiceScript's Lack of a String-"Contains" Operator.** The player's own (equipment/race-granted): `player_resist_type_1`/`_2`, `player_vulnerable_type_1`/`_2` (persistent character stats, `*create`d empty, near `armor_class` — **not** fight-scratch, `fight_cleanup` never touches them). An enemy's own (type-library/fight-granted): `combat_enemy_resist_type_1`/`_2`, `combat_enemy_vulnerable_type_1`/`_2`, mirrored per-slot exactly like every other `combat_enemy1/2/3_*` field and reset by `fight_cleanup` same as condition/movepool. Two slots each is enough for anything this game's scope actually needs (no character realistically stacks 3+ elemental resistances) — a real "arbitrary list + contains check" would need a different storage shape ChoiceScript doesn't support cleanly (no substring/contains operator in `*if`), so this was chosen over a false-generality N-boolean-per-type explosion.
* **`apply_incoming_damage_resist_vuln`/`apply_outgoing_damage_resist_vuln` (`startup.txt`, right before `resolve_player_hit`) Are the Only Two Places This Math Happens — Every Damage Primitive Routes Through One of Them.** Resistance halves (rounded down, RAW), vulnerability doubles; **both present on the same type cancel to normal damage**, resolved as a single three-way branch (`(resisted) and (vulnerable)` → no-op, `elseif (resisted)` → halve, `elseif (vulnerable)` → double) rather than two sequential halvings/doublings, which would silently give the wrong answer whenever both apply. `apply_incoming_damage_resist_vuln` (called from `resolve_enemy_attack`, checked against the player's own `player_resist_type_1/_2`/`player_vulnerable_type_1/_2`) folds **Barbarian Rage's RAW resistance to the three physical types into this same check** instead of a separate halving elsewhere specifically so it correctly cancels against an item-granted vulnerability to the same type rather than silently compounding with it. `apply_outgoing_damage_resist_vuln` (called from every player-damage primitive — `resolve_player_hit`, `resolve_player_weapon_hit`, `resolve_magic_missile`, `resolve_dissonant_whispers`, and Armor of Agathys' retaliation — checked against the *active* enemy's `combat_enemy_resist_type_1/_2`/`_vulnerable_type_1/_2`, already synced in by `fight_sync_target_in`) needs no locking of its own: both are only ever called from inside an already-locked hit-resolution block, so a replay that skips the outer guard skips these for free, same as every other primitive in this file.
  * **Hex's necrotic rider die is NOT split out as its own separately-typed damage instance.** A weapon hit with Hex active still resolves resistance/vulnerability against the weapon's own type only (the combined roll, dice + Hex die together) — a deliberate simplification consistent with how this engine already treats Hex as "+1d6 to a hit" everywhere else, not a RAW-perfect per-component split. Not worth the added complexity for a rider this small.
  * **Two independent banner-tag vars, `combat_incoming_dmg_suffix` and `combat_outgoing_dmg_suffix` — never one shared var.** `resolve_enemy_attack` can call *both* subroutines in the same invocation (an enemy's own hit, then its Armor of Agathys retaliation), and the enemy-hit banner (`combat.txt`, printed after both have run) reads the incoming one. A single shared suffix var was tried first and got silently overwritten by the later (outgoing/Agathys) call before the earlier (incoming) banner ever printed it — caught and fixed before shipping, not by a player. Every hit banner in `combat.txt` appends `${combat_incoming_dmg_suffix}` (enemy-dealt) or `${combat_outgoing_dmg_suffix}` (player-dealt, including the Agathys retaliation banner, which also had to stop hardcoding "5 Cold Damage" as literal text and interpolate the actual, possibly-adjusted `${combat_player_dmg_dealt}` instead) right after the damage number, so a resisted (`🛡️`)/vulnerable (`💥`) hit is visible to the player, not just silently different math.
  * **A future resistance/vulnerability-granting item follows the same attunement pattern as every other magic bonus (§2) — set `player_resist_type_1`/`_2` inside `recalculate_equipment_bonuses` (or a routine it calls), gated on that item's own `X_attuned`, never a bare `apply_<slot>_loadout` write.** It's a real, revocable defensive bonus (comparable in weight to an AC or ability-score bonus), not a mundane cosmetic find. The two racial traits that already promised a damage resistance in their dossier text before this system existed — Dwarf's "resistance to poison damage" and Tiefling's "shrugs off fire" — are innate, not items, so they're wired the ordinary way instead: a flat `*set player_resist_type_1 "poison"`/`"fire"` right in `company_intake.txt`'s race-choice branch (and mirrored in `startup.txt`'s matching dev-menu presets), alongside that race's existing ability-score bonus, no attunement involved.
  * **The player has an action budget each round, as numbers, not flags.** `combat_player_actions_left` and `combat_player_bonus_left` are refilled at the start of every round from `combat_player_actions_max` and `combat_player_bonus_max` (all 1 by default; `startup.txt`), by `combat_begin_round` in `combat.txt`, which `fight_setup` and the end of `fight_enemy_turn` call. An **action** (attack, damage spell, Agathys, False Life, Brace, an item) leaves the hub through `fight_action_spent`: one action is spent and, if another is left, the hub reopens in the same round with no enemy turn. A **bonus action** (Hex, Healing Word, Second Wind, Rage) is gated on `combat_player_bonus_left > 0`, tagged `[Bonus Action]` in its hint, and leaves through `fight_bonus_spent`, which reopens the hub with the action still to come. Never spend by hand: both spends, and the one-off grants `combat_grant_action` / `combat_grant_bonus` (Action Surge), are replay-locked, because a bare `-1` runs twice when the page is replayed. An ongoing effect changes the `_max` value (Haste: `combat_player_actions_max` 2 while it lasts, back to 1 when it ends; 5e restricts its extra action to one weapon attack, Dash, Disengage, Hide or Use an Object, which a spell option can check with a flag when it is built; a feature that grants an extra bonus action raises `combat_player_bonus_max`), and `fight_cleanup` puts all four back to 1. **Extra Attack is not this:** it is more attacks inside one action. **Reactions are not a budget yet:** Shield is an armed flag that fires on the next hit. `combat_enemy_disadvantage` is cleared once per round in `combat_begin_round`, **not** on every hub entry, because the hub now reopens mid-round and must not undo a Ray of Frost cast earlier in it. When fights become turn-ordered, these become the acting creature's budget and `combat_begin_round` becomes `combat_begin_turn`. Test with the real engine and `refresh: true` (zero drift over several rounds), and sabotage a lock to prove the check can fail.
  * **Turn Order / Initiative (2026-09-27, step 4 of the turn-order rebuild) Is Rolled ONCE Per Fight, Not Per Round.** `combat_roll_initiative` (`combat.txt`, called from `fight_setup` right after every slot is built) builds `combat_turn_kind_1`-`_11`/`combat_turn_slot_1`-`_11` (`startup.txt`) -- the fixed order every combatant in THIS fight acts in, kept for the whole fight, 5e's own rule. Two parallel fields per position (`kind`: the literal string `"player"`/`"ally"`/`"enemy"`; `slot`: 0 for the player, 1-4 for an ally, 1-6 for an enemy) instead of one composite id like `"enemy3"` -- this engine has no reliable substring/parse support, so a composite string would need parsing back apart later; two fields never do. Candidates are the player plus only the POPULATED ally/enemy slots (`1..combat_ally_count`, `1..combat_enemy_count`) -- a 1-enemy fight builds a 2-long order, not an 11-long one padded with empty slots. Each candidate rolls `*rand 1 20` + `score_to_mod`'s modifier for their own DEX (allies got one `combat_allyN_dexterity` field for exactly this, default 10 -- not the full six ability scores enemies have, since nothing else needs an ally's stats yet). **Built with a selection sort, not insertion** -- repeatedly scan every not-yet-placed candidate for the best remaining one (`cri_is_better_than_best`), place it, mark it used; simpler and safer than an insertion sort's shifting step, and with at most 11 candidates the O(n²) cost is nothing. **Tie-break ladder, fully deterministic so it's testable:** higher initiative roll, then higher RAW DEX SCORE (5e's own rule -- proven to matter with a real test case: DEX 12 and 13 both give the same +1 modifier under the corrected `score_to_mod`, so a modifier-only tiebreak would have no way to order them at all), then player over ally over enemy, then ascending slot number. **Scratch candidate storage (`combat_init_kind_1`-`_11`/`_slot_/_score_/_dex_/_used_`) is persistent `*create`d, not `*temp`** -- so `{}`-indirection can target it the same way every other scratch pool in this engine already does, which also means it must be explicitly re-cleared (the `_used` flags) at the top of every call, since persistent storage doesn't reset itself between fights the way a fresh `*temp` scope would. **Index 0 needs its own inert placeholder** (`combat_init_kind_0` etc.) for the same quicktest branch-coverage reason documented under the enemy-widening bullet above -- `cri_is_better_than_best`'s `*else` branch is walked even on the pass where `cri_best` is still 0. **Nothing reads `combat_turn_kind_*`/`_slot_*` yet** -- `fight_round_hub`/`fight_enemy_turn` are unchanged, still their own two-phase loop; this chunk is the roll and the order only, verified in isolation (an 8-check suite forcing `rand: "mid"` for the whole run, which cancels the roll identically across every candidate and isolates the ordering to DEX alone) before anything is wired to consume it. **A cross-file `*gosub` reminder that bit the real code this time, not just a test:** `score_to_mod` lives in `startup.txt`; calling it from `combat.txt` needs `*gosub_scene startup score_to_mod ...`, not a bare `*gosub` -- caught by the IDE's own ChoiceScript diagnostics ("this label wasn't found") before ever running it, not by a test.

## 7. Verification & Tooling Discipline (Right-Sized Testing)
* **Run `quicktest` Freely After Any Scene Edit — It's Cheap and Reads Live State:** `autotest.js` loads every scene via `slurpFile` straight from `web/mygame/scenes/*.txt` on each run — no compile step, no caching across runs, always the current file content. It's a single deterministic static-exploration pass (seconds, not minutes), and it's the *only* tool here that catches label/reachability/syntax errors: a dangling `*goto_scene` to a scene that doesn't exist, a missing `*label`, unbalanced `*if`/`*elseif`, invalid `*create` syntax. The targeted linters below check prose voice and vocabulary, not structural reachability — they are not a substitute for `quicktest` when a change touches labels, `*goto`/`*goto_scene` targets, or a new scene file. Treat a scene-structural edit as incomplete until `quicktest` has been run against it.
* **Targeted Linters for Prose/Voice/Vocabulary Concerns:** When auditing a specific plan or scene file for tone, choice formatting, or setting-appropriate vocabulary rather than structure, reach for the narrow tool, always passing the exact target file path as an argument:
  - Choice syntax & structure: `node tools/lint_choices.js path/to/target_file`
  - Prose tics & voice: `node tools/lint_prose_tics.js path/to/target_file`
  - Metallurgy & setting vocabulary: `node tools/lint_anachronisms.js path/to/target_file`
  - Weapon neutrality: `node tools/lint_weapon_assumption.js path/to/target_file`
  A markdown design plan (`quest/*.md`) isn't a scene file at all — `quicktest` has nothing to check there either way, so use these targeted linters (or a plain read-through) for plan-doc review instead of any whole-game tool.
* **Reserve Expensive Fuzzers for Real Integration Sweeps, Not Isolated Edits:** `randomtest` at high iteration counts, `check_coverage` with 1,000 playthroughs, and multi-thousand-run calendar monte-carlo passes are genuinely costly and are not warranted for a single scene adjustment — that's what `quicktest` (above) is for. Reserve the heavy fuzzers for full-game release validation or changes that plausibly affect many interacting systems at once (a shared subroutine in `calendar.txt`/`combat.txt`/`startup.txt`, a new stat that gates content across multiple scenes).
