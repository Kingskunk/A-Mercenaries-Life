# Gameplay Mechanics Rules

Shared implementation, combat, equipment, state-safety, and verification rules for *A Mercenary's Path*. Prose and voice live in `.agents/rules/narrative_guidelines.md`; quest shape, rewards, failure and time costs live in `quest/QUEST_DESIGN_RULES.md`. Cross-references below name the file and section.

This file records durable rules and constraints, not a changelog. When a bug is fixed, don't log the incident here — fold the standing rule that would have prevented it into the relevant bullet, or add a new one if none exists.

## 1. ChoiceScript Code Discipline & State Hygiene
* **Strict Line-Separated Flow Control:** `*if`/`*elseif`/`*else`/`*set`/`*goto`/`*gosub` must start on their own indented line, never inline in prose, or ChoiceScript prints the raw code to the player.
* **No Nested Multireplaces:** `@{var1 @{var2 ...|...}|...}` fails to parse. Compute multi-condition hints into a `*temp` string before the `*choice` block instead.
* **Expressions Need Explicit Parentheses Around Every Operator Pair.** ChoiceScript doesn't chain operators: `a + b + c` throws "expected CLOSE_PARENTHESIS". Nest pairwise: `(((gold * 100) + (silver * 10)) + copper)`, and write `or`/`and` chains as `(((a) or (b)) or (c))`. `quicktest` catches this on lines it reaches, but only those.
* **A Prose Line Must Not Start With `*`, and `*word*` Is Not Italics.** A leading `*` is read as a command. Mid-line, `*word*` prints the asterisks literally — use `[i]…[/i]` for emphasis.
* **`*comment` Is the Only Comment Syntax.** A trailing `; note` or `// note` becomes part of the line or a parse error.
* **Engine State Hygiene:** every temporary roll modifier (`advantage`, `disadvantage`, `guidance_active`) must reset to `false` inside `roll_d20_check` on return, so it never leaks into an unrelated choice.
* **Refresh/Replay Safety (No Bare `*set var +N`/`-N`):** a refresh or Stats/Menu round trip can replay the current page with no new player action, silently re-running every command on it. A bare increment/decrement is unsafe anywhere a page can pause (`*choice`, `*page_break`, before a `*gosub`/`*gosub_scene`) unless guarded:
  1. **Prefer a fully derived stat** — recomputed from persistent flags every time (`recalculate_armor_class`) instead of nudged with `+N`; a full recompute needs no lock at all.
  2. **Otherwise, lock the mutation:** `*if (not(X_locked)) or (not(locked_X_page_id = page_id)) ... *set stat +/-N ... *set X_locked true ... *set locked_X_page_id page_id`. Reuse `currency_txn_locked` for silver/copper, `stat_bump_locked`/`locked_stat_bump_page_id` for everything else — don't invent a lock per stat or site. If two independent mutations can land on the same page with no `*choice` between them, give the second its own lock — the pre-declared `stat_bump2_locked`/`locked_stat_bump2_page_id` slot exists for exactly this.
  3. **Splitting a guarded success block to add prose:** compute the bump once inside the guard, then follow with a second, unguarded prose-only re-check. If the *prose* re-checks the stat you just bumped against the same threshold that decided the bump, capture the pre-bump boolean into its own persistent flag inside the guard instead, and branch prose on that flag.
  4. **A page that legitimately triggers the same kind of mutation twice** (falling from one activity into another with no intervening choice) needs a per-call-site identifier on top of `page_id`: a plain `*create`d `..._call_id`, not `*params` (which throws if reached without a real gosub, where a `*create` default just reads as "unlocked").
* **A Dossier Action That Advances Time Must Put `advance_time`'s Lock Pair Back.** The dossier runs beside the game and replays the page underneath it when it closes. `advance_time` remembers only its last call (`time_advance_locked`, `locked_time_advance_page_id`, `locked_time_advance_id`), so a rest taken in the dossier leaves the lock holding *its* id, and the page underneath applies its own time advance a second time. Save those three plus `time_advance_call_id` in `*temp`s before the call and set them back after (see `codex_rest_short`). Test with a page that has just advanced time: open the dossier, act, close, confirm the clock moved by the action's time only.
* **Class Resources Live in One Place, and No Scene Types a Pool Number.** Pool maxima (Second Wind, Rage, Pact Magic, Wizard/Bard slots) are written once, in `refresh_class_resource_maxs`, as a ladder over `character_class`/`character_level`. A long rest is one routine, `restore_class_resources`. A sleeping place calls `resolve_sleep`, which calls that routine — a new inn or camp gets a full long rest for free by calling `resolve_sleep`; it lists nothing itself. A short rest is `short_rest_preview`/`do_short_rest`/`short_rest_banner`. Adding a pool means one line in the ladder, one in `restore_class_resources`, the short-rest routines, and the displays (`choicescript_stats.txt`, `index.html`, `inventory.js`) — never editing a scene that sleeps or rests. Second Wind follows 2024 rules: 2 uses (3 from level 4, 4 from level 10); a short rest returns one use, a long rest all of them. **Short rests are capped for every class** at `short_rests_max` (2) between long rests (`short_rests_left`, refilled by `restore_class_resources`); one that gives something back spends one, and one that would give nothing is not offered and not spent. A Wizard, Bard or Ranger gets back half their spell slots, rounded up; a Warlock all of theirs; a Wizard's Arcane Recovery is a once-per-long-rest bonus on top. The cap and the half-slot rule live only in `short_rest_preview`/`do_short_rest`.
* **A Genuine +1 Called From a Page Needs a Guard a Replay Cannot Repeat, and a `page_id` Lock Is the Wrong Guard in the Dossier.** A short rest always takes an hour, so the clock at its end is unique to it — `last_short_rest_stamp` remembers it, and a replayed page (same clock) gives nothing a second time. A `locked_..._page_id` guard set inside the dossier carries the *dossier's* page number back, which the game's own `page_id` doesn't follow, so a later page could collide with it and silently skip a real rest. **When a page in the dossier needs a replay guard that the clock cannot give, key it on flow, not on `page_id`:** the Rest result page sets `short_rest_applied` when it has done its work, a replay of it sees the flag and only reprints, and the Rest menu (`codex_rest`), which every new rest passes through, clears it. A `page_id` lock there skipped a real second rest, because the dossier's page numbers restart from the game page's own each time it closes. A replay check cannot see this: drive the flow twice in a real browser.
* **Max HP and Proficiency Are Derived From Level, and Only in `update_dnd_stats`.** `hp_max` is `character_level * (hit_die_max + con_mod)` (house rule: max of the die at every level); `prof_bonus` is `2 + (((character_level - 1) - ((character_level - 1) modulo 4)) / 4)`. Never set either anywhere else, and always call `update_dnd_stats` right after changing `character_level`. Take the remainder off with `modulo` before dividing — this engine's `/` and `round()` have no floor.
* **The Level-Up Pool Is Derived From Success Flags; a New Quest Is One Line.** `refresh_quests_finished` counts finished quests from flags set once, in the quest's success label, and never cleared; `refresh_level_up_progress` sets `level_up_ready`. Only a successful completion counts — a failed ending or a radiant job never does. Give every new quest its own completion flag, never a flag another route also sets. Training sessions go through `training_preview`/`do_training_session`, clock-guarded the same way as `do_short_rest`.
* **A Quest's Own Completion Flag Flipping AFTER `advance_time` Already Ran on the Same Page Needs an Explicit Re-`update_hub_condition`.** `advance_time` calls `update_hub_condition` (→ `refresh_quests_finished`/`refresh_level_up_progress`) internally, early. If a quest's `..._resolved`/`..._quest_stage "resolved"` flag is set LATER on that same page (no `*choice` in between — a `*choice` pick always starts a fresh page via `resetPage`'s `page_id` bump, which makes this a non-issue), `quests_finished`/`level_up_ready` stay at their pre-completion value for the rest of the page, even though both routines are themselves correctly idempotent. A refresh replaying from page start (already-flipped snapshot) recomputes fresh at that same early point and disagrees with the original run — reads as a duplication bug, but is really staleness. Recurred at 10+ separate quest-completion sites in `port_valen.txt`/`port_valen_dredge_end.txt` before each got its own explicit `*gosub_scene calendar update_hub_condition` immediately after its own resolution flag changes. Check for this whenever a completion flag is set on a page that also called `advance_time` earlier with no `*choice` between them.
* **A Level Is Taken by an Exact Target, and Everything Else Follows From State.** `do_level_up` sets `character_level` to `level_up_from + 1` (captured on the confirm page before the choice), so a replay of the apply page sets the same level again instead of adding another. HP and each class pool rise by the change in max, computed against pre-level-up snapshots captured at entry, so a replay finds the maxima already changed and adds nothing.
* **The Top-Bar Level Up Button Is a Shortcut, Never the Decision.** It opens the dossier's own `codex_levelup`, exactly like the Inventory's Rest card opens `codex_rest` — a missing button loses nothing. `level_up_ready` is kept current by `update_hub_condition`; a sub-hub that doesn't call it won't reflect it.
* **Detect the Open Dossier With `window.stats.scene.secondaryMode === "stats"`, Never With the Show Stats Button's `data-return`.** `data-return` stays set after any dossier visit regardless of how it closed. Look the top-bar button up fresh on every poll instead of caching it — the page rebuilds the bar.
* **A Training Place Follows One Shape, So Later Teachers Cost Prose Only.** A hub button gated on `level_up_sessions_needed > 0`; a place page whose training option is always listed and reworded (never hidden) when it can't run; a session page that advances time and calls `do_training_session`; prose picked from a rotating pool, never the clock or `*rand`; a talk page keyed to session/quest bands. The count, the once-a-day rule and the thresholds live nowhere in the place itself. A new teacher only adds vignettes and talk lines.
* **A Blank Line After an `*if` That Printed Nothing Does Not Start a New Paragraph.** The engine drops the blank line following a skipped block. Put the blank line before an optional check, not after. Check by rendering (`tools/render_hub.js`).
* **Reset a Consumed Input Outside the Lock, Not Inside It:** a subroutine that clears caller-supplied working variables when done (`advance_time` zeroing `minutes_to_pass`) must do that reset unconditionally *after* the guarded math — resetting to a fixed literal is always safe to repeat and needs no lock.
* **A Column-Wise Currency Subtract Can Drive a Higher Denomination Negative Even With Plenty of Total Funds.** Subtracting gold/silver/copper independently only borrows when a lower column goes negative — nothing borrows into gold, so a cost heavy in a denomination the player holds none of can drive that column negative despite ample total wealth. Always recompute from total value and re-split fresh instead.
* **A Shared Subroutine Called Multiple Times On the Same Page Needs a Per-Call-Site Lock.** A single "last call id" only tracks the most recent caller — if a loop calls the same guarded subroutine 3+ times on one page, each new call overwrites the remembered id. Use independent per-call-site memory (one boolean per slot), not one shared id.
* **A Persistent Stat Read For Display, Then Zeroed Later On the Same Guarded Page, Needs the Read Inside the Guard Too.** A refresh reconstructs from *current* stats, which by replay time may already hold the post-reset value — an unguarded read before the reset reproduces as blank/zero on replay. Move the display computation inside the same guard as the reset.
* **A Guarded Incremental Mutation Can Be Silently Erased By an Unrelated, Unconditional Line Touching the Same Stat On the Same Page.** The unconditional write reruns on every replay while the guarded one only applies once, so it silently outruns and erases the guarded value. Once two writers touch one stat on one page, stop mutating it from either side and recompute it as a pure function of persistent, correctly-guarded inputs instead (`recalc_hp_from_neglect` is the pattern).
* **`*goto_scene` Must Never Fire From Inside an Active `*gosub_scene` Call.** It discards the whole subscene stack, corrupting any outer `*return` still pending. A shared subroutine that needs to end the game or jump scenes on an internal condition must surface that condition as a plain stat and let the top-level caller do the jump after its own `*gosub_scene` has already returned.
* **Full Slot Coverage:** when gating by learned spells/cantrips, check every slot so no build is orphaned.
* **Three-Point Metadata Synchronization:** new lore/location/faction/companion needs all three: `*create var false`, progressive disclosure in the dossier, and dev jump menus setting prerequisite flags/clock state.
* **One-Time Story Grants Guard Themselves:** wrap a discrete once-only grant entirely in `*if (not(has_X)) ... *set has_X true ...`, checked before any side effect. Naturally replay-safe — no `page_id` lock needed.
* **Guard One-Time Init on a Dedicated Flag, Never a Variable With a Matching Default:** gate a run-once block with its own `..._initialized` flag, not another variable's value, without confirming that variable's `*create` default doesn't already read as "done."
* **`*set var -1` Is Decrement Shorthand, Not "Set to -1":** a leading `+`/`-` always means "adjust the current value", so `*temp d 1` followed by `*set d -1` leaves `d` at 0 (a Push Forward that shifted no enemy at all until this was found: `combat_shift_all_ranges`). To assign a negative, use a parenthesized expression whose first token is not an operator: `*set var (0 - 1)`. A bare `*create` of a negative literal is invalid for the same reason.
* **Never Build a Variable Name From `character_class` (or Any Value That Can Be `none`).** quicktest walks every branch, including ones whose guard is false, so `{(character_class & "_spell_slots")}` is looked up as `none_spell_slots` and fails there. Write each class out by name; a routine that serves several classes spells out its branches (see `do_short_rest`).
* **A Bare `*create X 85` Stores a String; Only `*set X +N` Produces a Real Number.** A Node harness inspecting `stats` directly must coerce with `Number(v)`/`isNaN`, not trust `typeof`.
* **`/` Never Floors.** A plain `/ 2` for a half-damage effect yields a fraction (`HP: 10.5 / 14`) that prints verbatim. Any `/ N` meant to floor needs `(X - (X modulo N)) / N`.
* **When Auditing a System for Missing Mechanics, the Dossier's Ability-Card Text Is the Fastest Source of Truth for What's Promised** — grep it for "advantage"/"disadvantage"/"until"/"can't"/"reaction" and cross-check each hit against the actual combat code. A feature can be selectable and fully described while doing nothing in a fight. Fix what maps onto mechanics that already exist; flag what would need a new one — implementing one such ability while its siblings stay unwired leaves the game more inconsistent than leaving all of them alone.

## 2. Equipment & Magic Item Systems
* **Tradeable Items Live in `tools/gear_catalog.json`; the Repeated Code Is Generated, Never Hand-Written.** One catalog entry per item (id, kind, names, price, hint, blurb, tier, sell percentages, loadout fields, dossier text). `node tools/gen_gear.js` (also run by `compile.js`) rewrites every `GEN:BEGIN`/`GEN:END` block: the `*create`d flags/cart variables (`startup.txt`), loadout branches (`equipment.txt`), dossier lines/equip options (`choicescript_stats.txt`), inventory panel entries, each shop's buy/sell stanzas, and `trade-data.generated.js`. Never edit inside a generated block; `--check` exits 1 if one is stale. To add an item: add its catalog entry, list its shops, run the generator. Armor picks an existing `armor_type`; quest rewards and story items stay out of the catalog. Worn clothing (`cloak`/`hands`/`waist`/`feet`/`neck`) is stackable with optional `traits` (`{cold, wet, heat, stat, bonus}`). A shop's `buyer` is `smith`/`pawn`/`general`/`tailor`, each with its own sell percentage — keep a cheap item's retail high enough that the percentage doesn't floor to 0.
* **Item Titles Are Short and Plain.** Three words or fewer, no treatment words (boiled, oiled, waxed…) and no lore prefixes — that detail belongs in the `blurb` and dossier line. A rename changes display text only (ids never change) and must be swept across the catalog, hand-written loadout tables, chargen/dev-preset defaults, the dossier, `inventory-data.js`, acquisition banners, and `EQUIPMENT_AND_ITEMS_REFERENCE.md`; grep the old title afterward. NPC dialogue and quest documents may keep an item's full in-fiction name. Two items must never share a title.
* **What a Worn Piece Does Is Shown Everywhere From One Table.** A worn piece's text lives in the `*set garment_hint` line in `equipment.txt`'s `garment_traits`; `tools/gen_equipment_data.js` publishes it to `window.GARMENT_HINTS`, read by every panel and the dossier. Never hand-write a piece's numbers in a panel.
* **Equipment Score Bonuses Are Derived From What Is Worn, Never Written.** `recalculate_equipment_bonuses` takes the single highest `garment_bonus` per stat across the seven worn slots (they don't stack) and rebuilds scores as base + timed boon + equipment before calling `update_dnd_stats`. Any code that equips/removes clothing goes through `equip_<slot>`/`equip_by_slot`/`sell_gear`, never a bare `*set equipped_<slot>_id`. The inventory panel can't recompute scores itself — a swap carrying a `statBonus` is handed to ChoiceScript (`codex_equip_do`).
* **Gear Is Stackable, and the Trade Panel Is Only a Layer Over the Menus.** `has_<id>` means "at least one"; `spare_<id>` counts the rest. Any grant/take goes through `grant_gear`/`sell_gear`, never a bare `*set has_<id>`, unless it's a one-off quest reward outside the catalog. The trade panel only builds a cart and clicks a hidden option — prices, counts and the currency lock are all decided in ChoiceScript. Every panel-offering shop keeps its plain menu as a fallback.
* **Consumables Are Catalog Items Used Through One Routine.** A `kind: "consumable"` entry with an `effect` (`heal`/`boon`/`wash`/`dressing`), stackable via `has_<id>`/`spare_<id>`. Its effect is written only in `use_consumable`; the combat option, dossier satchel menu, and inventory Use button all call it — never write a one-off `*set has_x false` heal. Healing consumables are free in combat; out of combat they share the once-a-day instant-heal limit. A new effect type needs a `gen_gear.js` branch and a `use_consumable` branch.
* **Armor Has a Derived Tier and a Class Proficiency Rule.** `armor_tier` is derived from `armor_type` in `apply_armor_loadout`; a new armor id needs its type mapped there, in `recalculate_armor_class`, and in `EquipmentEngine.recalcArmorClass` (run `tools/check_ac_formula_sync.js`). Shields follow the same pattern. Never gate gear by class — loot has to work for every build.
* **New Weapons/Armor Route Through the Loadout System, Never a Bare `*set weapon`.** A mid-game pickup grants a `has_X` flag, adds a branch in `apply_weapon_loadout` keyed by `equipped_weapon_id`, and is equipped via `equip_weapon` from the codex. Equipping two-handed auto-drops the shield.
* **Magic Items Are Attuned, Never Given Outright.** A bonus must never be a permanent `*set <stat> +N` — attunement has to be revocable: grant `has_X`, add the bonus as a candidate in `recalculate_equipment_bonuses` keyed on `X_attuned`, bind/unbind via `attune_item`/`unattune_item`, capped by `max_attunement_slots`. An ability-score bonus needs a `base_<stat>` snapshot so it adds/removes cleanly. Auto-attune on pickup if a slot is free.
* **The Full Paper-Doll Follows the Same Id-Driven Shape.** Every slot (head/cloak/hands/waist/feet/sidearm/neck/rings) has an `equipped_<slot>_id` and a pure `apply_<slot>_loadout` re-derive called unconditionally from `update_dnd_stats`. Only head carries real AC math. Every worn slot has `garment_traits` (exposure cuts, optional score bonus), read at use time from the equipped id so a swap never leaves a stale value. Don't invent per-slot variants — a new slot is just a new id + loadout pair.
* **A Mundane Find (No Stat Bonus) Skips the Attunement/Dossier Indirection Entirely.** An item with no mechanical effect just does `*set has_X true` + `equip_<slot>` directly at the pickup site, with a branch in the matching loadout for its desc. Reaching for attunement plumbing on a flavor item is over-engineering.
* **Equipment Ability-Score Bonuses Are Ordinary and Do Not Stack; a Bonus on the d20 Roll Itself Is the Rare, Gated Kind.** Ordinary purchasable gear may carry a +1/+2 to a score, and only the single highest equipment bonus to a stat applies (timed boons are a separate channel and still add). A flat bonus on the roll itself, an attack roll, or a spell save DC — or advantage — is worth a full point on every roll and belongs only to named-NPC gifts, rare quest rewards, and late-game content. Early ungated finds stay mundane (`QUEST_DESIGN_RULES.md` §10). Penalties on the roll (fatigue, grime) are a separate mechanic.
* **The Inventory Panel Is a Deliberate, Scoped JS Mirror of Equipment Logic — Not a Second Source of Truth.** `equipment.txt` stays the only authored source; `tools/gen_equipment_data.js` regenerates the panel's data automatically (auto-run from `compile.js`). The only hand-ported logic is `EquipmentEngine.recalcArmorClass`, kept in lockstep by `tools/check_ac_formula_sync.js` — run it after any edit to `recalculate_armor_class` and fix the mirror if it fails.
* **`equip_weapon` Must Swap, Not Overwrite, When the Incoming Id Already Sits in the Sidearm Slot.** Sidearm items carry no `has_X` flag — `equipped_sidearm_id` is their only record of existing. Any future slot pair sharing an id space the same way needs the identical swap guard.
* **The Inventory Panel's Interactive Slots Must Match What `choicescript_stats.txt`'s Real Menus Actually Offer, Never What `EquipmentEngine` Could Technically Do.** `swappable: true` is set per-slot in `inventory-data.js` to mirror the real menu's actual scope. Neck, Rings and Sidearm have no picker. Building a control for a slot the real menu never exposed produces a broken dropdown — check the real menu for a matching choice first.
* **A Renamed Item Id's Display Fields Touch More Files Than `equipment.txt` Alone.** Sweep chargen/dev-preset defaults, the dossier's live display AND its menu option text (which hardcodes item names), any scene banner naming the item directly, `inventory-data.js`, and `EQUIPMENT_AND_ITEMS_REFERENCE.md`. Grep the old name and the banned-jargon list across `web/mygame` after every rename — the "obvious" file list reliably undercounts real references.

## 3. Reusable Town-Content Primitives (Gambling, Taverns, Currency)
* **Never Hand-Roll a New Ante/Payout/Lock Trio Per Town — Call the Shared Subroutine.** `startup.txt` provides three so future towns don't reinvent this plumbing:
  * `currency_add` — pure arithmetic, no locking of its own. Input `currency_add_amount` (signed, copper-equivalent); adds/spends against `gold`/`silver`/`copper` with correct carry/borrow. Always call from inside the caller's own replay guard.
  * `resolve_wager` — one subroutine for any gambling table. Set `wager_bankroll_var`, `wager_ante_copper`, `wager_win_copper`, plus the usual `check_*`, then gosub. Debits the ante, credits the house, pays out on success capped to the bankroll. Returns `check_success` and `wager_bankroll_busted` — use the latter to hide the option once the house is tapped out.
  * `buy_tavern_item` — one subroutine for a purchasable consumable that spends coin and optionally heals HP and/or grants the single-slot nourishment buff. Hide an item's option while its own buff is already active.
  * **Food, drink, unique and sleep buffs are timed ability-score boons, not roll bonuses.** A buff's `_stat`/`_bonus` add to the ability SCORE (`buff_<stat>_bonus`, summed by `recalculate_buff_stats`) — the six score variables hold the boosted number, so the sidebar, dossier, and every raw-score check agree. After chargen never write a score directly: change `base_<stat>` and call `recalculate_buff_stats`. Scores are base + timed boon + equipment — the two bonus channels are separate and both add. Modifiers step at even numbers, which is what makes a +1 matter only sometimes. Never add a buff to a d20 roll or write "+1 X checks" in player text — write "+1 X".
  * All three primitives handle their own internal replay locks — a caller only needs `currency_txn_locked` around hand-written currency mutations elsewhere.

## 4. Testing Tools & Verification
* **Several complementary tools — use the right one, and don't treat any one as sufficient alone:**
  * `quicktest.js` (`node quicktest.js web/mygame`) — parses every scene and walks every reachable line once. Catches parse errors and `*goto`/`*label`/variable typos. Doesn't catch logic bugs.
  * `randomtest.js` (`node randomtest.js num=N seed=S`) — plays start-to-finish with random options N times. Catches crashes/reachability; does **not** check refresh-safety.
    * `showUnreachedLabels=true` flags labels with 0 hits — a candidate for dead content, but rerun with a different seed before concluding it's truly unreachable.
    * `gotoLoopCap=N` (default 200000) guards against a goto cycle with no intervening pause; reports `OPEN-WORLD WANDER` instead of aborting, since an open-world seed can genuinely wander forever with nothing forcing a `*finish`.
  * `refresh_fuzz_test.js` (`node refresh_fuzz_test.js num=N seed=S`) — catches the refresh/replay-duplication class this doc guards against. Snapshots stats at every pause, independently replays the page against a clone, diffs. Run after any change touching a bare `*set stat +N`/`-N`.
    * `mode=smart archetype=str|dex|con|int|wis|cha|balanced` makes the walk build-aware, giving repeatable coverage of each archetype's real success paths.
    * `[refresh-duplication]` findings are real bugs. `[shadow-diverged]`/`[shadow-no-pause]` are diagnostic-only (see the blind-spot note below) — don't chase them.
  * `tools/lint_thin_prose.js` — flags `*choice` options resolving with little/no narration. Report-only; `SILENT` (shared narration after the block) and `DELEGATED` (`${variable}`-sourced prose) are expected patterns, not findings.
  * `tools/lint_mechanics_leak.js` — flags mechanic vocabulary (`DC N`, `N damage`, dice notation, named ability checks) leaking into narration outside brackets/banners, per `QUEST_DESIGN_RULES.md` §11. Report-only.
  * `tools/lint_prose_tics.js` — flags the filler phrases `narrative_guidelines.md` §6 names. The negative-framing check (`includeNegativeFraming=true`) is opt-in only — high false-positive rate here.
  * `tools/lint_weapon_assumption.js` — flags `narrative_guidelines.md` §9's bladed-weapon phrases and checks whether the enclosing `*if` chain actually gates on a weapon type. `VIOLATION` = confident, `REVIEW` = ambiguous. Report-only, read every hit in context.
  * `tools/lint_anachronisms.js` — flags chemical/industrial anachronisms forbidden by `QUEST_DESIGN_RULES.md` §10. Report-only.
  * `tools/lint_blank_landing.js` — flags a `*page_break` destination that prints nothing before its `*choice` (a genuinely blank screen), distinct from `lint_thin_prose.js`'s `SILENT` case. Distinguishes BLANK from BANNER-ONLY (usually intentional). Report-only.
  * `tools/lint_vocab_overuse.js` — word-frequency analysis (global overuse, tight clusters, and a hand-maintained restricted-words list) complementing `lint_prose_tics.js`'s fixed-phrase grep. Proper nouns are auto-excluded. Report-only.
  * `tools/render_hub.js` (`[weather] [time] [day] [scene] [label]`) — renders a hub/POI's actual text across every weather × time × day combination after real calendar derivation. Run whenever weather/time/day prose changes; scan `street_life=empty` renders for people-words. `PICKS=N` exhausts a random pool instead of sampling it.
  * `tools/scripted_play.js` — plays one scripted path through the real engine and prints the prose, choices, dice, and stat deltas. `refresh: true` replays every page and reports drift; `sabotage` proves a check can fail. Shows prose but doesn't judge it.
  * `tools/sim_weather.js` — advances the real calendar and prints weather/temperature/exposure distributions and clock sanity checks. Run after changing weather tables or `calc_exposure`.
  * `tools/lint_thin_places.js` — word-counts every hub/POI across every weather × time × day combination against a minimum. Advisory unless `strict=true`; use `only=` for a fast run.
  * `tools/lint_all.js` — runs every per-file linter above on one file or folder. Add a new per-file linter to its `LINTERS` array, not to whole-game tools.
  * `tools/lint_dash_frequency.js` — reports em-dash density per file. Advisory.
  * `tools/lint_weather_names.js` — enforces `QUEST_DESIGN_RULES.md` §12's weather-naming rules. Advisory.
  * `tools/lint_slow_healing.js` — guards the Port Valen slow-healing rule: flags an absolute/uncapped heal or "fully restored" prose. Checks `port_valen*` only unless `all=true` (the prologue may heal instantly).
  * `tools/gen_equipment_data.js` / `tools/gen_gear.js` — regenerate the equipment/gear-catalog generated files (§2); both auto-run from `compile.js`. Use `--check` after editing the catalog.
  * **Testing a JS panel (`trade.js`, `inventory.js`) needs a real browser; `quicktest`/`randomtest` never see it.** Build with `node compile.js <output.html>`, load headless over the DevTools protocol, drive `window.stats`/button clicks directly. Re-test after a ChoiceScript redraw — the old page can linger during a fade.
  * `tools/check_ac_formula_sync.js` — drift-check between `recalculate_armor_class` and its JS mirror via real headless playthroughs. Run after any AC-formula edit; a mismatch means fix the mirror.
  * `tools/gen_ui_art.js` / `tools/gen_action_icons.js` / `tools/gen_spell_icons.js` — regenerate the inlined interface art, the HUD's action icons and the spell icons (data URIs; the game ships as one HTML file). `--check` after editing their source tables or the ICONS library. `gen_ui_art.js` needs Chrome (it shrinks the images in a canvas).
  * **`tools/scripted_play.js ... refresh=true` is the replay check for pages the random fuzzer cannot reach** (dossier menus, a specific fight option). Read what differs: a change to the player's own state is a real bug; scratch outputs of a check routine are noise; enemy stats changing on the first page of a fight started INSIDE the combat scene is a harness artifact (a real fight is entered through `*gosub_scene`, and a real browser reload leaves the enemies identical, so confirm there). It cannot see a page-number collision between two visits: drive that flow twice in a real browser.
  * **A real-browser probe (headless Chrome over the DevTools protocol, e.g. `scratch/probe_battle_hud.js`) is the only check for panel and interface behaviour.** Use a fresh browser profile each run (a stored autosave resumes mid-menu), wait for an option to exist before picking it, measure positions and sizes instead of judging screenshots, and run an interface change at 1920x1080 and at 3840x2160 (the screen-fit zoom, §9).
  * **A one-off directed trace** for a mechanic the fuzzers won't reach on their own — bootstrap like `randomtest.js`, override `Scene.prototype.choice` to pick by a scripted substring list, or inject a `stats[k]=v` pass post-intake. Delete the scratch script when done — it's a throwaway, never commit it.
* **Harness setup requirements** for any fresh harness: make `saveCookie` fire its callback immediately (not deferred), and set `global.safeTimeout = function(fn) { safeCall(null, fn); };` before loading `mygame.js` — otherwise a fresh Scene's first `execute()` silently reads as "no content" instead of a real parse error.
* **`refresh_fuzz_test.js` has a blind spot at a pause point reached through `*gosub_scene`** (any fight): reconstructing a bare Scene there doesn't rebuild `choice_subscene_stack`, so a simulated `*return` runs off the end instead of re-pausing (`[shadow-no-pause]`, not a confirmed bug). To actually verify refresh-safety at such a point, simulate a real cold refresh instead: capture `choice_page_start_scene`/`_line`/`_indent` at the pause, construct a fresh Scene there with fresh temps, execute, confirm it re-pauses identically.

## 5. Reusable Small-Combat Engine (`startup.txt` primitives + `resolve_*`)
* **For a short, contained skirmish, reuse the combat primitives in `startup.txt` rather than hand-rolling a new one per fight.**
  * **The player's own attack roll needs zero new code** — just `roll_d20_check` with `check_dc` = `combat_enemy_ac`. Set `check_add_prof_bonus true` before a weapon attack or attack-roll cantrip (always proficient with an equipped weapon/known spell). A save-based spell (Vicious Mockery, Dissonant Whispers) never calls `roll_d20_check` — the target saves against `spell_save_dc`.
  * **General skill checks (in or out of combat) go through `roll_skill_check`, not a hand-set `check_stat`/`check_skill` pair.** `*gosub_scene startup roll_skill_check <DC> "<skill1>" "<override1>" "<skill2>" "<override2>" "<skill3>" "<override3>"` — always 7 args, an empty slot is `""`. Takes the best of up to three skills, rolls once, and reads real per-skill proficiency. Composes correctly with Rogue Expertise. A grounded repair or simple-mechanism task sets `check_task_type "repair"` before this call and offers Investigation, Sleight of Hand, or both; the shared engine then adds the carried Repair Kit's +1 automatically.
    * **A non-empty ability override forces that ability for a skill** while still reading its own proficiency/display name — for a check this campaign lets resolve through more than one ability (e.g. Intimidation via STR or CHA). Offer the skill twice, once per ability, rather than inventing a new skill id.
    * **Skill proficiency is granted in three fixed layers inside `update_dnd_stats`** (`apply_background_skills`, `apply_class_skills`, `apply_race_skills`) — no player choice, by design. Double-granting from two layers is harmless.
  * **`resolve_player_hit`/`resolve_player_weapon_hit`** — call after `check_success`. Applies to `combat_enemy_hp` (floored at 0), self-locked. The weapon variant also resolves Sneak Attack.
  * **`resolve_enemy_attack`** — rolls the enemy's attack against `armor_class`, applies damage on a hit (halved raging, floored at 1). Self-locked. Reads the fight's own atk/damage fields plus the caller-managed `_disadvantage`/`_advantage` flags (both true cancels per normal rules).
  * **`combat_roll_initiative` (called once from `fight_setup`) needs a whole-body self-lock too, for the same reason as the attack callers above.** `fight_setup` → `combat_roll_initiative` → `combat_begin_round` → `announce_turn_order` → straight into `combat_next_turn`'s own dispatch of everyone who acts before the player all happen on ONE page (fight entry to the first real pause, however many turns deep a surprise round goes) — a refresh replays from the fight's own entry point and rerolls every combatant's initiative from scratch, producing a different turn order and a cascade of different attackers/targets/damage. Structurally it already only ever runs once per fight in normal play, so the lock is never even consulted again once the fight moves past its first page — harmless, not a new per-round cost.
  * **A whole targeted-attack CALLER (`resolve_weapon_attack_choice`, the inline Dissonant Whispers/Vicious Mockery/Fire Bolt/Ray of Frost/Shocking Grasp/Eldritch Blast/Chill Touch `*choice` options) needs its OWN outer self-lock around the full sequence, not just around the roll/damage primitives it calls.** `fight_pick_target`'s kill-priority scan is deliberately left unlocked (it has to pick up a HUD click made after the page rendered) — replayed on the same page after this same attack already killed its target, it silently re-derives the next-lowest-HP LIVING slot instead, and `check_dc`/the flavor-text pick/a one-shot mark (Favored Foe) all ride along with the swap even though `roll_d20_check`/`resolve_player_weapon_hit`/`resolve_player_hit`/`resolve_enemy_save` individually replay correctly. Wrap `fight_pick_target` → flavor pick → roll → damage → any one-shot mark in one outer `X_locked`/`locked_X_page_id` guard; leave the branch-and-print tail after it unconditional (reading only the now-settled persisted stats), so a real refresh still reprints the page. The five attack-roll cantrips share ONE lock (`combat_cantrip_choice_locked`) with each other and with Vicious Mockery — safe because all six cost the same ACTION and so are mutually exclusive within any one page, the same assumption `resolve_player_hit`'s own single shared lock already makes for the same five/six callers. **A call site that piggybacks on this same click** (equip_weapon's sidearm-swap ahead of "Attack with your sidearm") needs the SAME lock too, not a new one — it's part of the same one-shot action, and left unguarded a replay re-swaps weapon↔sidearm a second time, reversing it back to the pre-swap loadout.
  * **The whole one-time fight-SETUP phase (ability-score rolls, their derived combat bonuses, a fight's own random enemy-type pick) shares `combat_roll_initiative`'s own lock (`combat_init_locked`/`locked_combat_init_page_id`), not a lock of its own per call.** `apply_ability_score_range`, `apply_derived_combat_bonuses`, and a hand-authored fight's own setup-time `*rand` (`fight_dredge_ambush`'s random bruiser weapon) all run only once per fight, always BEFORE `combat_roll_initiative` sets that lock true within the same `fight_setup` call, on the same first page — so checking the same flag correctly says "should run" on the real pass and "already ran" on any same-page replay, for all of them, with no separate bookkeeping. `apply_derived_combat_bonuses` needs the lock even though it looks like a pure recompute from already-stable ability scores — it writes through the SHARED `sm_mod`/`sm_mod_str` scratch (`score_to_mod`), so re-running it on a replay isn't free of side effects just because the inputs are stable. **A value copied out of a locked block for a caller to read later must be captured INSIDE the lock, at the moment it's decided — never as a separate unconditional line after the guard closes.** The value it's copied from can be a transient, CONSUMED field (a `*gosub`'s own working scratch, cleared once read) rather than something durable — a locked replay that skips the roll leaves that scratch holding whatever it was reset to by the END of the ORIGINAL run, not what was actually rolled, so a copy taken outside the lock silently captures the wrong (often blank) value even though the roll itself replayed correctly.
  * **A per-round mutation (round counter, action-menu choice) still needs the standard replay lock** — reset to a fixed literal at the fight's true start, increment only where a genuinely new page cycle begins.
  * **A reaction spell (Shield, etc.) doesn't need a new pause point.** An "arm it" option sets a persistent flag and loops back to the round hub at no cost; the relevant primitive checks the flag and auto-fires/disarms itself. **Hellish Rebuke follows it:** armed free from the hub, it fires inside `resolve_enemy_attack` right after a hit's damage, spends a slot and `player_oa_used` (the round's one reaction), and keeps its roll and banner in `combat_rebuke_*` so the attack narration prints them in order.
  * **A flag set before a `*gosub_scene` can get cleared by the call it's feeding.** `roll_d20_check` resets `advantage`/`disadvantage` before returning, so read its own output (`roll_had_advantage`) instead of a caller-managed copy of "was this true going in."
  * **A spell with a genuinely unusual damage shape** (always-hits, no attack roll) is often clearer as its own small inline block than forced through `resolve_player_hit`. Don't generalize the primitive for a one-off.
  * **Audit a dormant "built for later" subroutine for a replay lock before giving it its first real caller** — an unlocked subroutine's bug can hide simply because nothing has exercised it yet.
  * **A resource-spending spell that reports one computed number doesn't need its own output variable** if it can share one (`combat_cast_result`); buff casts that can never be chosen the same round can share one lock too.
* **A Spell With a Duration in Hours, Castable Outside a Fight, Is a Minutes-Left Counter Plus One Shared Routine.** Mage Armor (24 hours) and False Life (12 hours) are `mage_armor_minutes_left`/`false_life_minutes_left`, counted down by `advance_time`, with the expiry applying its own recompute or removal. Each has a `*_cast_check` that reports its cost and its refusal reason through `*create`d globals (a `*temp` does not cross a `*gosub_scene`) and a `cast_*` routine with its own per-page lock; the fight's option, the dossier Cast menu and the sidebar spellbook's one-shot label (`codex_cast_now_<spell>`, which ends with `*finish` and reports through `spell_cast_toast`) all call that one routine. A free version (an invocation such as Armor of Shadows) is the same routine with cost `free`. Adding another is a check routine, a cast routine, a countdown line, a one-shot label, and an entry in `CASTABLE_OUT_OF_COMBAT` in `index.html`.
  * **An ongoing damage-rider (Hex's +1d6) belongs inside the damage-dealing primitive itself, gated on an explicit "was this an attack roll" flag the caller passes in** — never applied unconditionally inside a shared primitive, since a rider correct for some callers isn't safe to assume for all (Hex fires on an attack-roll hit, never on a failed save).
  * **Temporary hit points need their own pool (`temp_hp`), separate from `hp_current`, absorbed first on a hit.**
  * **Bonus-action spells loop back to the round hub free; full-action spells consume the round.** (Second Wind/Rage deliberately consume the round despite being bonus actions in 5e — a tested tradeoff, not an oversight.)
  * **Attack cantrips need their own bespoke `*choice` option each** — never a single generic "cast a cantrip" option reading back a detected name/stat, which breaks per-cantrip flavor text and makes a second attack cantrip on the same build unreachable behind an `*else` chain.
  * **Where a cantrip/spell's RAW secondary effect maps cleanly onto an existing engine flag, wire it in** — check the dossier's ability-card text for what's already promised first. Don't force a translation that doesn't fit; a vivid, distinct description already satisfies the prose rule on its own.
  * **Every hit/miss line needs real variety** (3+ randomized phrasings that vary the actual physical action, not just adjectives), and a killing blow needs its own distinct text and banner, checked immediately after every damage source. Death-blow lines are deliberately generic/enemy-agnostic — a full per-fight, per-damage-type finisher set isn't worth the writing cost.
  * **A rider that depends on a per-enemy trait (not just hit/miss) gets its own per-slot tag on the enemy**, following the `combat_enemy_epithet`-style per-slot field pattern.

## 6. Combat as a Standalone Scene File (`combat.txt`) — Fight Library Pattern
* **`combat_prose.txt` holds every static narration pool `combat.txt` selects from** — weapon hit/miss/finishing-blow text, enemy type flavor, spell flavor, and the narration selector labels. Reached with `*gosub_scene combat_prose <label>`, never a bare `*gosub` (ChoiceScript can't gosub across files). It's a `*gosub_scene`-only library scene: not in `*scene_list`, named to `compile.js` via its own `verifyFileName("combat_prose.txt")` line. `*temp` does not cross a `*gosub_scene` file boundary — a scratch variable shared between the two files must be a real `*create`d global in `startup.txt`, not `*temp`.
* **The round-by-round combat loop lives once in `combat.txt`**, entered via `*gosub_scene combat fight_<name>`. It returns `combat_outcome` (`"victory"`/`"rescued"`/`"fled"`) and prints no start/end-of-fight prose itself — the caller owns the narrative reaction.
* **A new fight costs one short `fight_<name>` entry label** — enemy stats and a few flavor strings, then `*gosub fight_setup` / `*goto fight_round_hub`. Everything else is already shared.
* **Most ability-casting flavor is enemy-agnostic and belongs directly in the shared `fight_round_hub`, not parametrized per fight** — Hex, Agathys, False Life, Healing Word, Magic Missile, Shield, Second Wind and Rage all describe the player's own casting motion, not the creature. What varies by foe comes from the enemy type library and the damage-type-keyed labels, so a fight normally sets no `combat_flavor_*` at all.
* **Reusing the same enemy across two quests just means two scenes calling the same `fight_<name>` label** — `*gosub_scene`'s return address is dynamic. For a distinct feel, set per-slot flavor overrides rather than copying the label.
* **Up to `combat_enemy_slot_cap` (6) simultaneous enemies are supported, and a single-enemy fight needs zero changes.** Slot 1 is the original bare `combat_enemy_*` names; `fight_setup` snapshots them into `combat_enemy1_*` automatically. Every damage/attack primitive stays single-target — `fight_sync_target_in`/`_out` mirror the active slot into the canonical names around each primitive call. The player auto-targets the first living slot unless overridden; a dead slot's turn is skipped entirely. Tune per-enemy damage down for a multi-enemy fight, since N attackers roughly multiplies incoming damage by N.
* **Any operation over the numbered enemy-slot pool** (sync, target-pick, death-check, per-slot overrides, type application, narration lookups) is written ONCE as a generic label using `{}` name indirection (`*temp p (("combat_enemy" & slot) & "_")`, then `{(p & "hp")}`) plus a bounded loop — never duplicated per slot. **Sharp edge:** quicktest's line-coverage walk visits an `*if` body's lines even when the guard is false for the current data, so an indirected read/write inside any `*if` body must resolve to a variable that exists for every slot value the walk might leave in place — give a slot-1-only field an inert numbered placeholder rather than trying to guard the read.
* **The ally pool (`combat_ally1_*`–`_4_*`) has real turn-taking AI via a type library mirroring `apply_enemy_type`** (types set via `combat_ally_lib_N` before `fight_library`). A ranged ally attacks every turn (no range penalty modeled); a melee ally tracks its own `combat_ally<N>_range` independently of the player's own distance and closes one tier per turn before attacking. **There is no real per-pair position model — one shared depth axis per combatant, not coordinates.** A combatant's own `_range` (or `_chase_range` while an active chase has frozen the plain field) is honest as "how far this thing is from where it's headed" and nothing more — it is NOT itself "distance from the player" for an ally, since an ally's target is frequently not the player's. **Deriving distance-to-player (2026-09-30, on request) uses a real, if approximate, geometric relationship rather than reusing the ally's own range directly:** `combat_enemy<T>_range` is tracked per enemy SLOT, independent of which enemy the player personally has selected, so the player's own distance to whichever enemy T an ally is fighting is always available — treating player and ally as closing on enemy T from the same general direction (the same one-shared-axis assumption the rest of this system already leans on), `|distance(player, T) - distance(ally, T)|` is the honest estimate of `distance(player, ally)`. Read the absolute difference, never a floored subtraction — an ally sniping a target the player has since closed on and engaged is still far from the player, not "basically adjacent," and only `abs` gets that right. See `allyDistanceToPlayer` (`index.html`). A `${}` token inside a string resolves immediately at the `*set` that assigns it, never later when printed — build narration text inline after the epithets are synced, don't pre-store it as a named constant. Always drive a combat test through a real caller scene, never a bare `scene=combat label=fight_<name>` jump — the fight's exit `*return` expects a call frame the bare jump never pushed.
* **The Sidebar's `effectiveRange`/`allyDistanceToPlayer`/`combatantSubLine` (`index.html`) Are the One Place This Distance Math Happens, and Any Future Reader (a Spell/Bow Range Check Included) Should Reuse Them, Not Re-Derive.** `combat_ally<N>_range`/`combat_enemy<N>_range` freeze the instant a commit-and-chase starts (deliberately, so breaking off needs no reset — see `combat_enemy1_chase_target`'s comment in `startup.txt`); `_chase_range` is the live number for that whole span instead, and `effectiveRange(s, kind, slot)` picks whichever is current — an enemy's own `effectiveRange` output IS its distance to the player, no further derivation needed. `allyDistanceToPlayer(s, slot)` derives the ally-specific number (see the bullet above) and falls back to the ally's own `effectiveRange` before it has picked a target this fight, the only case with nothing yet to difference against. `combatantSubLine(s, kind, slot)` shows "chasing `<X>`" over the ordinary "fighting `<X>`"/blank line whenever a chase is active on either side, with the combatant's own distance-to-target tier riding along in parentheses. The one exception: the "In your reach" alert (engaged with the PLAYER specifically) deliberately reads plain `_range`, never the chase-aware value — a chasing combatant was never engaged with its default target when it committed (commit-and-chase only fires for someone not already engaged), so plain `_range` already correctly excludes it, and swapping in `_chase_range` there would wrongly describe distance to its quarry as distance to you.
* **"Fall Back" mirrors "Push Forward" exactly** (same cost, same range-tier cap, no Attack of Opportunity in isolation) — retreating one tier without ending the fight, distinct from "Break off and run" which ends the encounter outright.
* **Interception (`find_intercepting_ally`) lets an ally at range 0 draw an enemy's attack instead of the player** — a shared adjacency bucket, not a real per-pair distance. Mechanism A: any living ally at range 0 is a legal target regardless of weapon type (melee or ranged both qualify), picking the lowest-HP eligible one to spread aggro rather than let it dogpile one. Mechanism B (only when A finds nobody, and only for a ranged acting enemy): snipes a living ranged-classified ally instead, wherever she is — no range check. `combat_ally<N>_target` is display-only for this purpose, not a real adjacency test. `resolve_enemy_attack_on_ally` is a separate, smaller label from `resolve_enemy_attack` (which carries player-only machinery — Shield, Agathys, temp HP, conditions — that doesn't apply to an ally target). **`combat_intercepting_ally > 0` does not mean "a melee ally is adjacent"** — Mechanism A admits a ranged ally too, so code that specifically needs a melee ally present (e.g. gating a cornered ranged combatant's own retreat, which only pays off if a melee ally exists to become the thing a future chase gets redirected onto) needs its own dedicated scan, not a reuse of this value.
* **Enemy `_disadvantage`/`_advantage` are per-slot (like Bane), consumed on that enemy's own next attack roll** — never cleared at round-start, since a melee enemy can take multiple rounds to close before it ever attacks. Pre-fight ambush advantage is a different lifecycle: the bare flag is a "pending" value `apply_enemy_type` copies onto every slot as it's built, so ambush call sites need no changes.
* **Enemy ability scores (`combat_enemy1_strength`–`_charisma`, default 10) exist for initiative and future saves/stat-modifying spells.** `score_to_mod` (real `floor((score-10)/2)`, uncapped) is the only place this formula should be computed — never hand-copy the ladder. Manual per-slot override follows the hp/ac/atk_override pattern (sentinel `0`, since 0 is never a legal ability score); otherwise `apply_ability_score_range` rolls within the type's own default range. Opt-in — `fight_cleanup` resets scores to 10 and overrides to 0 every fight.
* **The turn queue dispatches one combatant at a time (`combat_next_turn`), not an always-player-first batch** — an enemy that wins initiative genuinely attacks before the player's first choice. `fight_setup` can't `*goto` away from itself (it's reached via `*gosub`) to redirect to the dispatcher on the fight's first entry — it sets a flag (`combat_turn_needs_advance`) that `fight_round_hub`'s preamble checks and clears instead, so every existing `fight_<name>` entry label needs zero changes.
* **Target selection is a JS panel reusing `combat_player_chosen_target`, living inside the existing `#statSidebar`, not a separate panel.** A click writes the stat directly with no ChoiceScript round-trip; clicking the already-chosen enemy clears it (the game goes back to its own pick), and a pick is otherwise sticky until that slot dies. `fight_pick_target` prefers it over auto-pick whenever it is a living slot. A click does NOT rebuild the hub list already on screen, so anything that depends on the chosen target must be checked again when the option is chosen, not only when the page is built (next bullet). Below 1100px the sidebar is hidden: the fight is then not broken, just unadjustable.
* **Melee Reach Is One Flag, Offered by the Hub and Re-Checked When the Option Is Chosen.** `combat_melee_reach` (computed in the hub before the `*choice`) is true when a selected target is in reach or when ANY living enemy is at range 0; the melee weapon options and Shocking Grasp gate on it, and `combat_reach_epithet` names who will be hit. A selected (clicked) target only decides things while it is itself in reach: it is sticky until it dies, so a far enemy clicked for a spell used to hide every melee option even with two enemies Engaged (found 2026-10-02 from a player log), and now an out-of-reach click is ignored for melee. When chosen, `fight_reach_check` fails only when NOTHING living is in reach (a line, back to the hub, no action spent), and `fight_retarget_to_reach` redirects a swing whose target (default or clicked) is out of reach onto the lowest-HP enemy in reach; the click stays sticky for spells. A new touch-range option uses the same three pieces.
* **Any hand-authored sidebar/panel CSS or JS change belongs in `web/mygame/index.html`** (or its split-out panel files — `inventory.js`, `trade.js`, `equipment-panel.js`, `levelup.js`), never in the compiled `play_game.html`/`output.html` — `compile.js` only reads from source and silently discards a hand-edit made directly to the compiled file. Confirm a change survived by grepping a freshly recompiled output. The newer UI files follow the same rule (`battlehud.js/css`, `shell.js/css`, `theme.css`). `uiart.css`, `action-icons.js` and `spell-icons.js` are GENERATED (`tools/gen_ui_art.js`, `gen_action_icons.js`, `gen_spell_icons.js`, each with `--check`): edit their source tables, never the output. `compile.js` only inlines a stylesheet whose file name has no hyphen (a hyphenated `<link href>` is silently skipped), so name a new one like `battlehud.css`.
* **`fight_pick_target`'s fallback is kill-priority (lowest-HP living slot), not front-to-back** — the same fallback the player's HUD-less auto-target and every ally's turn both use, so allies focus-fire the most-wounded enemy with no ally-specific code.
* **Movement is a separate free budget from the action.** `combat_player_moves_left`/`_max` (same replay-locked spend/grant shape as actions/bonus, refilled every round) is spent by Push Forward/Fall Back to open/close one range tier; Dash costs the action and grants a second move point rather than moving itself. Enemy/ally closing takes a free tier and, if still out of range, a second (Dash-equivalent) tier for free, attacking that turn only if the free tier alone was enough.
* **Movement targets the nearest eligible enemy, direction-aware (`fight_pick_nearest_target`)** — a different rule from attacks' kill-priority target, since distance is the point of movement. It writes only `combat_active_target`, never the attack path's bare scratch, so a movement pick can't corrupt the next attack's target; the `*else` that clears a stale HUD click must be bound to the liveness test, not the eligibility test, or an alive-but-ineligible click gets wrongly dropped. Movement availability (`combat_can_push_forward`/`_fall_back`) is computed by its own dedicated scan across every living enemy — never reused from `combat_enemy_range`, which tracks the kill-priority target and can silently be the wrong enemy.
* **One movement action shifts every living enemy's range tier at once (`combat_shift_all_ranges`)** — stepping toward one enemy in a group is a step toward all of them. It doesn't re-sync the narrated/active-target scratch itself; the caller does that once, via `fight_pick_nearest_target`'s own choice, after the shift.
* **A movement button that previews its own from/to tier pair needs a dedicated read-only computation** — never a preview call to `fight_pick_nearest_target` itself, since that label mutates state as a side effect of actually picking. The preview must mirror "chosen-target precedence" exactly (a live, eligible chosen target skips the nearest-scan entirely) or it mislabels the button.
* **A ranged attack against a creature at range 0 has disadvantage** — a deliberate 2024-rules house rule adopted into this 2014-rules game, since otherwise a ranged enemy that never closes and suffers no range penalty is unanswerable, and a melee ally has no way to suppress an archer. A `*temp` OR'd in at roll time, never a write to the condition-based `combat_enemy_disadvantage` flag (which is consumed elsewhere and would silently eat a debuff still owed). Known limit: doesn't cover `resolve_enemy_attack_on_ally` — a ranged enemy attacking an engaged ally gets no penalty, since there's no enemy-to-ally distance model.
* **Opportunity attacks trigger when a creature leaves melee range.** `find_opportunity_attacker` returns at most one enemy per move (lowest-HP engaged), and each enemy gets at most one per round (`combat_enemy<N>_oa_used`) — both caps are deliberate departures from RAW, since one movement action shifts every enemy at once and this engine has no player reaction budget to answer a full volley. Eligibility requires living, melee, range 0, and not yet used this round; the candidate must be captured BEFORE the tier opens, since range 1 alone can't distinguish "just left melee" from "was never in melee." Resolves through the normal attack/narration path whole (Shield, resist/vuln, conditions all still apply). "Disengage" is a universal action (no Battle Master maneuver system exists) that suppresses the player's own opportunity-attack exposure for the round; a plain retreat is not suppressed by it and still provokes.
* **Combat choice labels are `[b][ACTION][/b] [b][Name][/b] <prose>`, capped at 15 rendered words, enforced by `tools/lint_choice_labels.js`.** Cost is unconditional, bolded, and first; both bracket runs sit inside the bold span (unbolded brackets collide visually with the following text). The lint derives cost from the option body (what it spends), not a hardcoded list, so a new action-spending option is caught automatically. Reject em/en dashes in button text. The consumable-item buttons are generated (`gen_gear.js`'s `useLabel`) — a hand-edit to their text in `combat.txt` is silently overwritten by the next generator run. **The Battle HUD (`battlehud.js`) reads these labels to group and draw the hub options** (the cost tag, then the bold name; a bare `[Name]` is a free option; movement and the rest by their opening words), so the label format is load-bearing: a reworded cost tag or name changes where an option lands on the bar. The weapon-attack slots are matched on the `weapon`/`sidearm` stats, not on the label text.
* **Dodge (RAW: +5 AC for the turn, can't move) is the game's action-costing defensive option.** Its "can't move" half is enforced through one shared `combat_can_move` flag every movement option tests, rather than four separately-edited gates. The +5 lives in a durable `dodge_active` flag, never written onto `armor_class` — equipment's own AC recalc must never absorb a spell effect. Build any AC-modifying banner from one shared DC value the hit check, Shield's re-check, and the printed banner all read, so the three can't disagree.
* **Leveled spell damage adds the caster's spellcasting ability modifier via one durable `spell_damage_mod`** (set in `update_dnd_stats` from the same casting-ability table as `spell_save_dc`, deliberately adjacent so the two can't drift on which ability a class casts from) — cantrips never add it (RAW fixed damage; hardcode `combat_player_dmg_bonus 0`). Magic Missile is the RAW exception even among leveled spells: its +1-per-dart is flat and caster-independent (no attack roll exists for a modifier to apply to), so it uses a literal `3`, never `spell_damage_mod`. Dissonant Whispers applies the modifier before halving on a successful save.
* **Magic Missile's multi-target dart allocation is armed via a separate `*choice` screen (`fight_target_magic_missile`)** rather than resolving immediately — sidebar clicks while armed call `assignMultiTargetDart(slot)` directly (pure JS, no ChoiceScript round-trip) instead of the single-target chosen-target write. The Cast option's own body re-sums the per-slot dart counts fresh at the moment it's chosen, since a `*choice`'s own `*if` guard is evaluated once at page-build and would go stale after a live sidebar click. Damage is summed per target (not dart-by-dart) before resistance/vulnerability and the HP subtraction. Both arming and Cancel must clear every slot's dart count back to 0.
* **Every combat-prose narration label that runs mid-sequence must end with its own trailing `*line_break`** — nothing in this engine supplies a leading one, so two labels' output otherwise runs together on one line. This applies uniformly to narration labels and to every player-facing hub option whose own Miss/Hit/no-banner branch is the last thing printed before the hub redisplays. A trailing break added only after a branching `*if` block does nothing for a branch that exits early via its own `*goto` — the break must sit inside each branch that actually falls through.
* **`$!{var}` (capitalized) is required at the start of any narration sentence that opens on an epithet variable** — `${var}` (lowercase) is correct only mid-sentence, since an epithet defaults to a lowercase phrase ("the swordsman"). Check any new combat-prose pool for this.
* **`combat_attacker_name`/`_epithet` and `combat_defender_name`/`_epithet` are shared scratch, overwritten as a side effect of `fight_narrate_ally_attack`/`fight_narrate_enemy_turn` narrating whoever THEY were just called for — not durable, not scoped to one caller.** Code that sets these itself for its own inline narration (a retreat/movement line, say) and reads them again after an intervening `*gosub`/`*gosub_scene` to either label for a DIFFERENT attacker/defender pair (a reactive opportunity attack resolved mid-turn, an interception) will silently print the intervening call's names instead of its own. Re-set both, fresh, immediately before the second read — don't assume a value set earlier in the same turn survives any narration call in between.
* **Any scene-file edit meant to reach `play_game.html` needs `node compile.js` before it's actually tested** — `quicktest`/`lint_all`/`scripted_play.js` all read the raw `.txt` source directly and will pass against a fix that never made it into the compiled build.
* **A `*gosub_scene`-only library scene (`combat.txt`, `equipment.txt`, `death.txt`) must NOT be added to `*scene_list`** (list order builds the implicit `*finish`-continues-into-next-scene chain) — but it still has to be named to `compile.js` via its own `verifyFileName(...)` line, or it's silently dropped from the compiled build with no error at compile time. `quicktest`/`randomtest`/`refresh_fuzz_test` read scenes straight off disk and can't catch this class of bug — check the actual compiled output. `death.txt` is reached only via a bare `*goto_scene` (nothing to return to), never `*gosub_scene`.
* **A Weapon's Damage Die Comes From `weapon_type`, and Two-Handedness Comes From `weapon_hands`, a Separate Field.** A two-handed melee weapon needs only `hands: "two_handed"`, never a `weapon_type` variant.
* **`combat_engaged` Is True From `fight_setup` Until `fight_cleanup`.** The dossier's satchel and inventory Use button refuse while it's true. Any new fight exit must go through `fight_cleanup`, or the flag sticks.
* **A Night-Danger Encounter Is an Arrival Hook With Non-Combat Exits** (pay a toll, fight, slip away on a check, turn back) — never a forced fight, per the Dredge-End ambush pattern.
* **Combat Lethality Is Opt-In Per Fight, Default Off.** `combat_player_can_die` (default `false`) gates whether a hit floors `hp_current` at 1 or lets it reach 0. Every `*gosub_scene combat fight_<name>` call site must check for a `"player_died"` outcome alongside victory/rescued/fled, even for fights that are non-lethal today — an unguarded call site silently falls through to the caller's fallback branch instead of ending the game the moment that one fight's flag is later flipped.
* **Conditions Inflicted on the PLAYER (Frightened/Poisoned/Stunned on a hit) Are Opt-In Per Fight and Single-Round Only, By Design** — this engine has no way to cleanse a condition on the player early, so don't chain stun sources or extend either past one round. Every enemy is unaffected by default. **Conditions the player inflicts on an ENEMY (Slowed from Ray of Frost, Frightened from Cause Fear) are different: a per-slot rounds-left counter (`combat_enemy<N>_slowed`/`_frightened`), ticked at that enemy's own end of turn, with a repeat save through `resolve_enemy_save` where the spell allows one, and shown on the sidebar hover card (`CONDITION_KEYS` in `index.html`).** A new enemy condition is the counter, its effect where the enemy acts (`combat_next_turn`/`resolve_enemy_attack`), its end-of-turn tick, a `fight_cleanup` reset, and a `CONDITION_KEYS` entry. `resolve_enemy_save` clears its per-slot "already rolled" flags whenever the page changes; without that, a repeat cast reuses the last roll.
* **Condition/Stun/Movepool Fields Reset in `fight_cleanup`, Never `fight_setup`** — resetting in `fight_setup` would wipe the values the calling `fight_<name>` label just set one line earlier.
* **Enemy Movepool (`combat_enemy_move2_chance`, 0–100) Gives One Enemy a Second Attack Without a New Engine Concept** — 0 means never. A movepool enemy's move 2 owns the condition-infliction scratch flag once active; give the condition to move 2 explicitly rather than the base move.
* **The Enemy Type Library (`apply_enemy_type`) Drops a Reusable Stat Block/Movepool/Flavor Set Into Any of 3 Slots.** A scene sets `combat_lib_1/2/3` to type ids and calls `fight_library`, optionally overriding hp/ac/atk per slot (sentinel `999` = not set) and name/epithet per slot. A type is a weapon, not a person (`swordsman`, `axeman`, `archer`, `beast`, etc.) — turn a generic type into a specific foe via the override fields. Add a new type with an `apply_type_<name>` label, one dispatch line, one `flavor_from_type` line, and a `flavor_type_<name>` prose label.
  * **Every enemy line uses `$!{combat_enemy_epithet}` at a sentence start and `${combat_enemy_epithet}` mid-sentence** — a scene renames a fighter purely by overriding the epithet/name, never by editing the library's lines.
  * **Shared type and player-strike lines must stay place-free, gear-free and pronoun-free** (singular "they," never he/she/it), so any fight against human combatants can reuse them unchanged — no ground, weather, or worn-gear reference. Each line names one physical action and its cost. A creature's lines assume only a generic body, never creature-specific detail that breaks on a different type. Finishing-blow lines are keyed by damage type, not weapon, so an axe/spear/dagger/staff all read as slashing/piercing/bludgeoning.
  * **A condition rider should match its weapon** (poison on a knife, not a club).
  * **A new bare `combat_enemy_*` field needs a line in `fight_setup`'s slot-1 snapshot too, not just the type's own `*if (combat_apply_slot = 1)` branch.** Slot 2+ writes straight to its real `combat_enemyN_*` storage via the `apt_p` indirection, but slot 1's block only ever sets the BARE scratch name — `fight_setup` is the separate step that copies bare into `combat_enemy1_*` afterward, and it lists every field by hand (hp, ac, atk_bonus, weapon_type, range, …). Forgetting the new field there leaves `combat_enemy1_<field>` stuck at its `*create` default forever, silently working for slot 2+ and silently dead for slot 1 — caught here only by a live `scripted_play.js` run against a slot-1 fixture, not by `quicktest`/lint (the field is real and reachable, just never populated). The sidearm fields (`combat_enemy<N>_sidearm_*`, Ranged-AI Position Awareness plan §4.1) hit exactly this the first time: `apply_type_archer`'s slot-1 branch set the bare names correctly, but `fight_setup` never copied them, so a cornered slot-1 archer kept shooting at disadvantage until the snapshot line was added. **It recurred twice more in the same plan** — `combat_enemy_chase_chance` (Phase 4's per-type tunability retrofit) hit it live again (a slot-1 swordsman silently never chased until the missing line was found and added), and `combat_enemy_can_retreat` (Phase 5) would have hit it a third time had the pattern not been recognized *while writing the field*, not after a test caught it. Treat this as a standing checklist item, not a one-off lesson: **any new field a slot-1 `apply_type_*` branch sets needs its `fight_setup` snapshot line added in the same edit that creates the field**, before the first test run, not after one fails.
* **A ranged type's cornered fallback is a transient scratch override, not a second persistent weapon.** `combat_next_turn`'s row-2 quick-draw (Ranged-AI Position Awareness plan, `quest/RANGED_AI_PLAN.md`) overwrites only the active-target SCRATCH fields (`combat_enemy_weapon_type`/`_atk_bonus`/`_dmg_*`) that `fight_sync_target_in` just populated for that one `resolve_enemy_attack` call, from a per-type `combat_enemy<N>_sidearm_*` set (`""` weapon_type = no sidearm, the default for every melee type). The slot's own durable fields are never touched, so the type is back to its primary weapon next turn with no restore step — the same shape Bane and per-turn conditions already use. `combat_enemy_move2_chance` must be zeroed alongside it (the special move belongs to the primary weapon only), and `fight_narrate_enemy_turn` picks the dagger prose pool by redirecting the local TYPE-ID temp (`fnet_type` → `"<type>_dagger"`) for that one call, never the slot's own persistent `flavor_type` field, or the type would "become" a dagger-wielder forever.
* **A Field That Nothing Reads Yet Is Not Safe to Start Reading Without Checking What It Defaults To.** `resolve_ally_attack` gained the same ranged-at-close-range disadvantage `resolve_enemy_attack` already had (Ranged-AI Position Awareness plan §4.4, `combat_ally<N>_range <= 0`), and the field it reads had *always* defaulted to 0 with nothing to stop it — no fixture or real fight had ever needed to set an ally's range before, since `resolve_ally_attack` fires regardless of it. The enemy side never has this problem because every real ranged-enemy fight explicitly opens its archer/slinger at Close (`fight_wreckers`, `fight_shroud_thieves`, `fight_dredge_ambush` all set `combat_enemy2_range 1`) — nobody ever relies on the type-library default. The instant the read started, both Kess fixtures silently regressed to "always cornered," caught only by reading a live `scripted_play.js` transcript before calling the change done. Before gating new behavior on an existing field, check every place that field is currently left unset, not just the places that explicitly set it.
* **To Scripted-`stats`-Inject a Genuinely Wounded (Not Just Low-Max) Enemy or Ally, Bypass the Type Library Entirely — a Plain `stats` Override Gets Overwritten.** `apply_type_<name>`/`apply_allytype_<name>` always fully rewrite `hp`/`max_hp` (and every other field they own) the moment the type applies, so a `stats`-injected `combat_enemy1_hp`/`combat_ally1_hp` is silently clobbered back to the type's own number before the fight ever starts — same reason `combat_enemy_hp_override` can't produce a wounded state either, since it sets `hp` and `max_hp` to the *same* value (a full-health override, never a fraction of a larger max). Set `combat_lib_N`/`combat_ally_lib_N` to `""` instead — `apply_enemy_type`/`apply_ally_type`'s whole `*if (type = "...")` dispatch chain is then a no-op for that slot — and hand-set every field the type would normally have written (name, hp, max_hp, ac, dmg fields, weapon_type, any sidearm/behavior fields) directly via `stats`. Also hand-set any ability score (e.g. `dexterity`) if turn order matters to the scenario, since bypassing the type skips those too, and a slot with a low default may act later than expected.
* **Damage-Type Resistance/Vulnerability Is Real Data (`combat_player_dmg_type`/`combat_enemy_dmg_type`), Not Just Banner Text** — every damage source sets an actual type token matching `weapon_damage_type`'s vocabulary.
* **Resistance/Vulnerability Storage Is Two String Slots Each, Not a Boolean Per Type** (`player_resist_type_1/_2`, `player_vulnerable_type_1/_2`; mirrored per-slot for enemies) — ChoiceScript has no string-contains operator, and two slots covers this game's real scope. The player's slots are persistent character stats, never touched by `fight_cleanup`; an enemy's are per-slot fight scratch, reset by it.
* **`apply_incoming_damage_resist_vuln`/`apply_outgoing_damage_resist_vuln` (`startup.txt`) Are the Only Two Places This Math Happens** — every damage primitive routes through one. Resistance and vulnerability on the same type cancel to normal damage via a single three-way branch, never two sequential halvings/doublings (which double-applies). Barbarian Rage's resistance folds into the incoming check for the same reason. Neither needs its own lock — both only run inside an already-locked hit-resolution block.
  * **Hex's necrotic rider is not split into its own separately-typed damage instance** — resistance/vulnerability resolves against the weapon's own type only, combined with the Hex die.
  * **Use two independent banner-tag vars** (`combat_incoming_dmg_suffix`/`combat_outgoing_dmg_suffix`), never one shared var — a single hit-resolution call can trigger both an enemy's attack and its own retaliation, and a shared var gets silently overwritten before the earlier banner prints it.
  * **A future resistance/vulnerability-granting item follows the same attunement pattern as any other magic bonus (§2).** An always-on racial trait (not item-conditional) is set directly at character creation instead.
* **The Player Has an Action/Bonus-Action Budget Each Round, as Numbers** (`combat_player_actions_left`/`_max`, `_bonus_left`/`_max`), refilled every round by `combat_begin_round`. An action leaves via `fight_action_spent`; a bonus action via `fight_bonus_spent`. Never spend by hand — both spends and the one-off grant helpers are replay-locked. An ongoing effect (Haste) changes the `_max`, not the current value. Extra Attack is not this (more attacks inside one action); reactions are not a budget yet (Shield is an armed flag). `combat_enemy_disadvantage` clears once per round in `combat_begin_round`, not on every hub re-entry, since the hub can reopen mid-round.
* **Turn Order/Initiative Is Rolled Once Per Fight, Not Per Round** (`combat_roll_initiative`, called from `fight_setup`) — 5e's own rule. Candidates are the player plus only the populated ally/enemy slots. Tie-break ladder: higher roll, then higher raw DEX score (not modifier — two different scores can share one modifier), then player > ally > enemy, then ascending slot. Built with a selection sort over persistent (not `*temp`) scratch storage, so `{}`-indirection can target it — explicitly re-clear the "used" flags at the top of every call. `announce_turn_order` (called once from `fight_setup`, before any enemy that wins initiative gets to act) is the only player-visible confirmation the queue exists, printed once per fight since order never changes.

## 7. Scene File Organization (`scenes/` Subfolders)
* **`web/mygame/scenes/` may contain subdirectories** (2026-09-30, e.g. `scenes/port_valen/` holding Port Valen's hub plus its four district files) — a scene name is just a string nothing splits on `/`, so `port_valen/port_valen_dredge_end` is a completely ordinary scene name to the engine, `*goto_scene`/`*gosub_scene`, and `compile.js`'s own file-embedding logic alike. Moving a file is never "just move it," though — every place that names the scene by its old bare string needs the same update: the `*goto_scene`/`*gosub_scene` call sites, its `*scene_list` entry (if it's a chained top-level scene) or its `verifyFileName(...)` line in `compile.js` (if it's a `*gosub_scene`/`*goto_scene`-only library scene, per §6's own note on that pattern), and any tool that hardcodes the scene name as a string — `tools/gear_catalog.json`'s shop `"file"` fields, `tools/lint_thin_places.js`'s entry table, `tools/play_scripts/*.json` fixtures, and any `tools/*.js` default scene argument. Grep the old bare name across the whole repo, not just `web/mygame/scenes/`, before calling a move done.
* **Moving a Scene That's in `*scene_list` Also Needs `web/mygame/mygame.js` Regenerated, Manually, Before the Next `compile.js` Run.** `mygame.js` is a committed build artifact, not gitignored; `compile.js` reads the PREVIOUSLY-COMMITTED copy's `nav._sceneList` first (as one of three sources feeding its file-embedding list — see `verifyFileName` below), *before* it regenerates a fresh one, so a stale entry from before the rename is still in there and `compile.js` throws `Couldn't find file mygame/scenes/<old name>.txt` — even though the fresh `*scene_list` in `startup.txt` is already correct. Fix: `node mygamegenerator.js mygame > web/mygame/mygame.js` once, by hand, right after renaming/moving any scene that's in `*scene_list`, then run `compile.js` normally. A `*gosub_scene`/`*goto_scene`-only library scene (never in `*scene_list`) doesn't hit this — it's found purely through its `verifyFileName(...)` line, which has no stale-artifact dependency.
* **Every Per-File Lint Tool Under `tools/` Collects Its File List Via `tools/lib/collect_scene_files.js` (`collectSceneFiles`/`collectSceneRelativePaths`), Never Its Own `fs.readdirSync(...).filter(...)`.** A flat, non-recursive scan doesn't crash on a subfolder, it just silently never looks inside it — a scene moved into one goes invisible to that tool's coverage with no error at all. Any NEW lint/report tool that walks `scenes/` must use this shared helper from the start; any tool ever found still doing its own flat scan should be fixed the same way, not patched locally. `collectSceneRelativePaths` (not a bare `path.basename`) is required wherever files get indexed by name (`lint_gosub_arity.js`'s label index, `lint_blank_landing.js`'s `*goto_scene` resolver, `refresh_fuzz_test.js`/`tools/check_calendar.js`'s pre-loaded `global.allScenes` map) — a bare basename collides the moment two subfolders ever hold a same-named file, where a relative path (`"port_valen/port_valen_dredge_end.txt"`) never can. A regex matching a `*goto_scene`/`*gosub_scene` line's scene-name argument must allow `/` in that capture group (`[A-Za-z_][\w/]*`, not `[A-Za-z_]\w*`) — the label argument, which follows it, never contains one and keeps its narrower class.
* **The Offline "Upload the ChoiceScript Folder and Play via `file://`" Mode (`Scene.prototype.loadFile`, `web/scene.js`) Has Its Own, Separate Recursive-Walk Fix — It Never Touches `tools/lib/collect_scene_files.js`, Which Is Node-Only (`fs`).** It builds its own file map client-side from the `<input webkitdirectory>` upload's flat `FileList`, filtered by a regex against each `File.webkitRelativePath` (`rootDirTest`, matching anything under the scenes root at any depth, not just a direct sibling of `startup.txt`) and keyed by path relative to that same root (not bare `File.name`) — the same "recurse, and key by relative path, not basename" shape as everywhere else, just expressed against `webkitRelativePath` instead of a real filesystem walk since there is no filesystem here. This path can't be exercised by any Node harness (no DOM, no real `File`/`FileList`); verified instead by simulating the exact `webkitRelativePath` strings through the same regex/slice logic in isolation, confirming a nested path both matches and produces the same key `loadFile`'s own lookup (`this.name + ".txt"`) would ask for.

## 8. Verification & Tooling Discipline (Right-Sized Testing)
* **Run `quicktest` Freely After Any Scene Edit** — cheap, reads live state, and the only tool that catches label/reachability/syntax errors (a dangling `*goto_scene`, a missing `*label`, unbalanced `*if`/`*elseif`). The targeted linters below check prose voice and vocabulary, not structural reachability. Treat a scene-structural edit as incomplete until `quicktest` has run against it.
* **Targeted Linters for Prose/Voice/Vocabulary Concerns:** when auditing a specific plan or scene file for tone, choice formatting, or vocabulary rather than structure, reach for the narrow tool, always passing the target file path: `lint_choices.js` (choice syntax), `lint_prose_tics.js` (voice), `lint_anachronisms.js` (setting vocabulary), `lint_weapon_assumption.js` (weapon neutrality). A markdown design plan isn't a scene file — use these or a plain read-through, not any whole-game tool.
* **Reserve Expensive Fuzzers for Real Integration Sweeps, Not Isolated Edits:** `randomtest` at high iteration counts, `check_coverage` with 1,000 playthroughs, and multi-thousand-run calendar monte-carlo passes are costly and not warranted for a single scene adjustment. Reserve them for full-game release validation or changes that plausibly affect many interacting systems at once.

## 9. Interface Shell, Theme & Panels
* **Every Colour Lives in `theme.css`.** Panels, dialogs, the sidebar, the rail and the HUD read the `--ch-*` chrome tokens (dark stone, bronze and crimson, identical in both themes); the reading page reads `--pg-*`, which is what the two themes change: A, dark stone, the default, and B, parchment. A new interface file uses those tokens and never a raw colour. The theme is the engine's own Background setting (`applyBackground` in `web/ui.js`, stored as `preferredBackground`: "black" is A and "sepia" is B).
* **The Window Does Not Scroll; the Story Does.** `.container` (the engine's page container and its animation copy) is fixed between the rail and the sidebar and `#main` is the only scroller, so the rail, sidebar and HUD never move. The engine used to start every page at the top by itself through window scrolling; `shell.js` now resets `#main` on every page turn by wrapping `clearScreen`. The combat HUD docks under the frame by publishing its height as `--bhud-h`.
* **The Rail Clicks the Real Buttons.** The page's own button row stays in the page (hidden) because the engine and the panels use it; `shell.js` builds the rail outside the containers and clicks each real button by id, looked up fresh every time, and mirrors only state (visibility, the Lorebook badge, "return"). A new header button needs a rail entry in `ITEMS` and nothing else.
* **Anything That Positions From Coordinates Divides by `window.UI_ZOOM`.** The page is zoomed to fit the screen (an inline script in `index.html`, 1x up to 2.4x, 1920x1080 is the design size; the user's TV is 4K). Under that zoom, rects and mouse coordinates are in viewport pixels while `left`/`top` are in zoomed CSS pixels, so a hover card positioned from either must divide its final left/top by the zoom, and every viewport unit in a stylesheet is written `/ var(--z, 1)`. Missing this puts a card off-screen at 4K.
* **The Battle HUD Never Decides a Rule.** It reads the options the combat hub is offering, ticks the matching real radio and submits the real form, so every gate, cost and lock stays in ChoiceScript. It remembers what it has seen this fight so slots hold still and dims one the hub is not offering, with the reason on hover; "Classic list" restores the plain choices. A new hub option appears on the bar by itself, and gets art by one line in `tools/gen_action_icons.js` or `spell-data.js`.
* **The Sidebar Is Built Whole in `renderStatSidebar`** (identity, Today or Turn Order, spellbook, quests, effects), rebuilt every 400ms, so open/closed state of a fold lives in a module flag (`sbOpen`, `spellOpen`), never on the element. Keep the data hooks the click and hover code reads (`.turnRow` with `data-target`/`data-friendly`/`data-combatant`, the `.spellbook` component).
* **A Dialog Needs `dialog#id` to Beat an Inline Stylesheet.** The Save/Load and speech dialogs set their own border in an inline `<style>` that loads after `shell.css`; a plain `#id` rule ties and loses.

* **The Story Frame Is Drawn on `.container::after`, Above the Panel.** The panel behind the text (`.container::before`) runs 30px under the frame, and an element's own border-image paints below a negative-z child, so the container's own frame was covered and its curled corner ornaments were nearly invisible (found 2026-10-02). The container now keeps a transparent border for layout and the frame art is a pointer-events-none `::after` layer at z-index 3. Anything new that must sit under the bars goes on `::before`; anything that must show over it goes on `::after`.
* **The Primary and Sidearm Buttons Show What Is in Hand.** `weaponCard` in `battlehud.js` formats the `weapon_*` / `sidearm_*` variables (description, damage with type, melee/finesse/ranged, hands); a dimmed one says why, with "Out of reach. Advance (free movement) to close in" for a melee weapon, which is the usual first-turn reason now that fights open at Close.

* **Shield Follows 5e: It Fires Once, Then Lasts the Round (2026-10-02).** The wizard's free "arm it" option sets `shield_armed` (the held reaction; a slot is spent only if it fires). Because it is a reaction rather than an action, it remains selectable after Ray of Frost or another action; `combat_can_shield` also keeps the hub from auto-ending before that free choice is made. The first enemy hit that lands while it is armed fires it: it spends the slot and `player_oa_used`, sets `shield_active`, and re-tests that attack at +5 AC. A stale arm is discarded if its slot or reaction was spent elsewhere, so it cannot drive slots negative or coexist with an opportunity attack. `shield_active` then adds +5 to the AC of EVERY attack made against the player until the start of the player's next turn (cleared in the player-turn dispatch of `combat_next_turn`, and by `fight_cleanup`); a hit does not destroy it, and an attack that beats AC+5 simply hits. Both an unused arm and the active effect clear at the start of the player's next turn, requiring a fresh declaration each turn. `armor_class` itself is never written; the hub, the enemy banners and the sidebar show +5 only while an armed Shield still has both resources or `shield_active` is live.

* **The Close-Combat Ranged Penalty Reads ANY Engaged Enemy, Not the Target (2026-10-02).** 5e spoils a ranged attack while a hostile is within 5 feet of the attacker, whoever the shot is aimed at. `combat_check_engaged` (combat.txt) sets `combat_any_engaged` from every living enemy's range, and both penalty sites use it: the generated spell lookup (`tools/gen_spells.js`, edit the generator and run it, never the block) and the ranged-weapon attack in `resolve_weapon_attack_choice` (Close Combat Shooter still removes the weapon penalty). Touch spells and melee weapons are never penalised.

* **The Inventory Is One Window: the Doll on the Left, the Bag as an Icon Grid on the Right (2026-10-02).** `inventory.js` draws twelve doll slots (head, cloak, armor, waist, feet down the left; neck, hands, shield, two rings down the right; primary and sidearm beneath) around the silhouette, and the carried gear as 64px tiles. Everything still goes through `EquipmentEngine`, the same calls the old dropdowns made: `equipTo(bucket, id, ringSlot)` is the one path that puts something on, and it keeps the guards (a slot that is not `swappable` is changed from the dossier; a piece with an ability-score bonus is handed to the dossier's `codex_equip_do` through `equipViaDossier`; and the Hearthstone Talisman's attunement, which changes CON, is handed to `codex_attune_do` through `attuneViaDossier`; both are refused with a notice during a fight). Neck and ring slots are swappable (2026-10-02): both can be taken off (`none` is a bare throat or finger), a ring cannot sit on two fingers (putting it on one takes it off the other), and while the Hearthstone is attuned the neck slot offers only "Break the attunement". Ways to equip: drag a tile onto the slot that takes it (`accepts`: the item's `equip.slot` equals the slot's bucket), double-click it, or select it and press Equip (the last two work on touch, where dragging does not); clicking a slot opens the list of everything that fits it, including "switch back to starting gear". Hover cards are inside the dialog (it is in the top layer) and are positioned from the dialog's padding box, so a new overlay must subtract the frame's border and divide by `window.UI_ZOOM`.
* **Item Pictures Are Keyed by What an Item Is, Not by Item.** `tools/gen_item_icons.js` maps about 65 keys (`w_sword`, `a_chain`, `potion`, `frog_slime`...) to files under `ICONS/Item` and writes `item-icons.js` (`window.ITEM_ICONS`, 72px WebP data URIs, run the generator after editing `MAP`, `--check` verifies it). `inventory.js` chooses the key: `ID_ICON` by item id first, then a keyword match on the weapon, head or armor name, then the slot, then the category, then `misc`, so a new item always shows something. The library's icons with a coloured backdrop are magic items; use the plain ones for ordinary gear. Art made for this game goes in `ICONS/Generic` and is named in `MAP` with a `../Generic/` path (the chalk and the tinderbox were the first). Stand-ins (marked in the generator): belt, neck and scarf, prybar, manacles and bolt, the iron helm, brigandine, the splinter and the generic fallback. Adding an item is one line in `ID_ICON`, and replacing a stand-in is one line in `MAP`.

## 10. Dungeon Engine (`dungeon.txt`)

* **A Dungeon Rolls Its Random Encounters Through One Picker.** `dungeon.txt` (a `*gosub_scene` library, in `compile.js`) holds `dg_run_begin` (clears the run's history, once at the dungeon's mouth), `dg_tide_check` and `dg_pick`. A caller sets `dg_table` (which table) and `dg_call_id` (a string unique to that call site), calls `dg_pick`, and reads `dg_encounter`: an id, or `"none"` when every row is used or weighted 0. The picker only chooses; what an id means (a fight through `fight_library`, a check, a find) is the dungeon's own code, so a new encounter never edits an old room.
* **A Table Is One Label of `*gosub dg_row "id" lowWeight highWeight` Lines.** Add a table by writing a `dg_table_<name>` label and one dispatch line in `dg_run_table`; add a row with one line. A row's weight is its low-tide or high-tide number, and 0 once its id is in the run's history (`dg_pick_1..8`, which is also why a run holds at most eight rolls).
* **Tide Is Derived From `time_period`, Not Stored:** low water Morning through Dusk, high water Night and Pre-Dawn, the rule Dredge-End and the Silt-Gate quest already use. Hours spent in the dungeon go through `advance_time` as always, so the tide turns on its own.
* **The Whole Pick Sits in One Lock Keyed on `page_id` and `dg_call_id`** (`dg_pick_locked`, `locked_dg_pick_page_id`, `locked_dg_pick_id`), because it makes a `*rand` roll and adds to scratch totals. Two picks on one page with no `*choice` between them need different call ids. The `*rand` range is clamped to at least 2 and the roll is clamped back to the total, because Quicktest runs every branch and `*rand` rejects an empty range.
* **Testing:** Developer menu, Scene Select, "Test the Dungeon Encounter Picker" (`dev_dungeon_test_hub`): roll by hand with the history on show, jump the clock to a low-tide or high-tide hour, or sample 100 fresh-run rolls. The weights were proved exact with `tools/scripted_play.js` by forcing the roll to each of 1..total (`rand=(v-0.5)/total`) at both tides: every roll lands on the row the weights say. The sample loop is capped at 100 because 400 iterations of `*goto` plus `*gosub_scene` overflow the engine's call stack.
* **Harvesting Is an Offered Option After a Kill, Run by `dg_harvest`.** The dungeon sets `dg_hv_creature` (`frog`, `centipede`, `viper` or `lacedon`; anything else drops nothing), may read `dg_harvest_info` for the button text (DC, ingredient name), and calls `dg_harvest`: a Survival check, 15 minutes, one ingredient on a pass and two when the total beats the DC by 5. A failure costs the time and the ingredient, and the two venomous creatures nick 1 HP (never below 1). The counter and the nick share `stat_bump_locked`, so a replay changes nothing twice. A new ingredient is one catalog line (counted salvage with `herbalistPiece`), a `*create` of its counter, a dossier line and an `inventory-data.js` entry (the salvage kind's dossier and inventory entries are hand-written), plus a branch in `dg_harvest_info`.
* **A Counted-Salvage Buyer Is a Catalog Buyer Plus a Per-Piece Price.** `herbalist` (Ambrose's Still-Room) buys only counted salvage that carries `herbalistPiece`, whole stacks at once, like the smith and scrap steel; it returns 0 for everything else. The plumbing is `gear_piece_herbalist` in `equipment.txt` (`gear_info`, `gear_unit_value`, `gear_sale_value`) and `unitPrice` in `trade.js`; both sides must agree. The `ambrose_sell` shop in the catalog feeds the plain menu and the trade panel's Sell tab.
* **A Dungeon's Map Lives in Its Own Scene; the Walking Rules Live in `dungeon.txt`.** `port_valen/port_valen_silt_conduits.txt` is the first (8 hallway junctions, 5 rooms, 3 dead-end exits; the header comment has the map and the directions). Each move sets `dg_dest` and `dg_dest_hall` and goes through `dg_step`: 10 minutes through `advance_time`, one step of light, and on a hallway step a 40% encounter roll against `dg_table` (never twice in a row; rooms reset the streak). One lock (`dg_step_locked`, `locked_dg_step_page_id`) covers the whole step. A dungeon's own entry label must set `dg_table`, or the picker has no rows and returns "none".
* **Light Is Per Step and Never Gates the Path.** `dg_light_prompt` offers a torch (6 steps, about an hour) or the lantern with a flask of lamp oil (24 steps) and "go on in the dark". It is asked at the mouth and when the light dies, and skipped for a player who `sees_in_dark`, is already lit, or has nothing to light (a torch or flask is used up with `sell_gear`, which just removes one copy). Dark means disadvantage on every d20 roll (a block in `roll_d20_check`, worked out from the run's own state so it cannot go stale) and, when a dungeon calls `dg_fight_prep` before `fight_library`, enemy advantage through the existing `combat_enemy_advantage` flag. Outside a run (`dg_in_run` false, set by `dg_run_begin` and cleared by `dg_run_end`) neither changes anything.
* **An Encounter Is a Label the Dungeon's Scene Dispatches To.** The picker returns an id and `pvsc_encounter` sends it to `pvsc_enc_<id>`; an id with no label falls to a stub line that only names it. A fight sets `combat_lib_N` and any overrides, then goes through `pvsc_fight_go`: `dg_fight_prep` (darkness gives the enemies the first strike), `fight_library`, then by `combat_outcome`: `victory` offers a harvest of what the creature drops (`dg_hv_creature`, `dg_harvest`; mire-rats drop nothing), `fled` costs one step back the way you came (`dg_from`, through `dg_step`), `rescued` runs `dg_blackout` (an hour gone, six steps of light burned, back on the previous node), `player_died` goes to the death screen. The dungeon's fights are lethal: `pvsc_fight_go` raises `combat_player_can_die` before `fight_library` and lowers it after (`fight_cleanup` does not reset it, so it would leak into later fights), and sets `death_location_name` and `death_enemy_epithet` for the death screen; with it on a fight is never `rescued`, so `dg_blackout` is for a non-lethal fight. A scene that reads `dg_from` and then calls `dg_step` must do the read inside the step's own lock (`pvsc_fled`, `pvsc_retreat`), because the step changes `dg_from` and a replay would read the changed value. The giant frog, centipede and viper are the library `beast` with name, epithet, hit point, armor and attack overrides (not balance-simmed); the checks (ledge, rising water) are fail-forward (a slip costs 1 to 3 HP, never below 1; a failed wade douses a torch and costs 20 minutes, a lantern keeps burning), and the cache and the lantern-boy are a find and a talk. Rooms are still stubs; ladders and street exits stay at hallway dead ends, never inside a room where something lives.

* **A Spell Can Open an Option in a Dungeon Encounter (the camp mouse, 2026-10-02).** `dungeon.txt` `dg_swa_check` reports what casting Speak with Animals would cost the character and `dg_swa_cast` pays it (replay-locked): a racial knack is free, a Wizard casts it as a ritual with no slot and ten extra minutes (the rule in MAGIC_AND_ABILITIES_REFERENCE.md), a Bard, Ranger or Warlock spends one slot from their own pool. The `camp` encounter offers it once ever (`dg_silt_mouse_met`, kept between runs); a character who knows the spell but has no slot sees the option listed with the reason. A future encounter that offers another known spell should follow this shape: a check routine, a cast routine, and the option listed closed with its reason rather than hidden.

* **A Dungeon Place Is Written in Layers, Not as One Line (2026-10-02).** A place is read many times, and a text dungeon lives on its description, so each node writes (1) what the place IS, twice: a lit version of three or four sentences and a by-touch version for the dark that counts the openings you can feel; then calls `dungeon.txt` `dg_env` for (2) the TIDE line, chosen by how low the place sits (`dg_wet` 0 dry, 1 damp, 2 wet floor) and (3) one AMBIENT detail from a pool of eight that rotates with `dg_steps` (so walking on changes it and a refresh does not; the dark gets sounds, smells and touch). A room that writes its own tide text calls `dg_env_ambient` only. The Gate Hall (r2) is the model for a room: a custom lit/dark/tide opening, state lines for what has already been done this run, two once-per-run actions, and a closed option with its reason when the dark forbids one. Its lacedon fight is the shared `pvsc_enc_lacedon`, triggered by the crossing at high tide until the lacedon is dead for the run (`dg_silt_r2_lacedon_dead`, set in `pvsc_won`).

* **Dungeon Place Codes Stay Internal (2026-10-02).** `j1`, `r2`, `x3` are the scene's and the map's ids and are never shown to the player. A junction is headed by what is distinctive about it ("THE CROSS-DRAIN", "THE FOUR WAYS"), not by a code, and no heading may be near-identical to its neighbour's. The player points at a place with chalk and with those names.

* **A Dungeon Refills Every Few Days, Not Every Run (2026-10-02).** Walking back over ground, or leaving and coming back in, must never be a way to farm. A hallway step rolls its encounter ONCE: `dg_step` makes the roll and sets `dg_done_<node>`, and arriving there again rolls nothing. What the player did in a room (`dg_silt_r1_*`, `dg_silt_r2_*`, `dg_silt_camp_looted`, the lacedon's death) is kept too. Both are cleared by `dungeon.txt` `dg_respawn`, which `dg_run_begin` calls on entry once `dg_respawn_days` (3, about twice a week) campaign days have passed since `dg_reset_day_<dungeon>`. The map and chalk are never cleared, and a CHALKED junction rolls nothing even after a refill, so chalk is how a player keeps a route quiet. A step right after an encounter makes no roll and is not marked; fleeing a fight does not bring the creature back. The Dev walk menu shows the last refill day and has a "Refill the dungeon now" button. Every new dungeon room keeps its once-only state in flags that `dg_respawn` clears, never in `dg_run_begin`.

* **The Vault Pays Once Ever for the Rare Things and Every Refill for the Modest Ones (2026-10-02).** The Silt-Gate Vault (r5) has two actions per refill: the crates (two flasks of lamp oil and a torch, no roll) and the padlocked strongbox (Sleight of Hand DC 13 with ADVANTAGE from a lockpick set, listed closed without one; or Athletics DC 14, a fail cuts you; one try per refill, a fail jams it until the refill). An open box always holds 20 copper. Only the first time it is opened ever, it also holds the Night-Eye Ring (`has_night_eye_ring`). The once-ever piece is decided INSIDE the page's lock into `dg_silt_r5_ring_now`, and the prose reads that, so a refresh prints the same text. (A crews' account book was written and then removed: the user does not build content or hooks for a quest that has not been created yet.) **A worn magic ring that changes a derived flag must not rely on ChoiceScript running when it is put on:** the inventory panel writes `equipped_ring1_id` / `equipped_ring2_id` from JavaScript. `sees_in_dark` is therefore recomputed from the worn rings by `refresh_invocations`, which `dg_dark_check` and the darkness block of `dice_engine` call before they read it. The ring is not attuned; the two ring slots are its cost, which is why a situational ring is a fair find and later general rings will compete with it for them.

* **A Dungeon's Street Entrances Are Earned, and an Exit Lands Where the Ladder Goes (2026-10-02).** The Silt-Gate Channels have two real entrances. The Dredge-End Silt-Gates offer "Go down to the grating" only in the RESOLVED branch of Voss's Contraband quest (`silt_gate_quest_stage`), so the dungeon never overlaps the quest in progress. The Middle Ward wash-house cover leads to the cistern ladder but is barred from above (an iron bar across it) until the player has climbed UP through it from below once (`mw_cistern_open`, set inside the exit page's lock; the first climb prose knocks the bar free). So the first trip is always in through the Silt-Gates, which means after the quest; until then the yard option is closed-listed and says why. The third ladder (the cellar) is bolted from above and listed closed. Because both ends are free, the dungeon is a risky shortcut between Dredge-End and the Middle Ward, paid for in time, light and encounters; leaving by the Silt-Gates lands on the `port_valen_dredge_end` hub, which never re-rolls the night arrival ambush, so arriving that way skips it. `dg_dev_entry` (set by the Developer menu) sends every exit back to the Developer menu. Future, not built: a gated Factors Quarter reached by a bought month-long pass could be bypassed through the dungeon for a price in danger.

* **A Dungeon Is Three Shared Engines Plus Its Own Files; Nothing Is Silt-Specific in the Shared Ones (2026-10-02).** Shared and generic: `scenes/dungeon.txt` (picker, light, darkness, harvest, chalk, refill), `dungeonmap.js` and `dungeonmap.css` (the map panel). A dungeon owns: (1) its scene (`port_valen/port_valen_silt_conduits.txt`), with a `<prefix>_n_<id>` label per place and three labels the engine calls, `pvsc_table` (fills the `dg_trow_` slots: count, then id, low-tide weight and high-tide weight per row, at most 12), `pvsc_respawn` (what a refill clears) and `pvsc_forget_map` (the Developer menu's reset); (2) its map layout, `web/mygame/dungeons/<dungeon>.js`, plus one `<script>` line in `index.html`; (3) its `startup.txt` flags. **Namespacing:** every node id carries a short dungeon prefix (`silt_j1`), so `dg_seen_<id>`, `dg_mark_<id>` and `dg_done_<id>` of two dungeons cannot collide, the room flags are `dg_<prefix>_r<N>_*` (`dg_silt_r1_search`), and the last-refill day is `dg_reset_day_<dg_table>`. Scene labels stay short (`pvsc_n_j1`) because labels are local to their scene. **To add a dungeon:** write its scene and the three labels, its map file, its flags, ONE dispatch line in each of `dg_run_table`, `dg_respawn` and `dg_forget_map` (a scene name must be a literal, so the engine cannot look it up), set `dg_table` before `dg_run_begin` in every entrance, and add the scene to `compile.js`; `tools/check_dungeon_map.js` then checks the map against the scene, that ids carry the prefix, that no id is claimed twice, and that the shared files name no node. The table is filled into slots, not called row by row, because every cross-scene call nests in the headless engine and a 100-pick test run overflows the stack.

* **A Label Reached by *goto Needs a Blank Line Under It (2026-10-02).** ChoiceScript only ends a paragraph when it RUNS a blank line, and a jump skips the lines above the label. A place heading reached from an encounter outcome (`...at a run.` then `*goto pvsc_here`) therefore printed on the same line as the outcome ("...at a run. ◈ HALLWAY J7"). Every `pvsc_n_<id>` label now has an empty line directly under it; new rooms must too. `tools/scripted_play.js` lays pages out the way the screen does and prints `!! LAYOUT` when a heading or banner is glued to the sentence before, so read its output for line breaks, not only for words.

* **The Map Records What Was Seen WITH LIGHT, and Chalk Is Permanent (2026-10-02).** `dg_seen_<node>` is written on arrival only when the player could see (`dg_note_seen`: darkvision or light left, judged before that step's light burns, so a torch that dies on arrival still lit the way in); in the dark the map does not update. `dg_mark_<node>` is a chalk mark: one stick of a six-stick bundle (`dg_chalk_left` is the open bundle, opening one uses a Chalk Sticks item up through `sell_gear`), 5 minutes, replay-locked, forever. Both flag sets outlive a run, and a chalked hallway junction skips its encounter roll on arrival. A new node needs its two `*create` flags in `startup.txt`, and there is a `none` pair so the indirection never fails on an unset position (Quicktest reaches those lines with `dg_pos` at `none`).
* **The Map Panel Is a Copy of the Layout, Guarded by a Check.** `dungeonmap.js` draws an SVG from the flags for whichever dungeon `dg_table` names, and names no dungeon itself. Each dungeon's own list of places and ways (grid positions, east and south positive) lives in `web/mygame/dungeons/<dungeon>.js`, which registers itself in `DungeonMap.maps`; an unknown dungeon draws nothing. `tools/check_dungeon_map.js` compares every file in that folder with its scene and fails on any disagreement.

* **A Dungeon Room Is a Label With Per-Run Flags and Rewards From Systems That Exist (the Landing, 2026-10-02).** `pvsc_n_<room>` prints the header and the tide-aware description, then adds a line for each thing already done (`dg_<room>_<action>` flags, cleared by `dg_run_begin`, so a run is repeatable; the map and the chalk are the only things that persist), then offers its actions once each: a skill check, the result text, a reward on a pass and a cost on a fail (never the reward on a fail, per the fail-forward rule), the time through `dg_time` (`dg_mins` and `dg_time_id` set by the caller; light is per step, not per minute), and a `*goto` back to the room. An action that cannot be taken is still listed and says why (the Landing's steps are closed at high tide, its tally cannot be read without light), the closed-places rule. Rewards are existing items and coin (`grant_gear`, `currency_add`) inside a page-id replay lock, or a flag on the map (`dg_seen_<node>`); a room never invents an item. Option tags follow the usual form: `[~10 min]` then `@{show_stat_hints  [INT DC 10]|}`. The Landing's three actions: read the tally (INT DC 10, light needed, reveals J2 and J3 on the map), feel along the ring bolts (WIS DC 11, a torch and 4 copper or 1 to 3 HP), climb down the steps (STR DC 10, low tide only, a bundle of chalk or 1 to 3 HP).

## 11. Balance Data

* **The Fight Log (`fightlog.js`) Is a Passive Recorder, Never a Rule.** It polls `window.stats` (like the battle HUD) and writes one record per fight to localStorage (`mp_fightlog`, newest 500): class, level, HP, AC, light and darkness, the enemies and any allies (name, HP, AC), every action taken (the option's own label, read from the form at submit time, so the HUD and the plain list both count) with the player's, enemies' and allies' HP just before it, the outcome and the rounds. The end state is the last one seen while the fight ran, because `fight_cleanup` wipes the allies and the Developer hub heals after a fight. Read it with `FightLog.entries()` or the Developer menu's "Export the fight log" (sets `fightlog_export_req`, which the script turns into a `fightlog.json` download). It must never write game state other than clearing that one request flag.
* **Every Fight Opens on the Player's Turn at Close Range Unless It Is an Ambush or a Brawl (2026-10-02).** Changed after the first fight logs (a level-1 wizard, 7 HP, lost 8 of 11 fights, often to damage taken before the first action; the 8 barbarian fights won all). Both rules live inside `combat_roll_initiative`'s existing replay lock, so no caller changes: (1) the player's initiative is forced to the top unless `combat_enemy_advantage` is set (an ambush keeps the honest roll; the dungeon's darkness sets it too), and allies and enemies still sort among themselves; (2) an enemy slot left at range 0 opens at 1 (Close) unless `combat_enemy_advantage` or the new `combat_opens_engaged` (a caller sets it true for a fight already hand to hand; `fight_cleanup` clears it). A melee enemy at Close spends its first turn closing (closing costs its action), so the player gets one clean round; Close or Mid-Range gives one, Long Range gives two. A range a caller sets itself (the dev tests) is untouched. A fight meant to open hand to hand in the story now has to say so with `combat_opens_engaged true`.
