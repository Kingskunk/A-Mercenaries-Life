*comment SHARED SMALL-COMBAT ENGINE
*comment All dice math (attack rolls, damage, spell slots, temp HP, locks)
*comment lives in startup.txt -- this file just wires those primitives into
*comment a playable round-by-round loop and owns the mechanical shell every
*comment fight shares (the choice skeleton, the enemy-turn resolution).
*comment
*comment Calling convention: a scene starts a fight with
*comment   *gosub_scene combat fight_<name>
*comment and gets back combat_outcome set to "victory", "rescued", or
*comment "fled" once it returns. Nothing in here prints start-of-fight or
*comment end-of-fight prose -- that's deliberate: the kill/retreat and
*comment whatever NPC's reaction to it read as one continuous narrative beat
*comment when the calling quest scene writes both together, instead of a
*comment jarring cut between this file's text and theirs.
*comment
*comment Adding a new fight: write a new *label fight_<name> block below
*comment that sets the enemy's stats (combat_enemy_*) and its bespoke
*comment flavor lines (combat_enemy_epithet, combat_flavor_weapon_hit/miss,
*comment combat_flavor_enemy_hit/miss, and optionally
*comment combat_flavor_dissonant_hit/miss), then *gosub fight_setup and
*comment *goto fight_round_hub. Everything else -- every spell/cantrip/
*comment ability option, the enemy's attack resolution, retreat/rescue
*comment handling -- is already shared and needs no duplication.
*comment
*comment Every cantrip (Fire Bolt, Ray of Frost, Shocking Grasp, Eldritch
*comment Blast, Chill Touch, Vicious Mockery) and buff/utility spell below is
*comment its OWN bespoke *choice option with its own real description and
*comment RAW secondary effect where one maps cleanly onto this engine
*comment (Ray of Frost/Vicious Mockery both set combat_enemy_disadvantage,
*comment matching what the dossier's print_ability_card already promises the
*comment player -- see choicescript_stats.txt). This used to be a single
*comment generic "Channel ${attack_cantrip_name}" option reading four shared
*comment variables (has_attack_cantrip/attack_cantrip_name/_stat/
*comment _dice_sides, populated by a detect_attack_cantrip primitive) --
*comment that was more reusable to write but broke two things: every cantrip
*comment read identically ("the working..."), and the *else-chained
*comment detection only ever exposed the FIRST matching cantrip slot, so a
*comment build with two attack cantrips could never reach the second one in
*comment combat at all. Deliberately avoid an enemy-specific wording in these
*comment options -- they describe the PLAYER's own casting motion, not the
*comment creature (parametrize with ${combat_enemy_epithet} instead) -- so
*comment new ones never need a per-fight override, same as the buff spells.
